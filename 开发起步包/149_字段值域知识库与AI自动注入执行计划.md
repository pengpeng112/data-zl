# 字段值域知识库与 AI 自动注入执行计划（修订版 v2）

## 0. 背景与目标

2026-08-24 取数事故：AI 依据错误字典表（`COMM.DISCHARGE_DISPOSITION_DICT`，实为治疗结果）猜值域，把病案首页离院方式 4/5 含义写反（正确：4=非医嘱离院、5=死亡），经 JHEMR `report.r_pat_visit` 交叉验证纠正。事故的三个根因——**负知识缺失**（没人告诉 AI 勿用该字典）、**多来源证据无法表达**（实测+JHEMR+人工确认只能留一条）、**冲突无法暴露**——是本计划建模的直接对象。

**目标**：平台字段值域知识库（唯一权威源）+ AI 获取通道（写 SQL 之前全量到达）+ 多来源证据与冲突检测 + 防猜测维护闭环。

**非目标**：不建通用数据字典系统（`dict_medical` 已有）；与 `asset_columns.value_desc_cn` 分工明确——value_desc_cn 是字段描述文本，值域知识库是结构化代码语义+陷阱，后者引用前者所在列但独立维护；不自动猜测（AI 仅可提交 pending）；不改 126 查询/指标语义。

## 1. 总体架构（修订：注入主路径改道）

```
AI 实测发现值域（强制带证据，只能写 pending）
        │ 唯一约束防重：(system_code, source_code, schema_name, table_name, column_name, code)
        ▼
asset_column_value_domains（主表：一字段一码一现行语义）
  ├─ asset_column_value_domain_evidences（证据一对多：多来源各留一条）★新增
  ├─ asset_column_value_domain_versions（版本时间线）
  │ 写入即做同字段同 code 互斥检测 → conflict_status 暴露 ★新增（不依赖 SQL 解析）
        │ 人工确认（权限码，AI 不可 confirm）→ confirmed
        ├──① 写 SQL 之前：POST /api/v1/ai/context/resolve 与 GET /api/v1/ai/system-context
        │      携带该系统全部 confirmed 值域+陷阱（不依赖列级解析）★修订主路径
        ├──② 写 SQL 之后：/api/v1/ai/propose-sql 基于解析（sqlglot）附精确字段值域（补充路径，
        │      解析失败显式提示"值域未注入"，禁止静默）
        ├──③ 主动查询：/api/v1/value-domains（新路由模块）+ updated_since 增量
        └──④ 离线兜底：value_domains.json（版本/哈希/导出时间/最大龄期）+ 148 导出视图（停手改）
P4（二期）：查询 ingest 字面量 vs confirmed 告警（建立在 144 sqlglot）；值域修订影响分析
```

**主路径裁决依据**（multi-review 证据终审，实测）：`GET /api/v1/ai/system-context` 现签名仅 `system_code+max_tables`（`ai.py:765-770`），无 sql_text 且 `.limit(max_tables)` 无稳定排序——列级解析注入在该接口不可行；`propose-sql` 发生在 SQL 写成之后挡不住生成阶段。故主注入 = 写 SQL 前 context 全量附带（首批仅数十字段，量级无压力）。

## 2. 数据模型（修订：P1 全部落地）

### 2.1 主表 `asset_column_value_domains`

| 字段 | 说明 |
|---|---|
| id / created_at / updated_at | — |
| system_code + source_code + schema_name + table_name + column_name | 定位键，与 `asset_tables/asset_columns` 对齐（HIS 源端 `MEDREC.PAT_VISIT` 与 ODS 镜像 `HIS.PAT_VISIT` 按物理来源各建一条，互不混用）★修订 |
| code | 值（枚举码/阈值表达式/字面量） |
| meaning / note | 含义/备注 |
| **domain_kind** | enum / threshold / literal / **trap（负知识）** ★新增 |
| **scope_condition** | 条件型口径（如"仅住院子集""OPER_STATUS>=35 场景""排班表仅 STATE IN (2,3)"）★新增 |
| status | pending / confirmed / deprecated |
| **conflict_status** | none / conflicted（同字段同 code 存在互斥候选或对立证据时置位，出现在冲突列表与注入提示中）★新增 |
| confirmed_by / confirmed_at / current_version_id | 确认人与版本指针 |
| **唯一约束** | (system_code, source_code, schema_name, table_name, column_name, code) ★新增：幂等与防重复的基础 |

### 2.2 证据子表 `asset_column_value_domain_evidences`（★新增，替代原单值 evidence 字段）

| 字段 | 说明 |
|---|---|
| id / domain_id / created_at | — |
| source_type | live_probe（活库实测）/ cross_system（跨系统交叉如 JHEMR）/ dict_table（字典表，须注明是否可用）/ manual（人工确认）/ ai_probe（AI 实测） |
| source_system / method / sample_count / observed_at / actor / snippet_ref | 来源系统、验证方法、样本数、观测时间、提交者、证据原文引用（如 148 文档小节号） |

事故映射：离院方式 4 的证据将有四条——HIS 实测 120 例、JHEMR 交叉 128 例、用户人工确认、trap 记录"勿用 COMM.DISCHARGE_DISPOSITION_DICT"。

### 2.3 版本表 `asset_column_value_domain_versions`（不变）

domain_id、version_no、快照（code/meaning/note/status/conflict_status）、change_reason、evidence_ref、actor、created_at。版本是串行采纳时间线，**不是**并行假说集——并行候选放主表多 pending + conflict_status。

### 2.4 冲突检测（★从 P4 前移至 P1，纯库内比对，不依赖 SQL 解析）

- POST 候选 / PATCH confirm / 新证据写入时：比对同 (定位键, code) 既有记录，meaning 不一致 → 相关记录 conflict_status=conflicted 并在响应中列出 competing meanings；
- conflict 未解决（人工裁决前）的记录不进入注入链路（降级为仅 pending 可见）；
- API 提供 `GET /api/v1/value-domains?conflicted=true` 冲突列表。
