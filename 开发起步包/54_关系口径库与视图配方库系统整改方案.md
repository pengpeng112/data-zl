# 关系口径库与视图配方库系统整改方案

## 0. 2026-07-14 扩展开发裁决

### 0.1 本轮必须实现

1. 配方新增、编辑、复制、版本比较、提交审核、批准、驳回、停用和只读查询。
2. 平台库保存配方元数据、版本、证据、审核状态与完整审计；迁移必须手写且可回滚。
3. JSON Schema 和服务端语义校验：表/字段存在性、join 键、过滤条件、方言、参数、脱敏和大表限制。
4. 与关系图谱联动：从关系边打开配方、从配方定位图谱证据、区分正式/候选/D 类待验证。
5. 视图流程：生成 SQL、格式化、风险校验、影响分析、预览、下载/复制、人工审批记录。
6. AI 只能读取已批准配方并生成建议，不得调用编辑、审批或执行端点。

### 0.2 自动建视图的硬边界

- 本轮默认只生成 SQL，不直接执行 DDL。
- HIS、ODS、HRP、LIS、PACS、EMR、YDHL、SM 等业务源库禁止 `CREATE VIEW` 或任何 DDL/DML。
- 如需真正创建视图，只能在未来明确指定的专用目标库中执行，并要求：独立写账号、目标白名单、审批、SQL 哈希、备份/回滚、审计和用户再次授权。
- 不得复用运维写通道绕过本模块审批，也不得把执行能力暴露给 AI。

### 0.3 建议状态机

`draft → submitted → approved → active → deprecated`，驳回回到 `draft`。已批准版本不可原地覆盖，编辑必须生成新版本。任何状态变更记录操作者、时间、原因和内容哈希。

### 0.4 验收

- CRUD、版本、审核、停用、检索、图谱联动全链路通过。
- 危险 SQL、多语句、DDL、未知表字段、D 类自动晋升、越权编辑均被拒绝。
- 未审批配方不进入 AI 正式上下文；已批准版本可追溯到证据关系。
- 业务源库保持零写、零 DDL。

## 1. 背景

当前系统已经沉淀了大量表结构、关系验证和治理资产，且用户会持续补充业务关系口径，例如：

- 检查/影像报告视图中 `EXAM_MASTER`、`EXAM_REPORT`、`PAT_VISIT`、`OUTP_TREAT_REC`、`CLINIC_MASTER` 的正式关联口径。
- 门诊关系必须先聚合明细表，避免行数放大。
- 某些字段名看似可关联但不能作为正式口径，例如检查场景中的 `ORDER_ID`。

目前这些关系主要散落在 Markdown 文档、CSV、JSON 和聊天记录里。虽然已经新增 `53_检查影像报告视图关系口径.md` 和 `数据资产_关系图谱/view_relation_recipes.json`，但系统内还缺少统一的维护、检索、展示、导入、AI 读取能力。

本方案目标是把用户持续提供的业务关系，从“文档资产”升级为“系统可维护资产”。

## 2. 用户需要的核心功能

用户后续会经常提供新的表关系、视图关系和业务口径，系统需要支持：

1. 能把用户提供的关系长期保存，不丢失、不只停留在聊天记录。
2. 能区分“正式可用关系”“候选关系”“禁止使用口径”“待验证关系”。
3. 能在系统里直观看到某个业务视图依赖哪些表、怎么 join、为什么这么 join。
4. 能让 AI 写 SQL/视图前读取系统里的关系配方，而不是重新猜关系。
5. 能在图谱里点击关系边看到验证证据、风险说明、来源文档和推荐 SQL 片段。
6. 能维护“字段取值优先级”，例如就诊流水号、报告时间、住院号怎么从多表取值。
7. 能记录“禁止口径”，例如某些字段覆盖率低、有患者不一致风险，后续 AI 不应使用。
8. 能从 `view_relation_recipes.json` 导入初始配方，并支持后续增量导入。
9. 能给外部 AI 或系统内部 AI 提供只读 API，让 AI 获取关系配方、证据和禁用规则。
10. 能和现有资产图谱、资产表详情、AI SQL 草稿、视图生成流程打通。

## 3. 总体目标

建设两个系统能力：

| 能力 | 说明 |
|---|---|
| 关系口径库 | 管理“表与表怎么关联”的业务确认口径，包括正式、候选、禁止、待验证关系。 |
| 视图配方库 | 管理“某个业务视图如何组合多张表”的 SQL 生成配方，包括 join、过滤、聚合、字段优先级和验证证据。 |

第一阶段以最小可用为目标，不做复杂编辑器，优先实现：

- 后端一张 JSONB 主表存配方。
- 导入 `view_relation_recipes.json`。
- 提供只读查询 API。
- 前端新增查看页面。
- 图谱边/节点能跳转到配方详情。
- AI 可以通过 API 读取配方。

## 5. 状态模型

关系和配方必须有状态，避免 AI 把候选关系当正式关系。

| 状态 | 含义 | AI 使用规则 |
|---|---|---|
| `candidate` | 候选关系 | 只能提示，不得直接生成正式视图。 |
| `verified` | 数据库验证通过 | 可用于 SQL 草稿，但建议标注证据。 |
| `user_confirmed` | 用户确认口径 | 优先使用。 |
| `formal` | 已进入正式资产/图谱 | 可作为正式关系使用。 |
| `deprecated` | 废弃关系 | 不允许使用。 |
| `forbidden` | 明确禁止口径 | AI 生成 SQL 时必须避开。 |
| `deferred` | 延后待验证 | 展示为待分析，不能进入正式视图。 |

## 6. 后端数据模型建议

### 6.0 `recipe_id` 命名规范

`recipe_id` 不建议使用过长的视图名拼接。统一采用：

```text
<domain>_<scene>_v<version>
```

示例：

| 字段 | 示例 |
|---|---|
| `recipe_id` | `exam_reports_v1` |
| `recipe_name` | `检查影像报告视图配方` |
| `business_domain` | `exam_imaging_report` |
| `recommended_view_name` | `V_INP_EXAM_REPORTS` |

旧版长 ID（如 `V_INP_EXAM_REPORTS_EXAM_OUTPATIENT_INPATIENT`）可作为 `legacy_recipe_id` 放入 `recipe_json`，导入时优先生成规范化短 ID。若不做自动转换，至少在前端展示中文名和短别名，避免用户直接面对过长 ID。

### 6.1 第一阶段主表

新增表：`asset.asset_relation_recipes`

建议字段：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | bigint / uuid | 主键 |
| `recipe_id` | varchar | 配方唯一编码，如 `exam_reports_v1`；与 `version` 组成唯一约束 |
| `recipe_name` | varchar | 中文名称 |
| `version` | integer | 配方版本，默认 `1` |
| `is_active` | boolean | 是否启用，默认 `true`；查询默认只返回启用版本 |
| `business_domain` | varchar | 业务域，如 `exam_imaging_report` |
| `source_system` | varchar | 来源系统，如 `HISUSER/HIS` |
| `recommended_view_name` | varchar | 推荐视图名 |
| `status` | varchar | 状态：`user_confirmed/formal/...` |
| `recipe_json` | json/jsonb | 完整机器可读配方 |
| `evidence_doc` | varchar | 来源文档，如 `53_检查影像报告视图关系口径.md` |
| `evidence_summary` | text | 验证摘要 |
| `risk_summary` | text | 风险摘要，如一对多、患者不一致、覆盖率低 |
| `created_by` | varchar | 创建人/AI |
| `updated_by` | varchar | 更新人/AI |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

唯一约束建议：

```text
UNIQUE(recipe_id, version)
```

第一阶段避免过度拆表，`recipe_json` 保留完整结构；后续需要高级检索时再拆 `recipe_tables/recipe_joins/recipe_evidence`。

默认查询规则：

- 只返回 `is_active = true`。
- 若同一 `recipe_id` 有多个版本，默认返回最高 `version`。
- `deprecated` 代表业务状态废弃，`is_active=false` 代表系统层停用或隐藏。

| `asset_relation_recipe_joins` | 每条 join 条件。 |

| `asset_relation_recipe_forbidden_joins` | 禁止使用口径。 |

## 7. 配方 JSON 标准

后续所有用户补充关系都应转成统一 JSON。现有入口：

```text
开发起步包/数据资产_关系图谱/view_relation_recipes.json
```

推荐结构：

```json
{
  "recipe_id": "唯一编码",
  "status": "user_confirmed",
  "domain": "业务域",
  "source_system": "HISUSER/HIS",
  "recommended_view_name": "建议视图名",
  "description": "业务说明",
  "primary_tables": [],
  "joins": [],
  "filters": [],
  "dedup_strategy": {},
  "field_logic": {},
  "do_not_use_as_primary_join": [],
  "validation_evidence": {},
  "hard_rules": [],
  "human_readable_doc": "对应文档"
}
```

### 7.1 必填校验

导入脚本必须校验以下字段，缺失则拒绝导入并输出错误清单：

| 字段 | 要求 |
|---|---|
| `recipe_id` | 必填，字符串 |
| `status` | 必填，必须属于状态枚举 |
| `domain` | 必填，字符串 |
| `primary_tables` | 必填，数组，可为空但必须存在 |
| `joins` | 必填，数组，可为空但必须存在 |
| `human_readable_doc` | 必填，字符串 |

建议校验状态枚举：

```text
candidate, verified, user_confirmed, formal, deprecated, forbidden, deferred
```

### 7.2 JSON Schema 后续要求

第一阶段可以先做必填字段校验；P2 再补完整 JSON Schema。若第一阶段实现成本允许，建议直接在后端新增轻量 schema 校验函数，避免前端和 AI 读取结构不稳定。

## 8. 后端 API 设计

### 8.1 查询接口

```text
GET /api/v1/relation-recipes
```

查询参数：

| 参数 | 说明 |
|---|---|
| `page` | 页码，从 1 开始，默认 1 |
| `page_size` | 每页数量，默认 20，最大 100 |
| `keyword` | 搜索视图名、表名、业务说明。 |
| `domain` | 业务域。 |
| `source_system` | 来源系统。 |
| `status` | 状态。 |
| `table` | 涉及表，如 `EXAM.EXAM_MASTER`。 |
| `view_name` | 推荐视图名。 |
| `include_inactive` | 是否包含停用版本，默认 `false`。 |

排序规则：

1. 状态优先级：`formal > user_confirmed > verified > candidate > deferred > deprecated > forbidden`。
2. 同状态按 `updated_at DESC`。
3. 同一 `recipe_id` 默认只返回最高启用版本。

返回字段：

```json
{
  "page": 1,
  "page_size": 20,
  "items": [
    {
      "recipe_id": "...",
      "recipe_name": "...",
      "version": 1,
      "is_active": true,
      "business_domain": "...",
      "source_system": "...",
      "recommended_view_name": "...",
      "status": "user_confirmed",
      "primary_tables_count": 8,
      "joins_count": 6,
      "forbidden_joins_count": 1,
      "evidence_doc": "...",
      "updated_at": "..."
    }
  ],
  "total": 1
}
```

### 8.2 详情接口

```text
GET /api/v1/relation-recipes/{recipe_id}
```

返回完整 `recipe_json`，以及标准化摘要：

- 涉及表。
- 正式 join。
- 必须过滤条件。
- 聚合/去重逻辑。
- 字段取值优先级。
- 禁止口径。
- 验证证据。
- 来源文档。

### 8.3 导入接口或脚本

优先做脚本，避免开放写接口过早复杂化：

```text
backend/scripts/import_relation_recipes.py
```

输入：

```text
开发起步包/数据资产_关系图谱/view_relation_recipes.json
```

行为：

- 按 `recipe_id` upsert。
- 不删除系统中已有配方。
- 保留 `created_at`，更新 `updated_at`。
- 导入完成输出统计。

后续如做接口：

```text
POST /api/v1/relation-recipes/import-json
```

必须限制管理员权限，且记录审计。

### 8.4 AI 只读接口

```text
GET /api/v1/ai/relation-recipes?domain=exam_imaging_report
GET /api/v1/ai/relation-recipes/by-table?table=EXAM.EXAM_MASTER
GET /api/v1/ai/relation-recipes/{recipe_id}/prompt-context
```

`by-table` 返回数组，因为一张表可能参与多个配方。排序同列表接口：`formal > user_confirmed > verified > candidate`，再按 `updated_at DESC`。

`prompt-context` 应返回 AI 友好的精简上下文：

- 推荐 join。
- 禁止 join。
- SQL 片段。
- 字段逻辑。
- 验证证据摘要。
- 硬规则。

不返回敏感明细数据。

`prompt-context` 返回示例：

```json
{
  "recipe_id": "exam_reports_v1",
  "recipe_name": "检查影像报告视图配方",
  "status": "user_confirmed",
  "recommended_view_name": "V_INP_EXAM_REPORTS",
  "must_use_joins": [
    "er.EXAM_NO = em.EXAM_NO",
    "pv.PATIENT_ID = em.PATIENT_ID AND pv.VISIT_ID = em.VISIT_ID",
    "e_or.APPOINT_NO = TO_CHAR(em.EXAM_NO) AND e_or.PATIENT_ID = TO_CHAR(em.PATIENT_ID)"
  ],
  "forbidden_joins": [
    {
      "condition": "EXAM_MASTER.ORDER_ID = OUTP_TREAT_REC.ORDER_ID",
      "reason": "覆盖率低，存在患者不一致和一对多风险"
    }
  ],
  "field_logic": {
    "report_time": "NVL(er.report_time, em.report_date_time)"
  },
  "sql_fragments": {
    "outpatient_subquery": "LEFT JOIN (...) e_or ON ..."
  },
  "hard_rules": [
    "门诊部分必须先聚合 OUTP_TREAT_REC，不允许直接明细表关联。"
  ],
  "evidence_summary": "修复后 V_INP_EXAM_REPORTS 总行数 298048，去重数 298048，重复明细 0。"
}
```

权限建议：

| 权限点 | 用途 |
|---|---|
| `asset:relation_recipe:view` | 查看列表和详情 |
| `asset:relation_recipe:import` | 执行导入脚本或导入接口 |
| `asset:relation_recipe:export` | 导出完整 JSON |
| `asset:relation_recipe:admin` | 后续在线编辑和状态变更 |

具体权限编码实现时可按现有 RBAC 命名规范微调，但必须保留“查看、导入、导出、管理”四类能力边界。

## 9. 前端页面设计

```text
关系口径库 / 视图配方库
```

### 9.1 列表页

筛选条件：

- 关键词。
- 业务域。
- 来源系统。
- 状态。
- 涉及表。
- 推荐视图名。

列表列：

| 列 | 说明 |
|---|---|
| 配方名称 | 中文名称/recipe_id。 |
| 业务域 | 如检查影像报告。 |
| 来源系统 | HIS/HRP/ODS 等。 |
| 推荐视图 | 如 `V_INP_EXAM_REPORTS`。 |
| 状态 | 用户确认/正式/候选/禁用。 |
| 涉及表数 | 主表数量。 |
| Join 数 | join 条件数。 |
| 禁止口径数 | 禁用 join 数。 |

| 操作 | 查看详情、复制 AI 上下文、图谱定位。 |

### 9.2 详情页 / 抽屉

详情需要展示：

1. 基本信息：业务域、系统、视图名、状态。
2. 涉及表：表名、别名、角色。
3. 正式 join：条件、验证等级、说明。
4. 聚合/去重逻辑：例如 `ROW_NUMBER() rn=1`。
5. 字段取值逻辑：字段名、优先级表达式。
6. 禁止口径：条件、禁止原因。
7. 验证证据：总行数、重复数、孤儿数、患者不一致、一对多风险。
8. SQL 片段：可复制。
9. 来源文档：第一阶段显示文档路径，不实现在线打开。
10. AI 上下文：一键复制“写视图提示词”。

### 9.3 页面交互重点

- 对 `forbidden` 或 `deprecated` 口径使用红色警示。
- 对 `user_confirmed/formal` 口径使用绿色/蓝色标记。
- 对 `candidate/deferred` 使用灰色/橙色，提示不可直接用于正式视图。
- SQL 片段必须只读展示，不提供直接执行按钮。
- 第一阶段只显示来源文档路径，不实现在线打开 Markdown；若后续要打开文档，需要单独提供文件服务或 Git 链接。
- 页面按现有 Element Plus 响应式布局实现，优先保证桌面端体验，移动端可折叠筛选区和详情抽屉。

### 9.4 前端权限控制

第一阶段权限建议：

| 能力 | 权限 | 说明 |
|---|---|---|
| 查看列表/详情 | `asset:relation_recipe:view` | 普通资产治理用户可用 |
| 复制 AI 上下文 | `asset:relation_recipe:view` | 只读能力，可开放给 AI 协作用户 |
| 导入 JSON | `asset:relation_recipe:import` | 仅管理员或数据资产管理员 |

## 10. 图谱联动设计

现有图谱已支持节点、边、证据详情。需要增强：

1. 图谱边详情中增加“相关视图配方”。
2. 表节点详情中增加“涉及该表的视图配方”。
3. 配方详情页提供“在图谱中定位”按钮。
4. 对同一配方内的表和边进行临时高亮。
5. 第一阶段禁止口径不进入图谱展示，只在配方详情里展示，避免误用。

图层建议：

| 图层 | 默认 | 说明 |
|---|---|---|
| 正式关系 | 开 | 当前治理关系。 |
| 视图配方关系 | 开 | 某业务视图使用的 join。 |
| 禁止口径 | 不展示 | 第一阶段仅在配方详情中警示，不进入图谱边。 |
| 待验证关系 | 关 | candidate/deferred。 |

关系处理原则：

- `recipe` 中的 join 与现有治理关系并行存在，不覆盖 `asset_relations` 或 `governance_relations`。
- 第一阶段不把 recipe join 自动写入正式关系图谱。
- 若某条 recipe join 与正式治理关系相同，仅在边详情中增加“相关视图配方”引用。
- 若 recipe join 尚未在正式关系表中存在，仅作为视图配方关系展示，不提升为正式关系。

## 11. 和 AI SQL / 视图生成的联动

后续 AI 写视图时流程应变成：

1. 用户提出“生成某业务视图”。
2. AI 先查 `relation-recipes`。
3. 若命中配方，必须按配方 join 和字段逻辑生成 SQL。
4. AI 必须避开 `do_not_use_as_primary_join`。
5. 生成 SQL 草稿后进入现有 AI SQL 审核链路。
6. 只允许人工审核后执行只读验证。
7. 不自动 DDL 创建视图。

第一阶段靠提示词和 AI context 约束 SQL 生成；P2 可考虑在 AI SQL 草稿表中增加 `recipe_id` 字段，保存草稿时记录使用的配方。

禁止口径检测建议：

- 第一阶段：`prompt-context` 必须显著返回 `forbidden_joins`，前端详情也必须红色展示。
- P2：AI SQL 草稿保存或风险扫描时，对 `forbidden_joins` 做文本匹配告警。
- 告警只阻断自动执行，不阻断人工查看；人工若坚持使用，必须重新提交验证证据和说明。

需要给 AI 的上下文示例：

```text
你正在生成检查影像报告视图。必须使用 recipe_id=exam_reports_v1；若历史数据仍使用 legacy_recipe_id=V_INP_EXAM_REPORTS_EXAM_OUTPATIENT_INPATIENT，也按同一配方处理。
住院按 PAT_VISIT 的 PATIENT_ID+VISIT_ID。
门诊按 OUTP_TREAT_REC.APPOINT_NO=EXAM_MASTER.EXAM_NO，并先聚合 rn=1。
禁止使用 EXAM_MASTER.ORDER_ID=OUTP_TREAT_REC.ORDER_ID 作为主口径。
```

## 12. 权限与安全

第一阶段全部只读展示，只有导入脚本写平台元数据库。

安全要求：

- 不连接源业务库执行写操作。
- 不执行 DDL。
- 不自动创建视图。
- 不输出 PII 明细。
- 导入 JSON 只写平台库 `asset` schema。
- AI 接口只返回元数据、关系、SQL 片段和验证摘要。
- `recipe_json` 中的 SQL 片段属于元数据级资产，不包含账号密码和明细数据；但不对普通用户开放全量导出，导出需 `asset:relation_recipe:export` 权限。
- 日志禁止打印完整 `recipe_json`；导入脚本和 API 日志只打印 `recipe_id`、`version`、状态、数量和错误摘要，错误详情限制长度。

后续如支持在线编辑：

- 只能管理员编辑。
- 需要版本号。
- 需要审计。
- 不能覆盖历史版本。
- 正式状态变更必须人工确认。
