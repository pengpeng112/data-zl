# 平台功能与资产导航统一整改执行计划

## 0. 结论先行

本计划把原 72 和 73 合并为一个执行入口，覆盖：

1. **E9：人员画像、权限申请审批、后端细粒度权限、数据范围权限。**
2. **E10：关系配方 CRUD、版本、审核、图谱联动和受控视图 SQL 生成。**
3. **E11：业务系统与数据资源合并、按真实目标 IP 归并系统、资源树重构、关系图谱显示与交互修复。**

不得只完成页面而不完成后端授权、迁移、审计和测试；不得只写代码而不执行浏览器验收；不得把“生成视图 SQL”偷换成“在业务源库执行 DDL”。

## 1. 已确认事实和不可变口径

### 1.1 业务系统口径

当前一级业务系统只有：

| 一级系统 | 归并依据 | 当前内容 |
|---|---|---|
| HIS | HIS 真实数据库目标 IP | HIS 多 Owner 源端 |
| HRP | HRP 真实数据库目标 IP | HRP 源端，WA_* 待补采 |
| 数据中心 | 数据中心真实数据库目标 IP | ODS 汇聚，含 HIS/LIS/PACS/YDHL/SM/JHEMR/CDA 等 Owner/Schema |

强制规则：

1. 同一真实目标 IP 只能属于一个一级系统。
2. 同 IP 不同端口、Service、SID、Database 是同一系统下的不同连接/库实例。
3. 跳板机、应用服务器、Nginx 的 IP 不能作为业务系统身份。
4. 数据中心内 LIS/PACS/移动护理/手麻等不是一级系统。
5. 未来接入这些系统的独立数据库 IP 后，才新增对应一级系统。

### 1.2 安全口径

1. HIS/ODS/HRP/LIS/PACS/EMR/YDHL/SM 等业务源库只允许 `SELECT`。
2. 业务源库禁止 DML、DDL、`CREATE VIEW`、存储过程执行和跨库写事务。
3. 平台库写入必须有后端权限、审批、审计和幂等控制。
4. AI 只能读取已批准数据和配方，不得调用审批、编辑或执行端点。
5. 密码只写不读，不得明文入平台表、API 响应、日志、Git、文档或浏览器存储。
6. 前端隐藏按钮不等于权限控制，所有写端点必须后端校验。
7. 运维写通道生产开关保持关闭。

### 1.3 已有能力，不得重复建设

- 登录、JWT、Refresh Cookie、ApiKey 双凭证已存在。
- `IdentityPerson/Department/Account/Source/SyncDiff` 已存在。
- `GovernChangeRequest` 和 `GovernAuditLog` 已用于身份审批。
- `AssetRole/AssetUserRole/AssetRolePermission` 已存在。
- 前端 `v-perms`、`hasPerms`、`<Perms>` 已存在。
- 配方只读模型和 `/api/v1/recipes` 查询 API 已存在。
- 资产树已有懒加载基础。
- 图谱已有 SVG/G6 两套组件，但显示和语义需要统一。

## 2. 对 73 号待复核决策的最终裁定

| 决策 | 最终方案 | 原因 |
|---|---|---|
| A 权限申请表 | **复用 `GovernChangeRequest`**，不新建 `asset_permission_requests` | 已有审批、禁止自审批、执行、审计范式；有效期和目标角色放 `request_payload`，执行结果写用户角色/数据范围表 |
| B 后端权限校验 | **FastAPI `Depends(require_permission(...))`** | 符合现有依赖注入风格，易测试、易组合，避免装饰器签名问题 |
| C 配方版本模型 | **原表扩展为一行一个版本，移除 recipe_id 单列唯一，新增 `(recipe_id, version)` 唯一** | 保留现有表和数据，减少新主从模型复杂度；批准/激活版本不可原地修改 |
| D 路由命名 | **保留 `/api/v1/recipes`** | 不破坏现有注册、调用和 RBAC 前缀；前端菜单可叫“关系配方库” |
| E 人员画像编辑 | **走 `GovernChangeRequest` 审批** | 人员画像属于治理主档，不能直接写；申请人与审批人分离 |
| F 权限资源目录 | **新增平台表持久化，当前硬编码目录只作种子和兼容回退** | 用户要求资源持久化和后续维护；只靠硬编码无法在线治理 |
| E10 范围 | **本轮包含图谱联动和 SQL 生成** | 用户已确认可做；73 将其推迟与当前范围冲突 |
| 视图执行 | **默认只生成/校验/预览/下载 SQL，不执行** | 业务源库零 DDL；未来专用目标库执行必须再次授权 |

## 3. 总体执行顺序

必须按以下顺序：

`S0 基线 → S1 公共权限底座 → S2 E9 人员权限 → S3 E10 配方库 → S4 E11 系统资源 → S5 E11 图谱 → S6 全量回归 → S7 发布与文档`

### 5.4 后端权限依赖

修改 `backend/app/core/security.py`，保留 `get_current_user()`，新增：

```python
def require_permission(resource_code: str):
    def dependency(
        request: Request,
        db: Session = Depends(get_db),
    ) -> str:
        user = get_current_user(request)
        # 1. 从 request.state.roles 或 DB 获取有效角色
        # 2. 排除 revoked/expired 和超过 expires_at 的角色
        # 3. platform_admin 或 *:*:* 可通配
        # 4. 查 AssetRolePermission / Resource
        # 5. 无权限写拒绝审计（不得记录 Token）
        # 6. 无权限 raise HTTPException(403)
        return user
    return dependency
```

注意：

1. 不能信任前端传入 operator/applicant/approver。
2. `request.state.roles` 仅作已认证上下文，最终权限以平台库有效角色和权限为准。
3. 过期角色和 scope 必须实时拒绝。
4. 公共只读端点继续走既有认证策略；所有本轮新增写端点强制 `require_permission`。
5. 写拒绝审计放 `GovernAuditLog` 或专门安全日志，避免每个 GET 拒绝制造海量数据库写入；至少测试环境可验证。

### 6.4 权限申请审批流

不新建权限申请表。扩展 `backend/app/api/v1/permissions.py` 或新建 `permission_requests.py`（推荐新文件，仍使用 GovernChangeRequest 模型）：

- `POST /api/v1/permission-requests`
- `GET /api/v1/permission-requests/mine`

- `GET /api/v1/permission-requests/{id}`
- `PATCH /api/v1/permission-requests/{id}/approve`
- `PATCH /api/v1/permission-requests/{id}/reject`
- `POST /api/v1/permission-requests/{id}/execute`
- `POST /api/v1/permission-requests/{id}/revoke`

请求模型：

```text
request_kind: role | data_scope
target_user_identifier
role_code（role 时必填）
scope_type/system_code/source_code/schema_name/domain/filter_json（scope 时使用）
valid_from/valid_to
reason
```

写入 `GovernChangeRequest`：

```text
module=permission
entity_type=user_role 或 user_data_scope
entity_ref=target_user_identifier
request_type=grant/revoke
request_payload=完整结构
approval_status=pending
requested_by=current_user
```

约束：

1. applicant 从 token 派生。
2. 禁止自审批：`approved_by != requested_by`。
3. 审批不等于生效；只有 execute 写 `AssetUserRole/AssetUserDataScope`。
4. execute 必须 `require_permission("permission:request:execute")`。
5. 同一审批单只能成功执行一次。
6. revoke 同样走审批，不允许直接删除角色。
7. 不允许申请不存在或禁用的角色/资源范围。
8. `valid_to <= valid_from` 返回 400。
