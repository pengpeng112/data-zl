## 2. 问题-方案对照（round-3 定稿，含修改点）

### P1 后端：overview 聚合 N+1（高·阻断）

- **根因**（核查报告 P1，三方一致+源码裁决）：`backend/app/api/v1/graph.py:1683-1692` 聚合边计算对全量 `AssetRelation`（1329 条）逐条调 `_resolve_relation_endpoint(db, rel, ...)` 且**不传 resolver**，物理键缺失行每条触发全表反查（N+1）；同文件 1586 行 object 分支已用 `_EndpointResolver.load(db)` 预载索引——聚合分支漏用。实测 23.5~24.9s。
- **修改**：聚合分支（`if nodes:` 块前）加载一次 `endpoint_resolver = _EndpointResolver.load(db)`，两处 `_resolve_relation_endpoint(db, rel, "from"/"to")` 改传 `resolver=endpoint_resolver`（与 1589-1590 行 object 分支同款写法）。**只增参数不改函数**。
- **验收**：隔离库 `curl -w '%{time_total}'` 三次取中位 **<1.5s**（数据规模 12702 表/1329 关系）；`pytest tests/test_graph*.py tests/test_graph_contract.py -q` 全绿。

### P1b 后端：object 层全量关系读取（中）

- **现状**（codex 独立发现）：`graph.py:1586-1603` object 层 limit 200 表但无条件 `select(AssetRelation)` 全量。P1 修复后 resolver 使其为一次查询+内存解析，可接受。
- **修改**：无独立代码改动；P1 验收顺带断言 object 层耗时 <3s。若实测仍慢，仅允许加 `rel_stmt` 与展示节点相关的预过滤（按 object_ids 命中的逻辑四元组过滤），登记 exceptions 后实施。

### P5 后端：overview meta 口径错位（低）

- **根因**（核查报告 P5，三方互证）：`graph.py:1714-1726` 非 object 分支 `_graph_meta(matched_assets, matched_assets, len(edges), matched_assets > len(nodes), ...)` 把**表数**填进 `total_relations/matched_relations`，`truncated` 恒 true——工具栏显示「总数 12702/返回 1/已截断」误导（与 977-999 行全局端点语义冲突）。
- **修改**：非 object 分支 meta 改为——`total_relations` = 满足 domain 过滤的 `count(AssetRelation)`（一次 count 查询，复用 rel_stmt 条件）；`matched_relations` = `sum(pair_counts.values())`（参与聚合配对的关系数）；`returned_relations` = `len(edges)`；`truncated` = `matched_relations > returned_relations`（聚合去重导致，语义真实）。**不动** object 分支（1703-1712 行语义本正确）与 `GraphToolbar` 文案。
- **验收**：新增后端测试——隔离库请求 `level=system`，断言 `total_relations==1329`（关系数而非表数）、`returned_relations==len(edges)`、`matched_relations>=returned_relations`。

### P2 前端：force 布局中心坍缩（高·阻断=用户主诉）

