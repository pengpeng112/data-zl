## 1. 目标与范围

当前运行版本已部署 Token/RBAC 基础能力，但前端模板调用 `/login`，后端没有对应的用户名密码认证接口。因此本计划分两条主线：

1. 建立可用于生产的本地账号密码登录，首位平台管理员可以登录网页并维护人员、角色和业务系统连接。
2. 按只读、安全、可审计原则接入 HIS、HRP、ODS、LIS、PACS、EMR、移动护理和手麻等业务系统，先实现连接检测、元数据与人员同步，再逐步启用治理功能。

不在本计划范围：向任何业务源库写数据、把密码或 Token 写入前端/代码/Git/文档、让 AI 执行平台写操作、未经审批的跨库同步与跨库事务。

## 3. 核心设计决策

| 决策 | 方案 | 原因 |
|---|---|---|
| 第一阶段认证 | 本地平台账号 + 密码 + 短期 Access Token + HttpOnly Refresh Cookie | 不依赖医院统一认证即可上线；兼容现有 Bearer 鉴权和 Vue 模板 |
| 密码存储 | Argon2id 哈希，参数由后端统一配置 | 不存明文或可逆密码；不得复用 API Token/数据库密码 |
| 首位管理员 | 受控部署脚本一次性创建 `platform-admin` 本地账号、绑定 `platform_admin` 角色 | 消除当前“仅 root 文件保存 Token”的网页登录障碍 |
| 会话存储 | 新建 `asset_auth_sessions`，只保存 Refresh Token 哈希、用户、到期时间、撤销时间和审计信息 | 支持登出、失效、轮换和按设备撤销，不污染 `asset_api_keys` 的服务 Token 语义 |
| 人员绑定 | 本地账号以 `user_identifier` 绑定 `asset_identity_persons.person_code`；首位管理员允许先使用平台内部标识 | 人员来源继续由 HIS/HRP 同步维护，不手工篡改人员主档 |
| 统一认证 | 第二阶段预留 OIDC/OAuth2；医院现有 SSO 确认协议后再接入 | 不自行猜测医院账号、LDAP 或 SAML 协议 |
| 业务源连接 | 每个业务系统独立只读服务账号、独立 `source_code`、独立凭据引用 | 最小权限、可撤销、可审计，杜绝共享超管账号 |
| 同步模式 | 先 metadata/字典/人员 dry-run，再差异复核、审批、写平台库 | 源库零写，平台写入可追溯、可回滚 |

## 4. 工作流 A：网页登录与权限闭环

### A0 需求确认与安全准备

1. 确认本地账号命名规则：建议平台账号 `platform-admin`、普通账号使用 HRP/HIS 工号或医院统一员工号。
2. 确认密码策略：最少 12 位、复杂度、首次登录强制改密、连续失败锁定、失效周期和管理员解锁流程。
3. 确认会话策略：Access Token 15 分钟、Refresh Token 8 小时或按医院安全制度设定；退出、改密、禁用账号必须撤销全部会话。
4. 明确登录审计字段：账号标识、结果、失败原因分类、时间、脱敏 IP/客户端；不得记录密码、Token 或完整个人信息。
5. 凭据安全：用户已取消本轮轮换要求，但现有数据库密码与 Token 仍不得作为网页登录密码，也不得进入代码、日志、Git 或文档。

**验收**：安全策略经业务负责人、信息科/安全负责人确认，形成配置项和测试用例，不记录实际密码。

### A1 数据模型与迁移

新增表均使用 `asset` schema 和 `asset_auth_<实体>` 前缀，迁移必须手写 `upgrade()`/`downgrade()`：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `asset_auth_users` | `username`、`password_hash`、`user_identifier`、`enabled`、`must_change_password`、`failed_login_count`、`locked_until`、`last_login_at` | 本地账户，不保存明文密码 |
| `asset_auth_sessions` | `user_id`、`refresh_token_hash`、`expires_at`、`revoked_at`、`created_at`、`last_used_at` | Refresh Token 轮换、撤销和会话审计 |
| `asset_auth_login_events` | `username`、`user_identifier`、`result`、`reason_code`、`client_ip_masked`、`created_at` | 登录成功/失败审计 |

约束：用户名唯一；`user_identifier` 可为空以支持首位管理员；Refresh Token 哈希唯一；所有查询按索引覆盖用户名、用户、有效会话和时间。

**⚠️ 补强（2026-07-13 复核新增）——依赖与 Token 选型**：

1. **新增依赖**（当前 `backend/requirements.txt` 没有，必须加）：
   - `argon2-cffi>=23.1` —— Argon2id 密码哈希（A2 要求，不要用 passlib 的 bcrypt 回退）。
   - `python-jose[cryptography]>=3.3` —— JWT 签发/校验。
   - 这两项加入 `requirements.txt`，并同步到离线 wheelhouse（见 58 号 R2 锁定流程）。

2. **Access Token 技术选型 = 自签 RS256 JWT**（原计划未定，现明确）：
   - payload：`sub`=auth_user_id、`username`、`user_identifier`、`roles`（数组）、`exp`=15分钟、`iat`、`jti`。
   - 签名密钥：新增配置项 `APP_JWT_ALGORITHM=RS256`、`APP_JWT_PRIVATE_KEY_PATH`、`APP_JWT_PUBLIC_KEY_PATH`（密钥对由运维生成，不进 Git；本地开发可用 HS256 + `APP_JWT_SECRET`）。
   - 中间件改造：现有 `main.py` 的 `_check_token`/`_lookup_roles` 同时支持两种 Bearer Token——① 现有 ApiKey（opaque + sha256 查库，机器/部署用）；② JWT（本地登录用户，无状态校验签名即可）。先尝试 JWT 解码，失败再回退 ApiKey 查库。

3. **不引入 Redis**：Access Token 无状态（JWT），Refresh Token 哈希存 `asset_auth_sessions` 表即可，一期不增加 Redis 依赖。

**验收**：空测试库 `alembic upgrade head` 成功；`downgrade` 在无业务会话数据时可执行；密码哈希和 Refresh Token 原文不落库；JWT 签名/校验单测通过。

### A2 后端认证服务与 API

新增 `backend/app/api/v1/auth.py`，认证业务逻辑放入 `backend/app/services/auth_service.py`，路由不直接写密码校验或数据库流程。

| 接口 | 行为 | 鉴权 |
|---|---|---|
| `POST /api/v1/auth/login` | 校验账号密码、锁定规则，签发短期 Access Token，设置 HttpOnly Refresh Cookie，写登录审计 | 公开 + 限流 |
| `POST /api/v1/auth/refresh` | 校验/轮换 Refresh Token，签发新 Access Token | Cookie |
| `POST /api/v1/auth/logout` | 撤销当前会话并清 Cookie | 已登录 |
| `GET /api/v1/auth/me` | 返回当前账号、绑定人员、角色和权限摘要 | 已登录 |
| `POST /api/v1/auth/change-password` | 校验旧密码或首次改密，撤销旧会话 | 已登录 |
| `POST /api/v1/auth/users` | 创建本地账号或绑定人员 | `platform_admin`/`identity_admin` |
| `PATCH /api/v1/auth/users/{id}` | 启停、重置密码、解锁、强制下次改密 | `platform_admin`/`identity_admin` |

实现要求：

1. 使用 Argon2id 库，不使用 MD5/SHA 直接哈希密码。
2. 登录失败返回统一错误，不区分“账号不存在”与“密码错误”。
3. 公开 `/api/v1/auth/login`、`/api/v1/auth/refresh` 必须加入限流与审计；其余 API 维持现有 Bearer Token/RBAC。
4. Access Token 不放 URL，不写日志；Refresh Token 只通过 `Secure`、`HttpOnly`、`SameSite=Lax/Strict` Cookie 返回。
5. 逐步将当前 API Key 定位为机器/部署/集成 Token；网页用户不再手工复制长期 API Token。
6. 生产环境强制 `APP_RBAC_REQUIRE_BOUND_TOKEN=true`，并把未映射的管理写接口改为默认拒绝。

**⚠️ 补强（2026-07-13 复核新增）——与现有体系共存、Cookie 安全**：

7. **与现有 ApiKey 中间件共存**（不要重写鉴权链）：
   - 现有 `main.py` 中间件已做：Bearer Token → `_check_token`（ApiKey 查库）→ `_lookup_roles`（角色校验）。
   - 改造方式：在 `_check_token` **之前**插入 JWT 解码尝试——若 Authorization 是合法 JWT，直接从 payload 取 `user_identifier`+`roles` 填入 `request.state`，跳过 ApiKey 查库；若不是 JWT 或解码失败，回退现有 ApiKey 流程。这样机器 Token 和人类登录两套凭证共用同一条中间件，无需平行鉴权。
   - 公开端点 `PUBLIC_EXACT` 增加 `/api/v1/auth/login`、`/api/v1/auth/refresh`；`PUBLIC_PREFIXES` 不变。

8. **HttpOnly Refresh Cookie 的 CORS/CSRF 配置**（不配会导致前端跨端口拿不到 Cookie）：
   - 后端 `settings.cors_origins` 必须包含前端实际 Origin（如 `http://10.10.8.83`），且 `allow_credentials=True`（已是）。
   - Cookie 属性：`HttpOnly; Secure（生产 HTTPS）; SameSite=Lax; Path=/api/v1/auth; Max-Age=8h`。开发环境（HTTP）`Secure=false`，由 `APP_ENV=dev` 控制。
   - CSRF 防护：因为 Access Token 在内存、Refresh Token 在 HttpOnly Cookie，CSRF 风险面仅限 `/auth/refresh` 和 `/auth/logout`。要求这两个端点校验 `Origin`/`Referer` 头在白名单内，或前端在 refresh 请求带自定义头 `X-Requested-With`（后端校验存在）。

9. **限流**：`/auth/login` 用现有 `slowapi` 限流（如 `5/minute/IP`），失败响应统一为 429 + 通用消息，不泄露"账号存在性"。

**验收**：正确密码登录 200；错误密码、禁用账号、锁定账号返回统一失败；登出和改密后旧 Refresh Token 失效；未授权访问返回 401/403；JWT 与 ApiKey 双凭证共存无冲突；跨端口 Cookie 正常携带；测试覆盖密码哈希、锁定、轮换、撤销、审计、RBAC、CSRF 头校验。

**⚠️ 补强（2026-07-13 复核新增）——复用已有脚本，不重复建设**：

5. **现有 `backend/scripts/create_admin_token.py` 已实现"创建 API Token 并绑定 user_identifier"**（用 `secrets.token_urlsafe(32)` + sha256 hash 存储，仅打印一次）。本流程**不要新建平行的管理员创建脚本**，而是：
