# 数据质量主动治理台账方案

## 0. 定稿结论

本方案把当前平台从“规则能发现问题”扩展为“问题能分派到科室和人员、整改、复测、关闭并留痕”的业务闭环。最终主链路为：

~~~text
质控清单 Control
  → 不可变观测 Observation
  → 整改台账 Issue
  → 科室/人员处理
  → 复测验证
  → 关闭、风险接受或复发
~~~

本次不替换现有探查引擎和元数据质量引擎。现有 ProbeFinding、QualityFinding 继续保留，作为检测来源和兼容证据；新建统一的质控清单、观测、问题台账和业务事件层。

本版已经收敛以下关键决策：

1. T1–T12 的编号是稳定的质控清单编码，不是永久问题编号。
2. 每次执行都写不可变观测；只有 FAIL 才按归并键创建或更新活动问题。
3. PASS 只形成绿色观测，不创建“已解决问题”占位行。
4. 问题编号表示一次治理事件，例如 DQI-202609-000001；问题关闭后再次失败，创建新的复发问题并关联上一条。
5. 科室和人员映射纳入本次范围，复用现有 Department、Person、AuthUser.user_identifier，不再用自由文本作为唯一责任信息。
6. 质量管理员可看全院；普通处理人只能处理本人或本人科室范围内的问题，数据范围必须由后端强制执行。
7. ERROR、BLOCKED、NO_DATA 不是 PASS，不能自动关闭业务问题；监测覆盖缺口单独作为 monitoring_gap 类型治理。
8. “已解决”必须经过复测与有权限人员确认；AI、检测任务和普通经办人不能自动接受风险或直接关闭。
9. 本期完成平台内闭环，不自动向微信、邮件、Jira 或厂商系统发消息。
10. 源业务库始终只读；生产平台迁移、种子 apply、部署、Git push/tag 仍是单独授权门禁。

## 1. 业务目标与验收边界

### 1.1 用户真正需要的能力

针对 HIS、LIS、PACS/影像、超声、手麻、电子病历等业务系统：

- 维护可版本化的质控清单；
- 定时或人工执行质控，保留每次结果和证据摘要；
- 失败后自动归并为整改问题，避免每个时间窗口重复开单；
- 指定主责科室、责任人和当前经办人；
- 记录整改计划、到期日、等待厂商原因和外部工单；
- 支持本人任务、科室任务、全院总览和逾期视图；
- 处理完成后发起复测，由有权限人员验证关闭；
- 关闭后再失败时识别复发；
- 导出可直接用于会议的问题清单；
- 全过程保留业务时间线和合规审计。

会议清单至少包含：

| 列 | 必须表达的内容 |
|---|---|
| 清单 | 稳定质控编码、名称、版本、启停状态 |
| 问题 | 问题编号、现象、最新指标、阈值、证据、是否复发 |
| 系统 | 主责系统、对端系统、标准 object_key |
| 责任 | 主责科室、责任人、经办人、是否等待厂商 |
| 整改情况 | 状态、措施、计划完成日、复测结论、风险接受信息 |

## 2. 已核对的当前系统事实

### 2.1 探查发现不是不可变观测

backend/app/models/probe.py 中的 ProbeFinding 当前表达“一个问题身份的最新状态”。backend/app/services/probe_service.py 会按归并键更新同一行；同窗口更新、resolved 后失败重开、false_positive 跳过都发生在同一 finding 上。

因此：

- ProbeFinding 不能直接承担历史观测表；
- 历史运行的汇总结果在 ProbeRun.metrics_summary JSON 中；
- 新模型必须增加不可变 Observation；
- 迁移旧数据时只能按当前可获得证据回填，并显式标注 latest_snapshot 或 summary_backfill，不能伪造历史精度。

### 2.2 原质量整改模型不能直接承接业务闭环

backend/app/models/quality.py 中的 QualityFinding 主要服务元数据规则。backend/app/api/v1/quality.py 已有运行、更新、分派和复核接口，但状态约束较松，分派和状态变化没有完整业务事件时间线。

处理原则：

- 保留 /asset/quality 和原 API；
- 页面显示名调整为“元数据质控”；
- 通过适配器把需要治理的 QualityFinding 转成统一 Observation/Issue；
- 不直接把旧模型扩成跨系统业务台账。

### 2.3 已有科室、人员和登录身份

- Department 和 Person 位于 backend/app/models/identity.py；
- AuthUser.user_identifier 可映射 Person.person_code；
- 现有身份管理接口受管理权限保护。

新模块只增加“责任选择”的最小只读接口，返回编码、名称和必要的在职/科室信息，不向普通质控用户开放完整身份管理能力。

### 2.4 已有统一对象标识

backend/app/services/object_identity.py 已提供 build_object_key。新模型必须使用 object_key，不再以 EXAM.EXAM_MASTER.DOCTOR_USER 这类自由文本作为唯一对象身份。展示名称可另存快照。

### 2.5 路由与兼容基线

- /quality-hub 当前重定向到 /probe-findings；
- /asset/quality 位于 asset 路由模块；
- /probe-findings 已投入使用；
- 现有 /relations/{id}/review、/dict-medical/* 等路径不得改变。

本次新增 /quality/issues 等页面，并把 /quality-hub 默认入口改到台账；旧路径必须继续可用。

### 2.6 迁移基线

2026-09-02 只读核对时 Alembic head 为 c1d2e3f4a5b6。执行 AI 必须在开始编码前重新读取当前 head，以实际值作为 down_revision，不得仅照抄本文件。

## 4. 目标领域模型

### 4.1 实体关系

~~~text
QualityControl 1 ── N ControlDetector
QualityControl 1 ── N QualityObservation
QualityControl 1 ── N QualityIssue
QualityIssue   1 ── N QualityObservation
QualityIssue   1 ── N QualityIssueEvent

ProbeFinding ──适配──> QualityObservation
QualityFinding ─适配─> QualityObservation
Manual input  ──适配──> QualityObservation / QualityIssue
~~~

### 4.2 编码语义

- control_code：稳定清单编号，例如 DQ-HIS-EXAM-001，可跨多次执行长期存在；
- control_version：规则口径版本，变更阈值、分母或 SQL 时递增；
- observation_id：一次执行在一个窗口、一个范围内的不可变结果；
- issue_code：一次治理事件编号，例如 DQI-202609-000001；
- scope_key：归并范围，例如系统级、表级、科室级或对象级；
- recurrence_of_issue_id：上一轮已关闭问题，后续再失败时建立复发链。

### 4.3 一条活动问题的唯一性

同一 control_id + scope_key 在非终态只能有一个活动问题。使用数据库部分唯一索引保证并发安全，服务层的“查后写”不能替代数据库约束。

终态为：

- resolved
- accepted_risk
- false_positive
- duplicate
- cancelled

终态后的新 FAIL 创建新 issue，并通过 recurrence_of_issue_id 指向上一条；同一活动问题持续 FAIL 只更新 latest 指标缓存、挂新观测并追加事件。

## 5. 数据模型

所有新表继续位于 asset schema，表名前缀为 asset_quality_。

### 5.1 asset_quality_controls：质控清单

必要字段：

| 字段 | 要求 |
|---|---|
| id | 主键 |
| control_code | 全局唯一、不可复用 |
| version | 正整数；与 code 组成业务版本 |
| title / description | 名称与口径 |
| lifecycle_status | draft / active / blocked / deprecated |
| dimension | completeness / validity / consistency / timeliness / uniqueness / referential / cross_system / monitoring |
| category | R-REF / R-CNT / R-KEY / R-XSYS / R-DOM / MANUAL |
| primary_system_code | 主责系统 |
| related_system_codes | JSON 数组，保存系统编码 |
| object_key | build_object_key 生成的标准键，可空但 active 自动规则原则上必填 |
| object_name_snapshot | 展示快照 |
| metric_name / metric_unit | 指标定义 |
| comparator / threshold_value | 阈值语义和数值 |
| no_data_policy | pass / fail / blocked，默认 blocked |
| default_severity | critical / high / medium / low / info |
| default_priority | P1 / P2 / P3 / P4 |
| default_dept_code / default_person_code | 默认责任 |
| schedule_expr / timezone | 可空 |
| verification_policy | manual / consecutive_pass，首版默认 manual |
| required_pass_count | consecutive_pass 时使用 |
| created_by / updated_by / timestamps | 审计字段 |

约束：

- control_code 唯一；
- version > 0；
- active 控制项至少有一个 active detector，手工清单除外；
- threshold/comparator 合法组合由 Schema 和服务双重校验；
- blocked 必须填写 blocked_reason。

### 5.2 asset_quality_control_detectors：检测来源绑定

一条质控清单允许绑定一个或多个检测来源，避免把来源写死在主表。

必要字段：

- id、control_id；
- detector_kind：probe_template / quality_rule / manual / external；
- detector_ref：如 T1 或 quality_rule_id 的稳定引用；
- detector_version；
- status：draft / active / blocked / disabled；
- scope_mapping JSON；
- result_mapping JSON；
- last_bound_at、blocked_reason；
- created_by、updated_by、timestamps。

唯一约束：control_id + detector_kind + detector_ref + detector_version。

### 5.3 asset_quality_observations：不可变观测

必要字段：

| 字段 | 要求 |
|---|---|
| id | 主键 |
| control_id / detector_id | 来源清单和检测器 |
| control_version | 当次执行的清单版本 |
| issue_id | 可空；归并后指向本次治理事件 |
| run_key | 执行幂等键 |
| scope_key | 归并范围 |
| window_start / window_end | 统计窗口 |
| observed_at | 观测时间 |
| result_status | pass / fail / error / blocked / skipped / no_data |
| metric_value / metric_unit | 实测 |
| threshold_snapshot | JSON，保存当次阈值与比较符 |
| control_definition_snapshot | JSON，保存当次指标、口径、对象和 no_data_policy 的脱敏定义快照 |
| numerator / denominator | 可空 |
| source_kind / source_record_ref | probe_finding / probe_run / quality_finding / manual / external |
| evidence_digest | 脱敏证据摘要 |
| evidence_ref | 受控证据引用，不存明细样本 |
| historical_precision | exact / latest_snapshot / summary_backfill |
| error_code / error_message_sanitized | 失败信息，必须脱敏 |
| created_at / created_by | 只增不改 |

幂等唯一键至少覆盖 control_id + detector_id + run_key + scope_key。control_code 在主表唯一，规则定义发生实质变化时在同一 Control 上递增 version；每条 Observation 固化 control_version 和 definition snapshot，从而保留历史口径。观测记录禁止业务 UPDATE/DELETE；需要纠错时追加 correction 观测或事件。

### 5.4 asset_quality_issues：整改台账

必要字段：

| 字段 | 要求 |
|---|---|
| id / issue_code | 主键和全局唯一问题编号 |
| control_id | 自动规则必填；纯手工问题可空 |
| issue_type | data_defect / monitoring_gap / manual |
| title / description | 问题描述 |
| primary_system_code / related_system_codes | 系统 |
| object_key / object_name_snapshot | 对象 |
| scope_key | 活动问题归并范围 |
| severity / priority | 严重度和处理优先级分离 |
| status | 见生命周期 |
| responsible_dept_code | 主责科室编码 |
| responsible_person_code | 责任人编码 |
| assignee_user_identifier | 当前经办登录标识 |
| dept/person/assignee_name_snapshot | 会议展示快照，不代替编码 |
| action_plan | 整改措施 |
| due_at | 计划完成日 |
| wait_kind / external_ticket_ref | 等厂商等外部依赖 |
| latest_observation_id | 最近观测 |
| latest_metric_value / latest_result_status | 列表缓存 |
| opened_control_version | 本次问题首次打开时的规则版本 |
| first_seen_at / last_seen_at | 首次与最近发现 |
| recurrence_of_issue_id / recurrence_no | 复发链 |
| duplicate_of_issue_id | 重复问题 |
| resolution_summary / resolved_at / resolved_by | 关闭信息 |
| risk_reason / risk_approver / risk_review_at | 风险接受 |
| false_positive_reason / suppressed_until | 误报仅按版本/范围限时抑制 |
| suppressed_control_version | 误报抑制所针对的规则版本 |
| lock_version | 乐观并发控制 |
| created_by / updated_by / timestamps / archived_at | 审计与软归档 |

关键约束：

- issue_code 唯一，使用数据库序列或等价的并发安全生成器，禁止用 MAX(id)+1；
- 非终态 control_id + scope_key 部分唯一；
- waiting_external 必须有 wait_kind 和说明；
- waiting_verify 必须有 action_plan；
- resolved 必须有验证通过的 observation 或人工验证事件；
- accepted_risk 必须有原因、批准人和复审日期；
- false_positive 必须有原因和 suppressed_control_version，suppressed_until 不得形成永久无期限跳过；
- due_at 早于当前时间且非终态时由查询计算 overdue，不额外维护易漂移布尔值；
- lock_version 每次修改递增，冲突返回 409。

### 5.5 asset_quality_issue_events：业务时间线

不可变事件类型：

- created
- acknowledged
- assigned
- status_changed
- action_plan_updated
- comment_added
- observation_linked
- verification_requested
- verification_passed
- verification_failed
- reopened
- resolved
- risk_accepted
- suppression_set
- duplicate_marked

字段至少包括 issue_id、event_type、from_status、to_status、before_json、after_json、reason、observation_id、actor_user_identifier、actor_name_snapshot、occurred_at、correlation_id。

## 6. 生命周期与自动化规则

### 6.1 状态

| 状态 | 含义 |
|---|---|
| new | 新建待确认 |
| acknowledged | 已确认问题有效 |
| assigned | 已明确科室/人员 |
| in_progress | 整改中 |
| waiting_external | 等厂商、上游或外部条件 |
| waiting_verify | 已声称完成，待复测 |
| resolved | 复测通过并关闭 |
| accepted_risk | 经授权接受风险，设复审日期 |
| false_positive | 本版本/范围误报，限时抑制 |
| duplicate | 合并到另一问题 |
| cancelled | 登记错误或对象退役 |

### 6.2 允许流转

| 从 | 可到 |
|---|---|
| new | acknowledged / false_positive / duplicate / cancelled |
| acknowledged | assigned / in_progress / waiting_external / accepted_risk |
| assigned | in_progress / waiting_external / waiting_verify |
| in_progress | waiting_external / waiting_verify |
| waiting_external | in_progress / waiting_verify |
| waiting_verify | in_progress / resolved |
| resolved | acknowledged，仅复发/管理员重开 |
| accepted_risk | acknowledged，到复审期或风险条件变化 |
| false_positive | acknowledged，抑制到期或规则版本变化 |

任何非法流转返回 409。不能通过通用 PATCH 绕过专用命令。

### 6.3 观测驱动

| 新观测 | 没有活动问题 | 有活动问题 |
|---|---|---|
| FAIL | 创建 new 问题并关联 | 更新 latest、关联观测、追加 observation_linked；不重复建单 |
| PASS | 只保留绿色观测 | 若 waiting_verify，生成待验证材料；默认不自动 resolved |
| ERROR | 不当作业务通过；必要时建 monitoring_gap | 记录执行失败，不关闭原问题 |
| BLOCKED | 建或更新 monitoring_gap | 记录阻塞原因，不关闭原问题 |
| SKIPPED | 记录跳过依据 | 不改变业务状态 |
| NO_DATA | 按 no_data_policy，默认 blocked | 默认不关闭 |

自动化服务必须事务化、幂等，并在并发冲突时依赖部分唯一索引收敛。

### 6.4 复发

- 活动问题持续失败：同一问题追加观测；
- resolved 后相同 control + scope 再失败：新建问题，recurrence_of 指向旧问题，recurrence_no + 1；
- accepted_risk 在有效复审期内失败：继续挂观测但不自动重开；到期后进入待复审；
- false_positive 的抑制只作用于指定 control_version + scope，版本变化或 suppressed_until 到期后恢复判定。
