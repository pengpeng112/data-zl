## 本轮已修复

| 问题 | 修复结果 |
|---|---|
| 真实capture把任意源行写成K1/V1两列 | 按冻结投影完整映射；列数不一致拒绝，禁止静默截断 |
| 日窗按UTC00:00计算 | 改为院区时区，默认Asia/Shanghai；保留左闭右开 |
| 金额、日期和二进制在暂存时变成字符串 | 增加带版本的无损编码，兼容旧普通JSON行；未知类型拒绝 |
| 暂存行数只相信元数据 | 按实际载荷核行数、字节和哈希；verify/apply/reconcile前再次检查，防完整标记写出后文件损坏 |
| DataX只有dirty=0也可成功 | 必须同时取得读数、写数和dirty，读写数相等、dirty=0才完整 |
| Python分页SQL可能先被驱动限量截断 | 查询限量与请求行数及哨兵一致，不把前5000行冒充完整窗口 |
| verify调用缺少rules，且汇总字段不一致 | 正确传质量规则，按稳定键分组，补必填、类型和已声明字节长度校验，正确统计valid_rows |
| JSON里的批准字符串被当成生产批准，围栏被关掉 | 真实装载必须注入生产ApplyPort、平台核验、耐久版本账及本表写租约；不再自建模拟批准绕过 |
| 内存仓储被允许装配成真实运行 | 真实build拒绝内存状态库 |
| 目标预览锁不释放，又开另一条写连接 | 预览读在finally回滚并关闭，写入前释放锁；目标执行器也处理连接释放 |
| 预览后目标变了仍静默跳过并签成功回执 | 锁内核目标键和预览内容；变化、重复/漏计划键、冲突动作或DML行数不符则回滚 |
| 已回滚结果仍可能被标为APPLIED | 未明确提交不得标成功；COMMIT_UNKNOWN仍单独冻结 |
| 同一ID的版本证据可能跨表串账 | 生产版本账按实例、Owner和表隔离 |
| 批次可被另一个目标/写列绑定使用 | 对比任务、原批次的目标三元组、完整投影和稳定键；配置/定义变更后旧暂存须重新核验 |
| PG状态每次从PLANNED/NOT_SUBMITTED开始验证 | 从持久化当前状态推进，正常链路可继续、非法回退被拒 |
| 日报把历史累计数显示成当日数量、隔离仍显示成功 | 按指定业务日计数；隔离与待父批次进入未完成项；PG批次列表改批量读取 |
| 多源长任务只续第一条读取租约 | 续全部读取与写入租约，分别保留各自TTL；修关键字context调用 |
| 配置中的投影、装载策略、版本和部分预算被丢弃 | 完整反序列化；不因此把候选自动变成READY |
| 调度异常只有返回值，没有待补/告警记录 | 按冻结日窗记缺口并写脱敏、不可变告警队列；同一未恢复故障复用事件；队列异常显式非成功，其他表继续 |
| 告警级别和时间容易违反公共接口 | 使用接口允许的yellow；首次发生时间为带时区的实际时刻，后续重试不改原字节 |
| 报告可能回显控制库连接串或患者键/内容 | 日报不打印URL，控制库支持受控环境变量；对账示例只返回差异列名 |
| 传relay URL便误以为外发已接线 | 未接sender明确拒绝；本轮只写本地outbox，不发真实消息 |
| 月替换模式在SQL执行器里实际没有删除 | 当前只支持MERGE，REPLACE_MONTH明确拒绝，避免把未实现功能报完成 |

## 维护、管理和扩展的判断

**维护方面**：批次、尝试、缺口、租约、回执和告警的拆分方向可用，避免靠日志猜成功。修复后更适合作为长期管道基础。但真实恢复执行、成功回读后缺口关闭、连续完成水位和告警恢复通知仍需在装配链中逐项验收，不能只返回next_action。

**管理方面**：当前是CLI管理，没有专门的T+1页面。已有list、validate、daily-report、resume、retry等入口；新增doctor如实报告缺线。初期可用日报和值守操作，后续若建页面，应调用同一个服务和审批链，不复制另一套调度或直接写数据库。磁盘容量、保留周期、权限、备份和跨版本恢复要在部署时落配置。

**扩展方面**：逐表TaskSpec和两类读取适配器可以复用，不需要每张表重写脚本。不过候选配置不是生效配置；源组相同不代表视图相同，源连接必须绑定具体任务/投影。DataX-only、LIS双源和父子关系要真实接入，不得默认用单源Python兜底。当前通用capture会拒绝尚未接专用路由的DataX/双源任务。

## 后续沿原计划完成，分两批即可

### 第一批：补齐运行链并做隔离验收，不动生产

1. 将首组四表候选转换为完整TaskSpec：源视图与投影、目标列类型、窗口、稳定键、指纹、逐表预算及凭据引用都要可追溯。配置文件的路径、版本和哈希显式冻结；保留候选停用和动作级绑定，不通过手工置READY解决。
2. 装配受控源工厂、目标连接工厂、平台生产ApplyPort和耐久版本账。目标连接需支持begin/read/rollback/close；Oracle DATE绑定用医院业务时区，不经字符串或UTC误转换。复用连接器和已存在白名单执行框架，不能新建临时直连写脚本。
3. 把Python与DataX的叶子窗口、暂存、质量和目标事务接成同一流程。超过行数/字节预算继续拆窗；同一秒仍超限时用已核唯一游标；不要整月进内存或一个事务。DataX插件、暂存表、导出回收及双源范围都要实测。
4. 补齐改写/撤销策略。无可信源版本的快照差异要明确CAS与单写者规则，不能把采集时间冒充源修改版本；父存在性、坏组隔离和合法组继续都要实际留账。
5. 将恢复建议落实为执行：失败窗口自动排队、成功回读后只关闭对应缺口，历史空洞未闭合不能推进连续完成水位；回看、重扫有自己的覆盖账。月度替换尚未实现，必须先开发和隔离验证，不按计划JSON直接执行DELETE。

验收要从正式入口跑 `capture→verify→apply→reconcile→日报/恢复`，同时覆盖迟到、修改、缺父、断连、提交不明和并发变化。只跑helper或dry-run不算这批完成。Oracle方言尚无隔离环境证据，必须单列。
