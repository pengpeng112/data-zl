# 先把容易卡住的地方处理好

两阶段、10批的安排可以保留，但原计划还缺几处明确的实施约束。尤其是“省端未就绪仍能做院内入库”“一张表失败其他表继续”，当前代码并没有完整做到。执行者要先修下列公共问题，再启用首组正式任务；不能只把命令补上就开始跑全年。

## 三、2026补齐与日常运行再补六条约束

1. **H在首组正式启用时才最终冻结。** A01只填候选，不能因开发延后每天重设已经生效的H。后续组在G日启用时，补 `[2026-01-01,H)` 的历史，还要建立 `[H,G)` 的日窗欠账，G以后接每日T+1。日报分别展示历史覆盖、H起日常连续游标和省端游标，不能以历史未补完挡住日常调度，也不能把日常完成当全年补齐。
2. **表依赖不能替代逐键依赖。** 父任务排在前面不代表父已提交。启动子发布前查真实父键及回执；目标已有父不用等同日父任务重新运行。对子数据的父来源按规范实际关系确认，未出院业务不能一律依赖尚未产生的首页；历史父未入库时，优先补必要真实父键。合法子组继续，缺父组等待并在父成功后自动唤醒，避免全表死等。
3. **旧源数据包、旧规则和变动业务日期要能重核。** 业务时间从某月移到另一月时，仅重扫新月可能留旧月多余行；保持稳定键索引、旧/新时间及路由/规则版本，触发相关范围重核，撤回按批准协议处理。日后人工改视图/字典只重核影响的列和窗口；已有staging定义过期就不可发布。不因代码升级粗暴重跑全年，也不把未知源版本伪装成捕获时间版本。
4. **历史任务要能让位，失败重试不能挤死月巡。** 首组默认每次历史可让出执行片5分钟，到分块/事务边界落盘后让出；单SQL超时仍按画像取消，正在提交的事务不能被优先级强杀。这个时长是初始配置，实测后调整。日常积压优先，另给历史/月巡保留经预算验证的最低日配额；达不到就告警覆盖周期降级，不能无限饿死月巡。容量按实测p95、每日增量与夜间可用时长测算，留至少候选30%余量再签内部08:00目标。
5. **磁盘、连接池和日志要有限。** A01测当前可用空间、暂存单行/大CLOB字节、2026总量估算；冻结stage/备份/outbox/日志的配额及保留期。空间低水位禁止新大捕获，保留已提交凭据和审计，不能清掉待发布/待回读清单救急。按operation_id组织数据、备份和回执，对象都能从容器重建；控制查询、目标发布和告警worker分别限制连接占用，避免慢源拖住心跳。技术凭据的增长不得沿用旧单月试点“年不到1万条”的估算，按实际叶窗×批次×重试推算。
6. **退出与恢复要有具体时限。** worker收到停止信号：停止领新任务，在合法边界持久化→释放匹配token的资源→退出；超时或崩溃由租约及目标凭据恢复。每项等待记录原因、负责人/角色、首次时间、下次尝试、最大自动尝试次数及升级时点。默认短暂断连每窗本轮最多3次指数退避并带抖动，随后转耐久待补，下一批准时段再排；认证失败不走这套重试。不得busy-loop，不得把长期待父/待视图记成完成或永久跳过。

## 四、第一阶段怎么安排更稳

保持A01—A05编号，不加新大批次。按下面的交付依赖执行，能做的不要互相等待：

| 节点 | 应先交付 | 正式卡住的范围 |
|---|---|---|
| A01第一片 | 首组候选、环境/权限/订阅缺项、在跑写者快照、源码卡点清单 | 原则上不等外部回复，继续A02—A04可独立部分 |
| A02—A04开发 | 优先修K01—K06、固定任务身份和结果契约；接线到PG、DataX暂存和白名单执行器；再做依赖/资源/恢复实测 | 缺特定数据库/源权限只阻相应真实验证 |
| A05a只读/隔离闭环 | 源→暂存→质量→隔离目标提交/回读→告警，含故障恢复 | 不能用此结果代替生产写批准 |
