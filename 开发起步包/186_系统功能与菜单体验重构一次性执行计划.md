## 0. 结论、目标与验收底线

系统已具备较完整的资产目录、关系图谱、查询与指标、质量台账、人员同步、字典维护、运维审计能力。当前主要问题是功能按建设批次累加：用户需要知道内部模块归属，才能找到做事入口；同一任务链分散在多个菜单；展示、分析、草稿、审批、真实执行的边界未在所有页面形成一致体验。

新增重点：夜间人员同步必须同时检查SYS_EMPLOYEE人员有效性和SYS_USER账号启停，任一停用则两个目标都停用，两者启用才允许两个目标启用；详见§4.6与I2/I3。

本轮不重写平台、不更换 Vue3/Element Plus/Pinia/Vite，不建设另一套查询引擎、权限系统或质控状态机。采用“七个业务分区 + 工作台 + 原路径兼容 + 跨页上下文 + 现有闭环补齐”的方案。

完成后用户应能：

1. 登录后看到自己可处理的任务、常用入口和最近访问，明确下一步做什么。
2. 从业务系统找到表，查看结构、关系、值域及关联查询，并带着正确物理来源继续分析。
3. 从探查发现进入质量台账，定位责任、处理、复测与证据，分清发现、观测和问题单。
4. 在取数分区区分 AI 辅助编写、查询资产、指标、产品和运行记录，不误入运维 SQL 执行。
5. 通过查询结果找到实际版本和执行证据，再发起准确性反馈；没有真实执行时不显示伪运行记录。
6. 在人员/字典同步异常页找到对应批次及原因；夜跑按双来源规则向JHEMR、无纸化同步启停，真实写入仍受现有审批与白名单约束。
7. 旧链接可访问，低权限角色不出现越权入口、缓存泄漏或未授权后台请求。

验收底线：不是“改了菜单名”即完成。必须交付菜单迁移映射、实际交互改动、权限回归、关键链路测试、浏览器截图和逐任务证据。未获批准的生产步骤单独记待批准，不计开发失败，也不能宣称已上线。

### 4.6 夜间HIS双来源启停规则与执行契约（用户新增，P0）

#### 4.6.1 已确认规则、原实现与未确认物理结构

> 以下“未核实”描述保留初版编制背景；当前结构证据采用 §12.0/§12.4 与 `output_r186/sys_user_evidence.json`，不重复从未知 Owner 开始探查。执行时复核证据时效与作用范围，仍禁止猜测新字段、值域或新增账号范围。

用户本次明确：`SYS_USER.STATUS = 1`是停用，`= 0`是启用；SYS_USER与SYS_EMPLOYEE只要其中一个停用，就将该人员的JHEMR和无纸化账号都停用；两者都启用，两个目标才允许启用。无纸化在当前代码中对应CDMS适配器，实施时核对部署登记对象一致。

当前代码事实（不是本次活库值域核验）：`his_identity_sync._employee_employment_status`优先处理`ISDELETED`；现helper把None、空串、0、N、False/false视为未删除，其他值视为删除；否则`VALIDSTATE=1`为active、`=0`为inactive。SYS_USER必须独立归一化，禁止复用这个方向相反的`_normalize_status`。保留已有删除兼容值的回归，新发现未定义标记先核实，不用本次改动悄悄重写全部人员有效性。COMM.STAFF_DICT的历史回退规则不能覆盖本次明确的SYS_EMPLOYEE与SYS_USER双来源门禁。

本次经sjzc只读查询HIS_SOURCE及登记别名HIS的平台表目录，均未命中SYS_USER；离线检索也未取得该表完整结构。这只能说明**当前检索证据不足**，不能认定源库没有此表。SYS_USER的Owner、员工关联键、唯一性/一人多账号、逻辑删除字段及可靠更新时间均待核实。现有SYS_EMPLOYEE取`EMPLCODE`作为人员键，不能据表名猜SYS_USER在FXHIS，不能据字段相似猜USERCODE/USERID可关联。

#### 4.6.2 状态真值表与判定对象

先在同一物理系统、已验证人员映射下分别生成`employee_state`和`user_state`，枚举为enabled/disabled/unknown，再计算`desired_account_state`。数值及其字符串形式可标准化，NULL、空白、未知码不得经布尔转换当启用。

| SYS_EMPLOYEE归一化 | SYS_USER.STATUS归一化 | 两目标期望状态 | 判定理由 |
|---|---|---|---|
| enabled（VALIDSTATE=1且删除标志有效） | enabled（0） | enabled | 两处均明确启用 |
| enabled | disabled（1） | disabled | HIS账号停用 |
| disabled（VALIDSTATE=0或已删除） | enabled | disabled | HIS人员停用/删除 |
| disabled | disabled | disabled | 两处均停用 |
| disabled | unknown | disabled | 已可靠映射的人员停用优先；未知不抵消明确停用 |
| unknown | disabled | disabled | 已可靠映射的账号停用优先；未知不抵消明确停用 |
| enabled | unknown | unknown | 不满足两处都启用，不新增启用或猜测停用 |
| unknown | enabled | unknown | 同上 |
| unknown | unknown | unknown | 两处证据不足，不启用、不猜测停用 |

表中disabled证据必须属于当前人员、来自本轮成功完整读取的对应记录；整批读取失败、分页截断或过期缓存不能套用此表制造确定性。另一来源暂不可用时，已有本轮可信disabled可以形成停用候选，但启用候选一律阻断；批量是否可执行仍须通过原来源健康检查、审批与熔断，不豁免全局门禁。

关键实现约束：

1. **人员在职状态与登录状态分开。** 保留`IdentityPerson.employment_status`既有语义；SYS_USER停用不等于员工离职，不因此终止劳动/科室/岗位归属。增加独立的有效账号状态与原因，夜跑账号动作消费此状态。
2. **身份不确定就隔离该对象。** 无人员映射、跨院区键冲突、一个账号映射多名员工、相互冲突的员工主记录均记blocked；不能取第一行或按姓名匹配。一人多SYS_USER账号属于尚未证实的情形，本计划建议先验证哪些账号属于该人员的本次医院业务登录范围，再对范围内账号采用“任一明确停用则disabled，全部明确启用才enabled，否则unknown”；这是一对多的保守实施建议，不冒充用户已明确指定账户范围。不能将服务账号、另一院区或历史回收账号默认计入。范围未证实时，该人员保持blocked并给出候选关系供核实，不按“有一个启用”放行。
3. **缺失不同于停用。** SYS_USER缺失、SYS_EMPLOYEE只在STAFF_DICT回退中出现、删除字段含义不明时，不视作两处启用；明确已删除则按已核实删除语义停用。缺失不创建占位HIS账号，不改变HIS数据。
4. **期望状态与执行许可分开。** 输出desired_state、execution_allowed、blocked_reason。双启用决定业务期望，但手工/安全锁定、受保护账号、既有医院/角色/人员分类边界、未批准动作不能因此被绕过；不允许把“受保护未修改”报告为“两个系统已同步成功”。
5. **保持既有人员范围。** 对已由平台管理的目标账号评估启停，不因人员离职、科室变化或不再满足新建账号条件而漏停。新增建号仍受原人员类别、科室、日期、冲突与审批规则约束；未建目标账号的disabled只记target_missing，无需创建后再停用。历史缺失建号资格的enabled对象不能走状态恢复分支偷建账号。

#### 4.6.3 变化发现、持久证据与补偿

夜跑实际链为`scheduler → run_nightly_pipeline(refresh_source=True) → his_identity_sync.sync_his_identity → 候选筛选 → executor_bridge → 目标adapter`。`identity_source_collector.collect_his_persons`是另一个入口，必须复用同一归一化规则，但单改它不会修复夜跑。

现有`_modified_employee_times`只看SYS_EMPLOYEE.MODIFIEDTIME，因此本轮默认采用**对既有受管账号集合及原新增合格候选集合的分批状态对账**，发现SYS_USER-only变化和上线前积压差异。不扩大为全源表无界扫描。人员集合分页、按已核实关联键绑定查询、设置每批上限/总量上限/超时；上限与当前规模/既有源端预算结合，在R0记录实际值，不凭空提高。单批达到限制时明确继续页或标不完整，不能把截断结果当完整快照。若关联键无可用索引或查询计划不可控，先给出限量验证方案与阻塞，不在源库建索引或强行全扫。

只有在SYS_USER时间戳及删除事件覆盖已证实可靠后，才可优化为两个来源独立水位+重叠窗口+周期性受控对账；不能只复用EMPLOYEE水位。默认分批对账不依赖该待确认字段，元数据不全不妨碍先实现变化检测接口及纯逻辑测试。

最小持久契约（字段名由现有模型映射决定，执行报告提供落点）：

| 对象 | 必须可追溯内容 |
|---|---|
| 来源观察 | person稳定键、物理系统/Owner/对象、脱敏源键、两个来源归一化状态及原因、captured_at、完整性/错误、rule_version、evidence_fingerprint；不保存账号秘密或姓名 |
| 状态判定 | desired_state、decision_reason、资格/保护检查、关联观察ID；不能只存employment_status |
| 目标尝试 | run_id、person稳定引用、target_system、target账户稳定引用/院区（保留既有HMAC，不新增日志明文账号）、action、before_state、desired_state、实际after_state、attempt/status/reason、审批及执行器引用 |
| 恢复依据 | 哪次经审批动作实际将哪个目标由启用变停用、提交与回读证据；仅观察到“已停用”不构成平台锁定所有权 |
| 对账与重试 | 两个目标各自applied状态/指纹、pending_reconcile/retry引用、最后错误；来源已观察与目标已应用分别记录 |

原状态枚举能表达则复用并加reason；不能表达时扩展DTO/模型/前端枚举，不用随意字符串破坏状态机。恢复证据涉及新字段时手写可往返Alembic迁移，旧记录空值按unknown/legacy_unverified处理，不回填“已双源核实”。

幂等以“目标账户+当前期望状态+来源变化代次/持久转换序号+规则版本”识别一次动作。evidence_fingerprint用于判断内容相同，不可单独作为永久唯一键，否则enabled→disabled→enabled→disabled的第二次停用会被当旧动作丢弃。相同待处理转换重试复用动作身份，成功目标不重复写；失败目标可恢复。源观察水位推进不等于双目标完成，未完成目标不得因推进水位或刷新指纹从队列消失。

#### 4.6.4 双目标写入、恢复与竞态

| 目标 | 已读代码编码 | 本轮需要补齐 |
|---|---|---|
| JHEMR | ACCOUNT_STATUS_ACTIVE=0；ACCOUNT_STATUS_LOCKED=8 | 现lock_account及execute_jhemr_lock复用；增加受控8→0恢复路径，不覆盖其他状态 |
| 无纸化CDMS | T_MSS_EMP_DICT.FUSERSTATE='0'启用、'1'停用 | 将既有lock_user接入受控桥接并补提交前回读；增加受控1→0恢复路径 |

以上目标编码为当前代码证据，发布前须对照目标元数据和受控样本核实，不将SYS_USER的0/1原样传给JHEMR。明确院区+账号唯一键；状态SQL使用稳定键、期望旧值与绑定参数，影响行数必须符合单对象预期。0行需回读区分已达标、对象消失、并发变化；多行/错行或回读不符回滚该目标事务。

1. 两个目标分别事务执行、提交前回读，不跨两个数据库假装原子提交。CDMS当前lock_user直接commit的实现须补齐本地事务内验证；桥接不能在已提交后才把失败回读当可回滚。
2. 停用和恢复都经`asset_action_executors`白名单与既有审批/运行开关，核对身份同步总开关、阶段批准、受保护账号、CDMS FTYPE限制等。不能从orchestrator直接调用裸adapter绕过桥接，也不能以本计划作为生产批准。
3. 重新启用只针对**有可靠证据被本规则实际停用且锁定原因仍归本规则**的账号；状态已enabled则只核对无需写入。已被人工/安全策略锁定、锁定原因未知或旧停用无证据的账号标protected/blocked，列待核实或逐例批准，不自动解锁。若目标没有锁原因/版本字段，单凭当前值8/1及历史平台停用记录不能证明期间无人追加安全锁；必须利用可用目标审计/版本证明仍归本规则，否则保持待核实。此限制必须在验收中显式呈现，不能冒称所有双启用人员已恢复。
4. 恢复状态不重设密码，不重建角色组，不重置账号，不顺带改医院/科室/签名。修复create/align、登录/签名同步、重试等旁路：effective_state=disabled/unknown不得通过其他流程隐式启用；显示在职但账号停用的人仍保留人员资料。
5. 每次写入前重新确认来源证据可用、审批范围和目标保护状态；同人员并行运行/人工操作通过既有运行锁、目标条件更新和状态版本防止覆盖。源端与两个目标无法形成分布式强一致事务：如果写前复查发现变化，取消陈旧动作并重新计划；提交后按当前证据再对账，记录观察时间与残余窗口，不承诺跨库瞬时一致。
6. 单目标失败不撤销另一目标已成功的安全操作，也不把整个人员标success。例如JHEMR停用成功、CDMS失败，保留JHEMR已停用并记录CDMS待补偿；恢复启用的部分失败同样明确partial。恢复重试前重读最新HIS状态，若已转停用，取消陈旧enable并生成当前disable动作，不盲目重放旧SQL。
7. 源端/平台审计失败、目标commit结果不确定时保留pending_reconcile，先受控回读再决定重试；禁止为补平台记录重复源写。回读确认当前停用只能证明当前状态，不能凭此伪造停用原因或自动恢复权限。
8. 沿用既有变更比例/停用数量/健康门禁，不自动提高阈值。首次补齐SYS_USER可能形成历史积压，先dry-run给出唯一人员数、每目标动作数和失败/保护数；超阈值标待复核，不以反复小批绕过总阈值。批准分批须明示总范围与每批范围。
9. 修正保护对象识别：当前候选筛选将所有IdentityProtectedAccount.account_id不分target_system直接与person_code比较，而登记唯一键为(target_system, account_id)。必须经真实目标映射按二元键匹配，不假设目标账号ID恒等于工号。为保留既有人员级保护，本轮默认任一实际关联目标受保护则该人员整组不自动变更，明确展示哪个目标触发保护；不能把其他人员同名目标ID误判进来。若以后要求只跳过受保护目标、继续另一目标，这是缩小原保护范围的行为扩展，单列决定后实施，不悄悄包含在本轮。执行前再次检查保护，不仅在选人时检查。
10. **保护映射必须可落地。** 现有ManagedRelation.target_key及composite_business_key实际保存HMAC fingerprint，不是可反解的目标账号。先从有权读取的目标账号快照/绑定键限量回读取得账号及院区，在服务端受控内存中验证“人员→目标实际唯一键→既有HMAC关系”与“保护表target_system+account_id”一致。按既有规范化和HMAC规则计算候选并核对，不尝试反解指纹，也不把target_key当明文账号查询。只持久保存关系引用、指纹/规范化版本、映射验证时间及证据引用；不得为省事将目标明文账号写进新普通DTO、日志、报告或不受控raw_data。旧关系无法唯一重建或保护表account_id语义不明时，标protection_mapping_unknown并禁止该对象停用/恢复，单列待核实；不得以“查不到保护行”等同无保护。

### I3 — 双系统启停执行、补偿与夜跑证据（P0，依赖I2；展示接I1）

**目标：**将同一人员的正确期望状态经现有受控执行链作用于两个目标；任何半成功、未知或保护都可追踪、可恢复，不误启用账号。

**步骤：**
1. 建立停用与恢复的白名单动作定义/桥接矩阵：JHEMR disable、CDMS disable、JHEMR enable、CDMS enable。复用已有JHEMR锁定和CDMS适配器能力，增加缺少的桥接/恢复方法与只改状态的SQL；本地代码支持不等于生产动作已获批准。

3. 对两个适配器补条件更新、影响行数、提交前回读、异常回滚、already_desired幂等；CDMS改掉当前先commit后返回且无状态回读的路径。JHEMR与CDMS各自事务，不能用一个“总体成功”代替独立证据。
4. 编排加入双目标停用及双目标恢复分支。已有符合条件的账号enabled只确认。目标缺失时严格分支：desired=disabled只记target_missing且零create；desired=unknown只记blocked/待核实；只有desired=enabled、双源明确启用并满足原新增资格才可进入独立建号评估。已受管目标的恢复函数只做enable，目标消失就返回缺失，不自动回退到create。保护/人工锁/归因不足显示需核实；重试前复查源状态及保护映射，不复用陈旧enable。
5. 实现持久重试/待对账与跨系统部分成功，支持进程重启、commit结果不明、源写成功但平台登记失败。仅失败/未确定目标进入恢复处理；最新状态变化时取消旧转换并重新规划，重复请求不重复写源库。

8. 准备生产前dry-run模板、旧数据兼容策略、试点清单及回退方案，满足§8.3后交用户审阅。夜间实际批量执行、目标写入、部署和cron调整仍按本次具体授权，未执行就保留待批准/待验证。

**验收：**T36—T46通过并复跑相关旧身份回归；两目标停用、受控恢复、人工锁保护、部分失败/重启补偿与写门禁均有断言。只测纯逻辑判断而未测真实编排入口不算完成；adapter fake通过不等于源库方言/事务已验证。交付按代码、隔离平台集成、目标模拟器、批准后真实试点分层报告。

### 12.2 部署规范缺口（P0 级流程约束，随发布批准一并执行）

- **顺序硬依赖**：按 §13.6，备份/暂停旧provider后，用候选迁移器升级到明确target_revision，再切新后端、回读API、切前端；c6d7e8f9a0b1是首轮revision，不是本次新增迁移后固定head。前端先切不是推荐方案。
- **当前生产基线**：v1.9只读证据为旧镜像r181/r175、head=d5e6f7a8b9c0、执行器0行、旧host cron运行、8.83 NTP未同步；执行前重新只读核对。它们是待整改差异，按S3/S4取得整改后证据；部署及两disable登记/目标停用已批准，恢复未批准。旧夜跑success不是186验收。

## 13. v1.10 复核修订：不修改两目标主机时间的方案与一次性执行合同

### 13.1 三个时间问题的处理决定与权限边界

| 问题 | 本轮落实的方法 | 不能据此推出的结论 |
|---|---|---|
| 8.83 NTP 未同步 | 纳入发布维护窗口，恢复可信时间源和 chrony 校时；先采配置/偏差证据，优先平滑校正。用户已同意该主机可校时；本次计划修订不立即修改服务器 | 手动设置一次时间不等于 NTP 健康；不能用本机 Windows/AI 日期作为权威源 |
| JHEMR 返回 PRC、驱动解析不清 | 在实际部署版本、实际会话、实际字段类型上建立只读时间序列化合同；以服务端明确格式文本/epoch 和数值 offset 交叉核对，绕开客户端只认时区名的问题 | 不能仅把字符串 PRC 替换为 Asia/Shanghai 或给所有 naive 值补 +08:00；当前 offset 不证明所有历史值含义 |

原本要求 DBA 手工提供两目标主机 NTP 的条件，改为可由执行 AI 通过既有受控只读通道取得的数据库时间合同和偏差证据；这是**时间证据获取方式调整**，不放宽锁归因，不授权恢复。无法取得目标 OS 信息本身不阻塞 disable-only。若未来没有可证明锁所有权的目标审计/版本能力，自动 enable 仍不可放行，即便三台已完全对时。

8.83 校时执行约束：

1. 只核查既有 chrony 配置、选源、网络可达性与服务状态，优先医院已登记的内网可信时间源；不扫描网段、不随意配置公共 NTP。若没有可用且可信的现有源，仅请求时间源地址/来源确认，其他开发、部署准备和获准 disable-only 继续。
2. 备份配置并记录 UTC、时区、`chronyc tracking/sources`、运行实例、调度锁和最近水位。禁止在身份写事务或迁移运行中跳时。优先 slew；若必须 step，先形成暂停受影响平台任务、排空事务及防补跑方案，再在该维护窗口执行；发现本计划外服务需要停机时仅该额外停机需协调。
3. 校时后至少连续两次采样确认选源有效、参考时间新鲜、Leap 非 Not synchronised，并检查 system offset、root dispersion、root delay；单凭 Stratum 非 0 或 `timedatectl yes` 不算充分证据。记录安装的 chrony 版本，使用其支持的命令；`waitsync` 必须有限次数，不无限等待。
4. UTC 墙钟用于审计展示；进程内超时/耗时/健康证明 TTL 使用 monotonic；持久转换代次、批次顺序、重试身份使用数据库序号/唯一键，不按墙钟倒退重置。不用单机 monotonic 值跨进程或跨重启排序；重启/检测到墙钟跳变须重新采样。校时前后保留旧证据及校时事件，不改写历史 executed_at 或来源水位。
5. 校时失败标 `clock_health=unhealthy`，停用运行保留真实结果与警示；enable gate 关闭。回退 chrony 配置不得自动把系统时钟拨回错误时间。

### 13.2 目标数据库时间合同与有界偏差采样（不改两目标时间）

实现独立只读采样/健康组件，参数通过现有 settings 管理；建议新增文件 `backend/app/services/identity_clock_health.py` 和对应专项测试，既有 API/配置模块扩展，不新建平行连接体系。

- 每个目标合同包含 source_code、物理端点身份、DB/驱动版本、会话时区、字段真实类型/精度、时间写入表达式、raw 值格式、offset/UTC 转换规则、证据时间与合同版本。字段 raw 值始终留存，不能只存转换后的字符串。时区/端点/写入表达式变更使合同失效；缺合同的旧证据标 legacy_unverified，不追溯补造 offset。
- JHEMR：先确认 Vastbase 当前版本是否支持 `clock_timestamp()`、`current_setting('TimeZone')`、`EXTRACT(EPOCH ...)` 及服务端格式化；这些 PostgreSQL 参考语义须在目标限量 SELECT 核验后使用，不假设完全兼容。`CURRENT_TIMESTAMP/now()` 可能是事务开始时间，不用于长事务中的“当前时钟”测量。`locked_time` 若是无时区类型，必须核实 CURRENT_TIMESTAMP 写入该列时的会话转换；不能把无时区 epoch 当 UTC。只改变客户端表示，不执行 ALTER SYSTEM/ALTER DATABASE/改目标时区。
- CDMS：查字段类型并同时读取 `SYSDATE`、`SYSTIMESTAMP`、`DBTIMEZONE`、`SESSIONTIMEZONE`。`FCHANGEDATE=SYSDATE` 的时间来源是数据库主机时间；DBTIMEZONE=+00:00、SESSIONTIMEZONE=+08:00 均不能单独证明该 DATE 字段是 UTC/+08:00。Oracle DATE 无时区且秒级精度；保存原始年月日时分秒与证据合同，不伪造亚秒精度。历史其他程序写入的 FCHANGEDATE 不自动套用本次写入合同。
- 每个目标串行取 3 次单行时间样本，每次记录平台发送/接收 UTC (`t0/t1`)、monotonic RTT、目标服务端实际时刻 `T`、字段精度。偏差估计为 `T-(t0+t1)/2`，误差区间至少包含 RTT/2、目标量化误差与平台时钟误差；不假设网络完全对称。多次采样区间不相容、RTT 异常或墙钟在采样中跳变时标不稳定，不能强行平均成可信值。
- 本轮建议默认：样本最多 3 次、单次超时 5 秒、RTT 上限 2 秒、健康证据 TTL 300 秒；这些是新组件工程默认值，不是对现有停用/变更阈值的调整。失败结束该目标采样，不循环等待 DBA；低可信/过期时 enable gate 关闭，disable-only 依当前来源/目标状态证据与写门禁判定。偏差绝对值大但稳定要明确告警，不修改目标时间，也不通过扩大容差放行恢复。
- 采样只读结果可以替代“必须拿到目标 OS NTP 配置”的材料要求，但不能成为解锁凭证。UTC 换算仅用于审计排列/排查；恢复比较同一目标原始状态证据，不通过减掉估计偏差去改写 locked_time/FCHANGEDATE。

### 13.3 锁归因必须独立于时钟接近程度（覆盖 P0-4/P0-9 的旧容差方案）

当前真实代码 `identity_account_state.attribution_matches` 及两适配器将 naive 贴为 UTC，再用 ±300 秒判断归因。仅改成目标时间或提高/配置化容差仍不满足 §4.6.4-3：人工可能在停用后 30 秒追加安全锁，也可能在同一秒内更新，甚至不改变状态或时间。**时间一致不是锁所有权证明。**

必须实现：

1. 停用真实执行前持久化意图/批准引用/目标指纹/源观察/转换代次，提交后记录目标 raw 状态、raw 时间/类型/精度、事务回读与 commit 结果、`origin_disable_attempt_id`。`already_locked` 或只读观察不得创建“平台拥有锁”的证据；commit 结果不确定记 pending_reconcile，回读不能补造归因。
2. enable 的归因输入明确引用未被后续事件取代的停用 attempt（与 enable 的 transition_seq 通常不同）。查询条件覆盖 target fingerprint、院区、rule_version/适用合同及锁周期；禁用“同工号最近一次停用时间”兜底。
3. 自动恢复资格必须同时有：本规则确实执行停用的持久证据、目标当前状态/原始值仍匹配、目标现有可靠审计或版本/锁原因合同能够排除后续人工/安全锁、HIS 本轮双启用、保护/映射/运行时审批全部通过。目标审计若不覆盖“重复锁/同值写/所有入口”，不能据“没查到新日志”断言没有人工锁；不新增目标表/触发器/锁字段以绕过限制。
4. 有可用目标版本时，以版本+状态+稳定键+院区在同一事务条件更新；只有时间字段时可作附加 CAS 条件，但不替代所有权。时间匹配按已核实数据库类型/精度精确比对，不使用秒级容差。读取后被人工改动必须零更新、回读并 blocked；受控执行器事务内部的行锁属于受控写实现，普通只读采样仍禁止锁表。
5. 缺可证明所有权的目标能力时，交付 `automatic_enable_supported=false` 及具体缺证据原因；保留隔离测试和代码关闭态，生产两个 enable 不启用。以后由用户逐例批准的人工恢复是独立治理路径，本计划不实现“点一下忽略归因”。8.83 校时完成也不会自动开启恢复。
