# 122 每日人员同步任务状态审计与签名失败整改执行计划

## 1. 目标与完成定义

本次要解决的不是“定时器有没有一条 success 日志”，而是让每日同步具备唯一调度来源、真实总状态、子任务可追溯、增量水位正确、每个目标动作可审计、失败可告警且可安全恢复。

完成后必须回答五个问题：

1. 昨夜任务是否真的被唯一调度器触发？
2. HIS→CDMS/JHEMR 主账号同步和 JHEMR 签名子任务分别成功、部分成功还是失败？
3. 本批处理了哪一个增量区间，水位何时、按什么条件推进？
4. 每个目标动作是计划、执行、跳过还是失败，失败发生在哪个受控步骤？
5. 超时、部分成功、权限不足、连续失败或调度中断时，谁能从状态接口和告警中及时发现？

## 2. 2026-08-09 只读核查结论

### 2.1 当前实际调度

平台存在两套“是否启用”的事实：

- 容器配置 `identity_sync_enabled=False`、`identity_nightly_enabled=False`，因此进程内 APScheduler 不注册任务；
- 宿主机 `/etc/cron.d/data-asset-identity-nightly` 每日 02:00 通过 `docker exec` 运行 `/app/scripts/run_identity_modified_nightly.py`。

因此页面/状态接口若只读容器 settings，会显示“关闭”，但任务实际上由宿主机 cron 每日运行。这个分裂会造成误判，也存在未来误开两个调度器导致重复执行的风险。

### 2.2 最近运行事实

| 日期 | 主流程候选 | 主流程成功 | 主流程失败 | 签名子任务 |
|---|---:|---:|---:|---|
| 2026-08-06 | 2 | 2 | 0 | 固定权限失败 |
| 2026-08-07 | 2 | 2 | 0 | 固定权限失败 |
| 2026-08-08 | 4 | 4 | 0 | 固定权限失败 |
| 2026-08-09 | 4 | 4 | 0 | 固定权限失败 |

主流程 `triggered_by=host_cron_modified_sync`，运行状态 success，熔断器关闭且连续失败为 0。但 `identity_signature_sync.sync_missing_jhemr_signatures()` 每天固定产生 16 条 `InsufficientPrivilege`，runner 仍按主流程状态返回退出码 0。

### 2.3 已确认缺口

1. `run_identity_modified_nightly.py` 先取得主流程结果，再把签名结果挂到 JSON；进程退出码只看主流程 `status`，签名失败被掩盖。
2. `identity_nightly_scheduler.py` 的状态来自容器 settings 和最后运行，不能表达宿主机 cron 的真实启用、配置指纹和心跳。
3. cron 固定传入 `APP_IDENTITY_SYNC_MODIFIED_SINCE=2026-08-04T00:00:00`，并非真正按成功水位增量推进。
4. `asset_identity_sync_watermarks` 当前 0 行，无法证明批次边界或恢复点。
5. `asset_identity_sync_actions` 当前 0 行；虽然有 scheduler run、batch 和 managed relation，却无法逐目标审计计划/执行/跳过/失败。
6. 签名子任务失败没有进入 scheduler run 的 failed_count、总状态、熔断或告警。
7. 日志会输出很长的脱敏 ID 数组；虽然已遮蔽，仍不符合最小日志原则。

结论：每日 02:00 的主账号同步近期在运行且主流程成功，但整套任务不能判定为“完全健康”，应判定为“主流程成功、签名子任务持续部分失败、监控口径不完整”。

## 3. 目标运行架构

### 3.1 唯一调度提供者

生产只保留一个真正触发任务的 provider。结合多 worker 容器风险，本计划优先保留宿主机 one-shot 调度（cron 或后续 systemd timer），进程内 APScheduler 保持关闭。这里是目标方案，不授权 Luna 直接修改生产。

调度状态不再只看配置布尔值，至少由三类事实组成：

```text
configured provider：host_cron / systemd_timer / in_process / disabled
provider heartbeat：配置指纹、最后观测时间、下一计划时间
persisted run facts：最后开始、结束、总状态、各子任务状态、是否逾期
```

如果检测到两个 provider 同时启用，状态必须为 `misconfigured` 并阻止第二个任务启动，不能依赖数据库锁后仍把重复调度视为正常。

### 3.2 统一总状态

建立稳定枚举：

- `success`：所有必需子任务成功，允许定义明确的无候选 skipped；
- `partial_success`：主流程成功但任一必需子任务有失败，或部分目标成功；
- `failed`：主流程失败、关键前置失败、事务/回读失败或达到熔断条件；
- `skipped`：无候选、维护窗口、锁被占用等可解释跳过；
- `running`：仍在时限内执行；
- `overdue`：超过 26 小时没有成功/部分成功 run，或运行超过最大时长；
- `misconfigured`：重复调度提供者、缺关键配置或水位不合法。

`lock_held` 作为 skip reason，不应与 success 混为一谈。

### 3.3 统一结果信封

runner 最终只输出聚合后的安全摘要：

```json
{
  "run_id": "...",
  "triggered_by": "host_cron_modified_sync",
  "overall_status": "partial_success",
  "main_sync": {"status":"success","planned":4,"succeeded":4,"failed":0},
  "signature_sync": {
    "status":"partial_success",
    "planned":16,
    "succeeded":0,
    "skipped":0,
    "failed":16,
    "error_classes":{"InsufficientPrivilege":16}
  },
  "watermark": {"from":"...","to":"...","advanced":false},
  "duration_ms": 0,
  "warnings":["SIGNATURE_PERMISSION_DENIED"]
}
```

退出码建议：

- `0`：success 或定义清楚的正常 skipped；
- `2`：partial_success，用于 cron/systemd 和监控明确识别；
- `1`：failed/misconfigured/不可恢复异常。

脚本必须在 finally 中完成 run 状态落库，再返回退出码；不能因为 JSON 打印或次要告警失败而覆盖原始异常。

## 4. 详细解决方案

### 4.1 子任务状态持久化

推荐在 `asset` schema 新增 `asset_identity_sync_subtasks`，不要仅把不可查询的大 JSON 塞进 run：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `run_id` | 关联 scheduler run |
| `subtask_code` | `main_account_sync` / `jhemr_signature_sync` 等稳定枚举 |
| `target_system` | CDMS/JHEMR/aggregate |
| `status` | running/success/partial_success/failed/skipped |
| `planned_count` | 计划数 |
| `succeeded_count` | 成功数 |
| `skipped_count` | 跳过数 |
| `failed_count` | 失败数 |
| `error_classes` | 只存类别和计数的 JSON，不存姓名/完整工号/SQL参数 |
| `started_at/finished_at` | UTC 时间，展示层转 Asia/Shanghai |
| `report_summary` | 限长安全摘要 |

要求手写 Alembic `upgrade()`/`downgrade()`；本地无隔离 PostgreSQL 时只做静态/单元验证并标记阻断，不得用生产库代替。若团队裁决暂不加表，最小兼容方案也必须把各子任务状态聚合到 scheduler run 的结构化 summary，但不能把它作为永久终态。

### 4.2 签名失败精确分类

`identity_signature_sync.py` 不能只捕获一个泛化异常。按操作步骤包装并归类：

```text
source_signature_select
target_user_lookup_select
target_picture_lock_select
target_picture_update
target_picture_insert
target_commit
target_readback
```

每类错误记录：目标系统、步骤、异常类、脱敏数据库错误码、数量、是否可重试。禁止记录 SQL 参数、签名二进制、姓名、完整工号或凭据。

`InsufficientPrivilege` 的修复流程：

1. 用专用账号在受控环境执行最小权限只读探针，确定是 SELECT、INSERT、UPDATE、sequence 还是函数/Schema 权限不足。
2. 输出“当前权限/所需操作/建议最小 GRANT/回滚 REVOKE/验证 SELECT”的 DBA 权限矩阵。
3. Luna 只生成矩阵和验证脚本，不直接 GRANT/REVOKE。
4. 运维显式授权并由 DBA 处理后，只做一个受控账号验证；验证成功仍不得自动补跑历史 16 条。
5. 经用户批准灰度补跑，再验证幂等、回读和审计。

不得把捕获异常后 `continue` 当作整体成功，也不得为了变绿关闭签名子任务。如果签名同步是非必需功能，需要业务负责人书面改成 optional 并在状态页明确展示；不能由开发自行降级。

### 4.3 增量水位

废除固定 `modified_since=2026-08-04` 作为长期运行策略，使用平台水位表维护：

```text
watermark key = pipeline + source + entity_type
value = last_modified_at + employee_tiebreaker
safe_lookback = 可配置的小时间窗
```

推进规则：

1. run 开始时读取上次 committed watermark，形成 `[from, candidate_to]` 批次窗口。
2. 来源查询使用 `modified_at > last_time OR (modified_at = last_time AND employee_key > tie_breaker)`，同时可应用安全回看窗口。
3. 依靠 managed relation、HMAC 业务指纹和目标回读保证重复记录幂等。
4. 只有达到预先定义的可接受状态才推进水位。默认：所有必需子任务 success 才推进；若签名和账号采用独立水位，则分别推进且总状态仍可 partial_success。
5. 失败/中断不推进；重跑复用同一窗口。
6. 初始水位必须 dry-run，比较固定窗口候选数、去重数和预计动作数，经人工确认后再 seed；不得直接以“当前时间”跳过历史数据。
7. 水位写入与 run 完成状态应在平台库事务内一致提交。

优先推荐为主账号和签名各设独立 watermark，避免签名权限失败长期阻塞账号增量，也避免主流程 success 错误推进签名进度。

### 4.4 动作审计

每个目标动作必须写 `asset_identity_sync_actions`，至少包含：

- run/batch/subtask/target；
- 员工稳定 HMAC 指纹，禁止可逆明文标识；
- action type：create/update/lock/role_sync/dept_sync/signature_insert/signature_update/readback；
- status：planned/executed/skipped/failed/rolled_back；
- reason code、rows affected、started/finished；
- safe before/after digest，仅记录非敏感字段差异摘要；
- exception class 和数据库错误码，不存 SQL/参数/堆栈中的凭据。

动作审计写失败属于任务失败，不能继续执行无法追踪的业务目标写入。对纯 dry-run 也记录 planned/skipped，便于候选数守恒。

### 4.5 事务、幂等和熔断

- 继续按单人员×单目标事务隔离，CDMS 失败不自动回滚已经独立提交的 JHEMR，但总状态必须 partial/failed 并进入补偿队列。
- 每个动作执行前检查 managed relation 和目标当前状态；执行后强制回读。
- 同一 run/pipeline 使用数据库分布式锁；锁 owner、获取/释放时间进入审计。
- 失败率、连续权限错误、回读不一致达到阈值即熔断剩余动作；阈值从配置读取并在状态接口展示。
- 权限类确定性失败默认不可盲目重试；网络瞬时失败才允许有限指数退避。
- 不自动 DELETE 人工角色/控制配置，不覆盖用户明确要求保留的目标配置。

### 4.6 状态接口与告警

状态接口至少返回：

- authoritative provider、provider config fingerprint、最后心跳；
- 上次和当前 run 的 overall status；
- main/signature 子任务计数；
- committed/candidate watermark；
- 最后成功时间、最后部分失败时间、连续失败数；
- circuit breaker、lock、overdue；
- 最近错误类别聚合和 correlation/run id。

告警条件：

1. overall `partial_success` 或 `failed`；
2. 26 小时无新的可接受 run；
3. run 超过最大时长仍 running；
4. 任一权限错误；
5. 水位连续两次不推进且候选非零；
6. 动作审计数不守恒；
7. 双调度 provider 或配置指纹变化；
8. 熔断器打开、回读不一致或隔离队列增长。

告警内容只含 run id、目标、错误类别、计数、时间和处理手册链接，不含人员明细。

### 4.7 日志最小化

将长 ID 数组改为：总数、成功/跳过/失败数、前 N 个 HMAC 短指纹（默认 N=3）和错误类别聚合。详细单项状态只进入受控审计表，不打印到容器标准输出。
