# 临床诊断映射导入同步与前端工作台一次性整改计划

## 1. 文档定位

本计划用于一次性完成并验收：

1. `临床诊断字典与国家版本映射关系_图片提取.xlsx` 的增量导入、审核、正式入库；
2. 诊断映射向 HIS 与 JHEMR（海量）下发前的安全整改；
3. 字典中心前端从“表格 + 原始 JSON + 单动作按钮”改造成直观的分步工作台；
4. 测试库迁移、后端测试、前端 typecheck/build 和浏览器验收；
5. 为后续 AI 留下明确、可复验的代码和文档入口。

本计划承接 `96_临床诊断字典同步海量与HIS分析与开发步骤.md` 与
`97_关系图谱与字典下发复核整改计划.md`。本文件只规划平台代码和测试；
在没有用户单独授权、审批和生产窗口时，不执行 HIS/JHEMR 业务库写入。

## 2. 本次复核结论

结论：**部分实现，不具备批量导入及安全下发封板条件。**

### 2.1 已具备

- 平台已有院内诊断、国家临床版 2.0、国家医保版 2.0 三类代码集。
- 映射模型允许多个院内编码映射到同一国家/医保编码。
- 页面支持单条映射维护、查询和导出。
- 后端已有 HIS/JHEMR 诊断及手术的计划、dry-run、单条新增和单条停用骨架。
- 写通道默认关闭，写凭据与只读凭据已有隔离方向。
- 灰码可写入 JHEMR `diagnosis_dict.ybhm='灰码'`，且不写医保对照表。

### 2.2 文件实测

目标 Excel：

- 工作表：`诊断字典映射`
- 数据行：35
- 表头：2 行
- 字段：字典属性、院内疾病编码/名称、国家临床版 2.0 编码/名称、
  国家医保版 2.0 编码/名称
- 35 个院内编码均非空且唯一
- 国家医保编码共 33 个不同值；`I63.200`、`I63.500` 各有两条院内映射，
  属于合法 many-to-one，禁止按医保编码去重
- `I63.800` 为医保灰码，医保名称为空
- 有 5 条国家临床版与医保版编码不同，必须保存为两套独立映射

该文件来自图片提取，应按 OCR 证据处理，默认只能进入待审核层，不能自动批准或直接下发。

## 3. 目标状态

最终形成下列闭环：

```text
Excel 上传
  → 文件 SHA 去重
  → 两行表头解析
  → OCR 暂存行
  → 格式/重复/冲突校验
  → 人工逐行或批量审核
  → 仅批准行增量合并正式字典
  → 对 HIS/JHEMR 只读差异检查
  → 服务端生成不可篡改计划
  → dry-run
  → 人工审批与确认
  → 按目标系统、诊断编码原子执行
  → 结果对账、失败重试、审计
```

平台 PostgreSQL 是字典治理事实源。HIS/JHEMR 是下发目标，不得反向自动覆盖平台。

## 4. 一次性实施范围

### 4.1 数据模型与手写迁移

新增手写 Alembic 迁移，禁止 autogenerate。新表继续使用 `asset` schema 和
`asset_dict_medical_*` 前缀。

建议新增：

1. `asset_dict_medical_import_rows`
   - `id`
   - `import_run_id`
   - `source_file_name`
   - `source_file_sha256`
   - `source_sheet`
   - `source_row_no`
   - `row_hash`
   - 七个原始 Excel 字段
   - 七个规范化字段
   - `insurance_mapping_status`：`valid/grey/empty/invalid`
   - `validation_status`：`valid/warning/error/conflict`
   - `validation_errors` JSONB
   - `diff_type`：`new/exact_match/platform_conflict/duplicate_in_file`
   - `review_status`：`pending/approved/rejected`
   - `reviewer/reviewed_at/review_note`
   - `merged_at/merged_by`
   - `created_at/updated_at`

2. `asset_dict_medical_push_plans`
   - 计划头、目标系统、类别、状态、平台数据版本、内容哈希、过期时间、创建人、
     审批人和审计字段。

3. `asset_dict_medical_push_actions`
   - 只保存结构化业务参数和服务器生成结果；
   - 不接受或持久化客户端 SQL；
   - 状态覆盖 `planned/exact_match/conflict/blocked/approved/executing/succeeded/failed`；
   - 唯一键保证同批次、目标系统、诊断编码、动作类型幂等。

4. `asset_dict_medical_push_runs`
   - 记录系统事务包执行、重试、行数、错误脱敏摘要和对账结果。

修改现有映射时，明确“同一院内编码、同一目标代码集、同一标准版本只有一条当前映射”。
如需保留历史，增加 `effective_from/effective_to/is_current/source_version/import_run_id`，
不得依靠查询字典覆盖多条结果。

迁移 `downgrade()` 只逆向结构，不尝试恢复已经合并或下发的数据。

### 4.2 Excel 增量导入服务

新增专用解析器，不修改原全量诊断+手术脚本的既有语义：

- 支持工作表 `诊断字典映射`。
- 自动识别两行表头，按名称匹配而不是固定列序。
- 限制扩展名、文件大小、工作表数量、最大行数。
- 计算文件 SHA256、行 hash；同一文件重复上传幂等返回既有批次。
- 规范化全角空格、不可见字符、首尾空白，保留原始值。
- 不改变编码大小写，除非业务规则有明确依据。
- 校验本批重复、同编码异名、缺少名称、非法灰码、国家/医保缺失组合。
- many-to-one 为合法，不得因目标编码重复报错。
- OCR 文件默认 `pending`，禁止导入时写 `approved`。

正式合并必须：

- 只处理 approved 行；
- 使用增量 upsert；
- 不删除本批次未出现的历史字典；
- 完全一致项幂等跳过；
- 名称或映射冲突进入 conflict，禁止自动覆盖；
- 灰码保存为明确状态，不创建伪医保代码项或医保映射；
- 一个批次在平台库单事务提交；
- 写入来源文件、行号、批次和审核人。

### 4.3 后端 API

建议接口：

```text
POST   /api/v1/dict-medical/imports/diagnosis-mapping
GET    /api/v1/dict-medical/imports/{run_id}
GET    /api/v1/dict-medical/imports/{run_id}/rows
POST   /api/v1/dict-medical/imports/{run_id}/validate
POST   /api/v1/dict-medical/imports/{run_id}/rows/review
POST   /api/v1/dict-medical/imports/{run_id}/merge

POST   /api/v1/dict-medical/push/plans
GET    /api/v1/dict-medical/push/plans/{plan_id}
POST   /api/v1/dict-medical/push/plans/{plan_id}/preflight
POST   /api/v1/dict-medical/push/plans/{plan_id}/approve
POST   /api/v1/dict-medical/push/plans/{plan_id}/execute
POST   /api/v1/dict-medical/push/plans/{plan_id}/retry
GET    /api/v1/dict-medical/push/plans/{plan_id}/reconcile
```

整改旧接口：

- 废弃客户端传完整 action 的 `/push/apply-one` 写模式；
- 如需兼容旧前端，旧接口只能 dry-run，并返回迁移提示；
- execute 只接受 `plan_id`、目标系统和确认信息；
- SQL 必须由服务端白名单模板重新构造；
- 计划生成后保存 content hash，源字典变化则计划过期；
- `category_code`、目标系统、表、动作类型均使用枚举严格校验；
- 对请求数量、编码数量和上传文件设置硬上限。

### 4.4 权限和审批

权限至少拆分：

- `dict.medical.view`
- `dict.medical.edit`
- `dict.medical.import`
- `dict.medical.review`
- `dict.medical.push.plan`
- `dict.medical.push.approve`
- `dict.medical.push.apply`
- `dict.medical.push.stop`

执行要求：

- 导入人与审核人不能为同一人；
- 计划创建人与审批人不能为同一人；
- apply 必须同时满足专用权限、服务端开关、计划已审批、计划未过期、
  写策略为 `medical_dict_push`、专用写凭据存在；
- 不允许只读凭据回退；
- confirmation token 不回显、不写日志、不写审计；
- AI 账号永远不授予 approve/apply/stop。

### 4.5 目标库预检、事务与对账

预检必须只读执行：

- 核实目标表和列存在；
- 核实字段类型、长度、NULL 和唯一约束；
- 不允许字符串静默截断；
- 读取远端当前记录并产生：
  `new/exact_match/conflict_name/conflict_national/conflict_insurance/stopped_exists`；
- 冲突不自动更新，进入人工处理；
- 大表查询必须按单编码或受限编码列表走索引，禁止全扫。

执行事务：

- HIS 每个诊断作为一个系统事务包；
- JHEMR 同一诊断涉及的 `diagnosis_dict`、`jhdict_icd_vs_clinic`、
  `diagnosis_contrast_dict` 使用同一连接和事务；
- HIS 与 JHEMR 分别提交并分别记录状态，不伪装成跨库原子事务；
- `serial_no` 使用目标库序列/身份列；不能改库结构时使用锁定分配或唯一冲突重试，
  禁止裸 `MAX+1`；
- 重跑只补失败事务包，成功项保持幂等；
- 执行后用只读查询逐项对账。

### 4.6 前端信息架构

不要继续把所有功能叠在一个长页面。字典中心改为四个清晰标签页：

1. **字典总览**
   - KPI：院内诊断数、国临映射覆盖率、医保映射覆盖率、灰码数、待审核数、冲突数；
   - 最近导入批次和最近下发状态；
   - 明确显示写通道关闭/开启状态，但不展示 token。

2. **映射维护**
   - 一行展示院内、国临、医保三段映射；
   - 固定院内编码/名称，国临和医保使用分组表头；
   - 灰码、缺失、冲突使用一致的 tag 与颜色；
   - 支持关键词、映射完整性、审核状态、来源批次筛选；
   - 详情抽屉显示版本、来源、审核和变更历史；
   - 多对一目标编码允许重复展示，不做错误标红。

3. **导入审核**
   - Step 1 上传；Step 2 解析校验；Step 3 差异审核；Step 4 合并结果；
   - 拖拽上传并显示文件名、SHA、工作表和行数；
   - 汇总卡显示新增、一致、警告、错误、冲突、灰码数量；
   - 表格支持只看异常、定位 Excel 行号、原始值/规范值对照；
   - 批量批准只能作用于“校验通过且非冲突”行；
   - 冲突必须逐行处理并填写审核意见。

4. **同步下发**
   - Step 1 选择已批准批次/编码；Step 2 目标库预检；Step 3 审批；
     Step 4 dry-run；Step 5 分系统执行；Step 6 对账；
   - HIS、JHEMR 使用独立状态卡，避免误认为跨库同时成功；
   - 不显示原始 SQL JSON；显示业务可读差异、影响表和动作；
   - 危险操作放在独立确认抽屉，按钮文字使用“执行已审批计划”，不用裸 `apply`；
   - 错误状态提供脱敏原因、重试条件和对账入口。

视觉约定：

- 成功绿、待审核蓝、警告橙、阻断红、未执行灰；
- 页面主操作每一步最多一个；
- 表格默认只展示业务字段，技术字段进详情抽屉；
- 重要状态同时使用文字和图标，不能只靠颜色；
- 适配 1366×768，表格横向滚动时冻结院内编码和操作列；
- 空状态说明下一步动作，不展示空白大表；
- 保持现有 `/dict-medical/*` 路径兼容。

### 4.7 前端工程要求

- API 继续放在 `frontend/src/api/dict.ts`，补完整 TypeScript 类型，禁止新增 `any` 扩散。
- 将当前单文件大页面拆为同目录组件，例如：
  `OverviewPanel.vue`、`MappingTable.vue`、`ImportWizard.vue`、
  `PushWizard.vue`、`MappingDetailDrawer.vue`。

## 7. 回滚

- 数据库迁移前做平台库备份并记录恢复点。
- 新增表可以通过 Alembic downgrade 回退结构。
- 正式字典 merge 必须记录 import_run_id，提供仅回滚本批新增项的受控平台回滚方案；
  若某项已被后续批次引用则阻断自动回滚。
