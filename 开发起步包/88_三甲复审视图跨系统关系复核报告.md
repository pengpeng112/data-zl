## 2. 总体结论

三甲复审视图应按以下真实层级理解：

```text
真实业务源系统
  ├─ HIS源库：MEDREC / ORDADM / LAB / EXAM / INPBILL / OUTPBILL / COMM ...
  ├─ LIS源库：rmcloudlis7.dbo
  ├─ 移动护理源库：LUNA_MCS_SDSEY
  ├─ HRP源库：人员与组织

数据中心 10.10.8.216
  ├─ HIS：HIS源表的同名汇聚/镜像层
  ├─ MTL/JHEMR：电子病历内容层
  ├─ SM：手麻汇聚层
  ├─ CDA：院内码到省级/国标码映射
  ├─ LIS/PACS/YDHL等：周边系统汇聚或历史Schema
  └─ ODS：面向标准数据集的 V_EMR_* 视图层
  ↓
三甲复审 / 省平台 V1.3 数据集
```

因此：

- 数据中心 `HIS` Schema 中的医嘱、费用、挂号、检验等基础表，与 `hisuser` 源库的业务表在业务含义上高度同源，但源库按多 Owner 存放，数据中心被归并成 `HIS` Schema。
- 数据中心 `ODS.V_EMR_*` 才是本清单中大部分标准化视图的实际位置。
- 数据中心 `CDA` 字典和本地映射表负责把源系统院内码转换为 V1.3 要求的标准码；这正是源 HIS 可能没有完整标准字典时的补充层。
- 电子病历内容、手麻记录、输血等视图并非只依赖 HIS 源表，不能全部归类为“HIS视图”。
- LIS、移动护理和 HRP 有独立源库对象；数据中心内可能另有镜像或重建视图，两者应保留“源对象 → 汇聚对象 → 标准视图”血缘。

- 同一个业务对象没有被多套源重复提供。

V1.3文档自身也存在待确认项，不能机械照抄：

- 章节编号重复；
- `CHAR1`、`ODER_ITEM_nAME`、`oDR_sn` 等疑似拼写问题；
- 部分说明不完整；
- 个别表格的多行说明可能在自动解析时被误识别为字段；
- V1.3新增字段可能尚未进入旧视图。

因此后续生成SQL应采用“标准字段名 + 活库真实类型 + 明确转换”的方式，而不是直接把V1.3类型强制套到源表。

## 10. 建议在平台中维护的关系类型

为了避免系统关系图谱误导，建议至少区分以下边类型：

| 边类型 | 示例 | 是否属于业务主外键 |
|---|---|---|
| `replicated_from` | `MEDREC.PAT_VISIT → 数据中心 HIS.PAT_VISIT` | 否，属于复制/镜像血缘 |
| `derived_from` | `ODS.V_EMR_DOC_ORDER_DRUG → HIS.ORDERS` | 否，属于视图血缘 |
| `business_join` | `PAT_VISIT(PATIENT_ID,VISIT_ID) → ORDERS(...)` | 是，需验证等级 |
| `standardized_by` | HIS院内码 → `CDA.CDA_DICTIONARY` → 国标码 | 否，属于值域转换 |
| `cross_system_match` | LIS `BARCODE` ↔ HIS `TEST_NO` | 是，跨系统验证关系 |
| `identity_match` | HRP职工号 ↔ HIS人员工号 | 是，需处理有效期和重复 |
| `candidate` | 仅从视图SQL或同名字段解析 | 否，待验证 |

平台展示时仍按“物理端点 → 数据库/服务 → Schema/Owner → 表/视图 → 字段”组织；业务系统标签不能替代真实物理归属。
