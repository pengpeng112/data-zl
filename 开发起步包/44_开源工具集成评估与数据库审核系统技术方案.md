# 开源工具集成评估与数据库审核系统技术方案

> 目标：评估 SchemaCrawler、SQLGlot、自研 SQL 规则引擎、Soda Core、Great Expectations、tbls、OpenMetadata、ECharts、React Flow/xyflow 是否适合集成到现有医院 BS 数据库审核系统，并给出可落地架构。

## 1. 总体结论

当前系统目标是医院信息科可实际运行的数据库审核、质控、关系分析和数据治理系统，不是单纯 ER 图工具。因此推荐路线是：主系统继续自研，第三方工具只作为能力插件接入。

第一阶段优先落地：数据源管理、元数据直采、资产目录、业务关系推断、自研 SQL 规则引擎、SQLGlot 视图血缘微服务、ECharts 质量看板。SchemaCrawler 和 tbls 作为辅助采集/文档工具先离线试点。Soda Core、Great Expectations、OpenMetadata 暂不作为主链路，后期按场景补充。

核心判断：医院老系统缺少真实外键，实际关系依赖 `PATIENT_ID + VISIT_ID`、`TEST_NO`、`EXAM_NO`、`APPLY_NO`、`REPORT_ID` 等业务键。第三方工具可采集真实元数据、解析 SQL、生成文档，但不能替代医疗业务关系验证和 SQL 质控规则执行。

## 3. 工具定位与评估

### 3.1 SchemaCrawler

定位：数据库 schema discovery / comprehension 工具，适合做元数据采集、数据字典、真实 PK/FK/索引/视图定义采集和基础 ER 关系生成。其项目说明强调 schema discovery、data governance、schema diagrams、JDBC 支持和 Java API 能力。

适用场景：

- 多数据库真实元数据采集：Oracle、SQL Server、PostgreSQL、MySQL 等，只要 JDBC 驱动可用。
- 离线或定时生成数据字典、HTML/图表、JSON 等结构化结果。
- 作为 `asset_tables`、`asset_columns`、`asset_relations` 的辅助数据来源。
- Java 后端可直接使用 Java API；非 Java 后端优先 CLI 调用，降低集成复杂度。

不适用场景：

- 不能自动理解医院隐含业务关系。
- 不能判断 `PATIENT_ID + VISIT_ID`、`TEST_NO`、`EXAM_NO` 等业务键是否真实可用。
- 不能替代数据质量规则执行。

推荐集成方式：

| 后端技术栈 | 推荐方式 | 说明 |
|---|---|---|
| Java | Java API | 直接拿对象模型，适合深度集成 |
| Python/FastAPI/其他 | CLI + JSON 输出 | 由调度任务执行，解析结果入库 |
| 内网定时任务 | CLI | 驱动、配置、输出目录标准化 |

落地建议：先保留现有数据库字典直采作为主采集链路，再引入 SchemaCrawler 做对照扫描。大 schema 必须按 system/schema/table include pattern 分批扫描，避免一次全库耗时过长。JDBC 驱动版本、Oracle 旧版本兼容性、字符集、视图 DDL 权限要做专项验证。

### 3.2 SQLGlot

定位：Python SQL parser / transpiler / optimizer，适合做视图 SQL 解析、来源表识别、JOIN 条件抽取、字段表达式分析和字段血缘。其 README 显示支持 Oracle、Postgres、TSQL 等官方方言，并支持表达式树遍历和 SQL 分析。

适用场景：

- 解析 `V_EMR_*`、平台上报视图、CDA/ODS 视图。
- 提取 `source_tables`、`source_columns`、`join_conditions`、`where_conditions`。
- 识别字段来源类型：直接字段、函数处理、`CASE WHEN`、`NVL`、`DECODE`、拼接、截断、聚合、常量、字典映射。
- 为 AI 解释上报字段来源提供结构化上下文。

医院 Oracle SQL 兼容评估：

| SQL 特性 | 处理建议 |
|---|---|
| `NVL` / `DECODE` / `CASE WHEN` | 解析表达式类型，标记为转换/兜底/映射 |
| `TO_CHAR` / 日期函数 | 标记格式化表达式，保留原始 SQL |
| `SUBSTR` / `SUBSTRB` / `DBMS_LOB.SUBSTR` | 标记截断/大字段截取 |
| `UNION ALL` | 按分支拆血缘，目标字段合并多来源 |
| 子查询 / 相关子查询 | 解析成功则展开，失败则保留 raw_sql 并人工复核 |
| Oracle `||` 拼接 | 标记 concat 表达式 |
| 存储过程 / 动态 SQL | 不作为第一阶段自动血缘范围 |

推荐集成方式：独立 Python 微服务。

```text
POST /sql-lineage/parse
input: { dialect, sql, default_schema, known_tables, known_columns }
output: {
  parse_status,
  source_tables,
  source_columns,
  join_conditions,
  where_conditions,
  target_columns,
  column_lineage,
  unsupported_fragments,
  raw_sql_hash
}
```

解析失败处理：保存错误、SQL 片段、失败位置；降级为表级血缘；进入人工维护表 `asset_lineage_manual_overrides`。不要让 SQLGlot 结果直接覆盖人工结论。

### 3.3 自研 SQL 规则引擎

定位：本系统核心能力，必须自研。第三方 DQ 工具不能覆盖医院三甲复审、平台上报、病案、HIS/EMR/LIS/PACS 多系统强业务规则。

规则分类：

| 分类 | 说明 | 示例 |
|---|---|---|
| UNIQUE | 唯一性 | 主键重复、业务键重复 |
| COMPLETE | 完整性 | 必填为空、关键时间缺失 |
| STANDARD | 规范性 | 字段长度、编码格式、值域合法 |
| RELATION | 关联性 | 子表关联不到主表、报告无申请单 |
| ACCURACY | 准确性 | 入院晚于出院、手术开始晚于结束 |

约束级别：`HARD` 严重、`SOFT` 人工复核、`WARN` 提醒、`INFO` 统计。

推荐执行模式：

1. `DQ_RULE.CHECK_SQL` 只写“问题数据 SQL”，即返回异常行。
2. 引擎自动包裹统计：`total_cnt` 使用目标表统计或规则配置 SQL，`error_cnt` 使用异常 SQL count。
3. 样例 SQL 加最大行数：Oracle 用 `ROWNUM <= :max_rows`，PostgreSQL/MySQL 用 `LIMIT`，SQL Server 用 `TOP` 或外层分页。
4. 结果入 `DQ_RESULT`，样例入独立 `DQ_RESULT_SAMPLE`，避免 CLOB 过大影响结果表查询。

SQL 安全要求：

- 只允许 `SELECT` / `WITH ... SELECT`。
- 禁止 `INSERT`、`UPDATE`、`DELETE`、`MERGE`、`DROP`、`TRUNCATE`、`ALTER`、`CREATE`、`EXEC`、`CALL`、`GRANT`、`REVOKE`。
- 禁止多语句分号执行。
- 禁止访问非授权 schema。
- 只读数据库账号 + 连接只读事务 + statement timeout + fetch size + max rows。
- CLOB/BLOB 默认不取全文，样例脱敏。

规则模板：

| 模板 | 生成逻辑 |
|---|---|
| 主键重复 | `GROUP BY key HAVING COUNT(*) > 1` |
| 必填为空 | `field IS NULL OR TRIM(field) = ''` |
| 字段长度超长 | `LENGTH(field) > max_len` |
| 值域不合法 | `field NOT IN (...)` 或无法关联字典 |
| 孤儿外键 | `LEFT JOIN parent WHERE parent.key IS NULL` |
| 时间先后错误 | `start_time > end_time` |
| 检验报告无申请单 | `LAB_RESULT/LAB_REPORT LEFT JOIN LAB_APPLY` |
| 检查报告无申请单 | `EXAM_REPORT LEFT JOIN EXAM_APPLY` |

### 3.4 Soda Core

定位：可选辅助数据质量/数据契约工具。其项目说明支持 YAML 定义 data quality contracts，并通过 CLI/Python API 验证 schema 和 data。

适用场景：基础通用规则，如 `row_count > 0`、`missing_count(ID)=0`、`duplicate_count(ID)=0`、字段非空率、简单值域。可用于数据仓库表、标准层表、CI/CD 检查。

不适用场景：医院复杂跨表、跨系统、业务时间逻辑、医保/病案/上报规则。老版本 Oracle 与内网部署兼容性必须先验证。

推荐结论：不作为主质控引擎。若接入，由系统根据 `DQ_RULE` 自动生成 YAML，执行后把结果回写 `DQ_RESULT`，不要让用户维护两套规则。

### 3.5 Great Expectations / GX Core

定位：成熟的数据质量测试和文档化框架，Expectation 适合标准化表达数据质量要求，结果文档化能力强。

适用场景：科研数据集、数据仓库、离线数据管道、标准数据集验证。

不适用场景：医院 BS 在线审核、多源库复杂 SQL、强业务规则、现有系统非 Python 主链路时的大规模集成。

推荐结论：不作为主引擎。后期可作为科研数据集或数仓主题表质量文档化试点。

### 3.6 tbls

定位：数据库文档生成工具，适合离线生成 Markdown 数据库文档。其项目说明强调 GFM 文档、多格式输出、单二进制、支持多数据库、diff、lint、coverage。

适用场景：

- HIS、EMR、LIS、PACS、护理、血透等库结构文档化。
- 生成 Markdown 给 AI/Codex 阅读分析。
- Git 管理数据库文档版本。
- 做结构变更 diff 和注释覆盖率检查。

不适用场景：在线质控执行、复杂关系推断、质量规则运行。

推荐结论：作为离线辅助工具，不直接嵌入 BS 主流程。输出 Markdown 可作为文档资产入库或归档。

### 3.7 OpenMetadata

定位：完整元数据和数据治理平台，覆盖数据目录、语义、血缘、质量信号、所有者、标签、API、SDK 等能力。

适用场景：后期建设医院级数据资产门户、统一元数据展示、跨系统搜索、负责人、标签、血缘、质量结果汇聚。

不适用场景：短期替换现有 BS 程序；三甲复审、平台上报、AI 二次校验等强业务审核仍需自研。

推荐结论：短期不作为主系统。后期可通过 API 同步本系统已验证的资产目录、血缘和质量结果，把 OpenMetadata 作为展示门户或元数据交换层。

### 3.8 ECharts

定位：前端统计图和关系图展示工具。适合质量看板、规则通过率、错误率、趋势图、表级评分、字段完整率和值域分布。

适用场景：

- 数据质量总览。
- 系统/业务域/表/规则维度统计。
- 简单表关系图和邻居图。
- Vue3 前端低成本集成。

不适用场景：复杂字段级血缘编辑、大规模节点交互、复杂拖拽编排。

推荐结论：第一阶段优先采用。

### 3.9 React Flow / xyflow

定位：React/Svelte 的 node-based UI 库，适合交互式流程图、节点编辑器、血缘图。

适用场景：React 前端下做表关系图、字段血缘图、源表-视图-上报表链路图、质控规则链路图。

当前系统前端是 Vue3，因此不建议第一阶段直接引入 React Flow。可选路线：

1. 继续用 ECharts graph 做第一版关系/血缘展示。
2. 如需高级交互，评估 Vue 技术栈图谱库或 Vue Flow。
3. 若坚持 React Flow，可用微前端或独立 React 子应用嵌入，但会增加构建、权限、状态管理成本。

## 6. 安全设计

1. 数据库账号：所有业务库只允许只读账号；不授予 DML/DDL 权限。
2. SQL 安全：AST + 关键字黑名单 + 单语句校验；只允许 SELECT。
3. 连接控制：超时、最大返回行数、fetch size、连接池隔离。
4. 方言控制：规则必须绑定数据源和方言，禁止跨数据源直接拼接 SQL。
5. 脱敏：姓名、身份证、电话、地址、病历文本默认脱敏后入样例。
6. 凭据：密码只存 `credential_ref`，实际凭据放环境变量或密钥服务。
7. 审计：连接测试、采集、规则执行、样例查看、权限变更全部写审计。
8. 大表保护：大表规则必须有时间或业务键过滤；禁止 `SELECT *` 抽样。

## 7. 最小可行版本 MVP

### 第一阶段：必须做

1. 数据源管理：Oracle、SQL Server、PostgreSQL，只读连接测试。
2. 元数据采集：表、字段、类型、长度、备注、主键、索引、视图 SQL。
3. 资产目录：系统-库-schema-表-字段四级展示，中文备注和业务域维护。
4. 关系分析：真实 FK + 业务键候选 + 数据验证 + 人工 A/B/C/D 分级。
5. SQLGlot 微服务：解析视图 SQL，生成表级和字段级血缘初稿。
6. 自研 SQL 规则引擎：五类规则、结果统计、样例脱敏、定时/手动执行。
7. ECharts 看板：规则通过率、错误率、系统/表/业务域质量统计。

### 第二阶段：增强

1. SchemaCrawler CLI 定时扫描，与直采结果做差异对比。
2. tbls 离线生成 Markdown 数据库文档，供 AI 和人工复核。
3. 规则模板库扩展到三甲复审、平台上报、病案首页、LIS/PACS 关联。
4. 字段血缘人工修正和版本管理。
5. 权限控制和审批流完善。

### 第三阶段：可选

1. Soda Core 试点通用规则，自动由规则表生成 YAML。
2. GX Core 试点科研数据集或数仓主题表文档化质量检查。
3. OpenMetadata 作为医院级数据资产门户，与本系统 API 同步元数据和质量结果。
4. 高级图谱组件按前端技术栈选择；Vue 优先不引入 React Flow，React 前端才优先考虑 xyflow。

## 8. 风险点与控制措施

| 风险 | 控制措施 |
|---|---|
| Oracle 复杂 SQL 解析失败 | SQLGlot 失败降级表级血缘，保留 raw_sql，人工修正 |
| 医院老系统无外键 | 业务键候选 + 数据验证 + 人工分级，不凭字段名直接入图 |
| 跨库关系难推断 | 先做单系统强关系，跨系统关系等用户提供源库后逐步验证 |
| 大库扫描慢 | 分 schema、分表、夜间任务、超时控制、增量采集 |
| 多数据库方言差异 | Connector + Dialect Adapter + 模板按方言生成 |
| SQL 规则误执行危险语句 | 只读账号、AST 校验、黑名单、超时、审计 |
| 样例泄露敏感信息 | 字段敏感标记 + 样例脱敏 + 权限控制 |
| 工具链过重 | 第一阶段只集成 SQLGlot 和 ECharts，其他工具试点化 |

## 9. 最终推荐

1. 主系统继续自研，不用 OpenMetadata、Soda、GX 替代。
2. 元数据第一优先用数据库字典直采，SchemaCrawler 做辅助校验和文档/ER 输出。
3. 视图 SQL 血缘用 SQLGlot 微服务，必须允许 partial/failed/manual 状态。
4. 数据质量规则执行以自研 SQL 规则引擎为主，覆盖医院五类质控规则。
5. Soda Core 和 GX 仅作为后期通用规则或科研/数仓场景补充。
6. tbls 作为离线文档工具，生成 Markdown 供 AI 分析和版本管理。
7. 前端看板用 ECharts；当前 Vue3 前端不建议直接接 React Flow，复杂血缘图后续评估 Vue 方案或微前端。
