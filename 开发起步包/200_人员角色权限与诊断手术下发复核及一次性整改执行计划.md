## 3. 已确认问题与修改要求

优先级：P0=启用实际写入前必须封闭；P1=本次必须修复；P2=本次完成的易用性和运维可见性改善。下面代码行号为审查时定位，执行者应按函数名重新定位。

### R01（P1）权限页面显示的授权，不一定是当前有效授权

证据：`backend/app/core/security.py:_effective_role_codes` 已过滤 status/valid_from/expires_at；`backend/app/api/v1/permissions.py:get_user_permissions`（约553）、`get_me_permissions`（约565）直接查询全部角色，且实时角色为空时回退到全部历史角色。ApiKey分支也有不带有效期的查询。

影响：已过期、尚未生效或已撤销角色仍可能显示在前端菜单/权限预览；这不直接等于所有后端接口越权，但用户会遇到“看得到却不能操作”。

修复：建立唯一有效授权服务，供中间件、端点依赖、`/me`、个人权限预览和前端数据使用。有效角色为空就是空，不回退历史授权。历史授权单列并显示状态/起止时间/授权来源；给出 `effective_at`。复用已有表，不创建第二套权限模型。

### R02（P1）历史 allow 权限仍可能“界面已勾选，后端拒绝”

证据：`seed_platform_rbac.py` 新建行已写 access，但 existing 集合只按 resource 跳过；`permissions.py:_permission_codes_for_roles` 接受 allow，`security.py:require_permission` 把 allow 拼成 `resource:allow`，语义不一致。

修复：统一权限编码归一函数并覆盖新旧数据。提供只读差异清单、限定旧值到新值的幂等修复与冲突合并策略；在隔离库验证重复执行零变更。正式平台 apply 留给明确批准，不自动重置用户定制矩阵。保留新种子的已修复代码。

### R03（P1）粗角色前缀与细粒度权限双重门禁限制自定义角色

证据：`main.py:ROLE_REQUIRED/_enforce_rbac` 对 dict-medical 仅接受 platform_admin/dict_admin；而端点已有 `dict.medical.plan.create/approve/execute`。自定义“字典审核员”即使有准确权限仍可能被前缀拒绝。

修复：逐路由建立“读/维护/创建/审批/预览/重试/对账”权限表，再将完整受细粒度保护的模块移交端点门禁；不得只删除粗门禁。计划详情/完整性等 GET 也显式要求 view；补匿名、只读、自定义单权限角色的矩阵测试。其他模块仅修复同一计算服务直接影响的路径，不借机全站重构。

### R04（P0）身份管理员能够授予平台管理员，关键端点缺少独立保护

主AI复核证据：`main.py` permissions/auth前缀允许identity_admin；`permissions.py:replace_user_roles`（530—549）无端点权限、不禁止授予platform_admin；`auth.py:create_user`（约368—420）在 `_require_admin_roles` 后直接写入请求的role_codes，没有逐角色存在性/授予范围校验。`bind_api_key`（654起）也允许直接更换密钥绑定身份。`identity.py` 多个列表/详情读接口没有与菜单一致的细粒度权限。

修改要求：建立统一 `can_manage_subject/can_grant_role` 对象级策略，所有创建账号、替换角色、申请执行、密钥绑定、账号重置/换绑入口共享。非platform_admin不得操作platform_admin身份、授予该角色或将密钥绑定该身份；用户不能给自己增加超出批准范围的权限。至少保护最后一个有效可登录管理员，拒绝并发删除/停用/撤权导致零管理员。角色存在性和人员/服务身份存在性必须检查。高风险角色变更使用现有申请审核链和审计，不新建另一套审批系统。

逐接口补view/grant/audit/bind等权限，复用已有准确资源码，确无资源再添加；不能把所有权限都塞到identity.role.manage。先补齐端点保护，再收敛粗前缀。ApiKey只返回非秘密管理信息；对人类与受控服务身份分型，不能强迫机器账号伪绑定真实人员。矩阵中platform_admin因全局旁路而实际全权，应只读并解释策略，不能让人误以为取消一个勾选就能限制管理员。

### R05（P1）账号身份回查与建号/换绑规则不一致

证据：`auth.py:create_user`允许无user_identifier；JWT生成用 `user_identifier or username`，`main.py`新的启用校验却只按 `AuthUser.user_identifier` 查询；由此无绑定账号登录可成功但后续受保护请求找不到账号。`auth.py:patch_user`约456直接改绑定，未复用建号时的人员存在/唯一绑定检查。

修改要求：以JWT的稳定 `sub=AuthUser.id` 定位本地账号并核对可信身份绑定和状态，保留已有禁用立即失效修复；不得用用户名回退绕过账号状态检查。人类新账号按当前产品约定强制人员绑定；既有独立维护/应急账号用显式账号类型兼容，不得批量锁死。人员换绑独立校验目标存在、唯一性、管理员保护，在一个平台事务内更新并撤销旧会话；旧access token通过绑定/版本检查失效。人员身份的历史角色默认留给原身份，不因账号换人而搬给新人员；新的授权须单独批准，不自动复制权限。

### R06（P1）角色替换会丢弃有效期和来源，申请执行需要补最终授权校验

证据：`replace_user_roles`删除目标全部AssetUserRole再重建，只写user_identifier/role_code/granted_by，丢弃状态、来源、申请号和有效期。`permission_requests.py:execute_request`已要求approved，但执行时直接采用payload写角色/数据范围，缺少当前高权限授予范围的统一检查。

修改要求：按授权差异增量撤销/新增，不删除历史；保留仍有效授权原始起止和来源。请求schema和执行边界都校验角色、目标、时间区间、scope_type枚举及filter_json字段/操作符/大小，不能接受任意JSON作为可信范围。执行前再次校验已批准快照未变、更高权限操作策略、申请有效期及当前执行者权限，并发执行幂等。保留“申请人不能自审”的既有规则；不凭本次审查强行引入三人审批。独立审核后的同人执行是否允许应按已明确的动作策略判定；无明确策略的高风险自提权拒绝并说明。

前端授权人显示当前可信登录人，去掉可编辑假授权人；密钥绑定用可搜索的已登记主体；授权保存展示新增/撤销/有效期差异、理由与审计编号，按权限分区请求数据并分页。高风险操作确认一次即可，不对普通页面浏览增加批准流程。

### D01（P0）普通计划没有明确范围，空选择可扩大为整类字典

证据：`dict_medical_push.py:create_push_plan` 只有 `if item_codes` 才限定；500 限制在 API 仅针对非空列表。`PushWizard.vue:createPlan` 普通 insert 不发送 item_codes。`import_run_id` 参数接收但未用于选项查询。

修复：insert/stop/sync_infectious 均要求明确选择；规范化去重后 1—500 个编码，缺失/空列表/空白编码不得解释为全选。所有选项须存在且状态符合动作，否则整个计划拒绝；不得悄悄只执行其中一部分。导入批次若保留，必须解析已审核批次的明确编码，并与用户选项比对；无法实现时显式拒绝该参数，不能继续忽略。stop 保持**单编码**停用约束，不扩大为批量停用。

### D02（P0）审批快照未覆盖全部最终写入内容

证据：`create_push_plan/verify_plan_integrity` v2 快照只覆盖基础名称、部分映射与传染病字段；`medical_code_push.py:_load_platform_rows` 还读取 operation_level、operation_category、performance_level4_flag、restricted_tech_flag、灰码、标准名称等 extra/目标字典字段；执行 `_rebuild_actions` 重新读取这些当前值。创建映射循环取最后一个匹配，核验用 next 取第一个，且计划查询缺少 from_code_set 的精确条件，与执行器查询口径不同。

修复：共享规范化选择/映射解析器；用完整执行语义生成带版本的不可变快照（来源、目标、机构、类别、动作、业务键、字段和值、字典/映射版本、执行器版本）。哈希覆盖全部写入参数；采用相同排序和精确 code_set，歧义映射直接阻断。worker按已审快照重建白名单SQL，并在写入前检查相关版本；中途数据改变拒绝，不能一部分用旧值一部分用新值。客户端不能传SQL/动作包作为可信执行内容。老版计划允许查看，缺少完整绑定的待执行计划要求重新生成，禁止静默补哈希继续写。

### D03（P0）自动审批使用固定身份，不能证明独立审核

证据：`dict_medical_api.py` 约576—600，维护映射后在两个开关开启时创建计划，并以 `approved_by="dict-auto-approver"` 调 `approve_plan`；后者仅比较创建人与审批人字符串。普通 insert/stop 的 `dispatch_target` 也没有专项传染病那样的 AssetActionExecutor 登记校验。

修复：自动生成最多到 draft，移除以固定字符串替代独立审核的自动排队。审批使用可信登录身份，禁止客户端/服务随意指定审批人；复核审批者当前权限并做防自审。将普通诊断/手术的来源、表、动作也纳入现有 `asset_action_executors` 白名单及审批链，默认关闭，复用专项执行器的校验模式。平台管理员不得绕过自身计划的独立审核。worker再次校验执行资格和授权范围；开关/确认令牌不替代对象范围批准。

### D04（P1）停用路径两处冲突

证据一：计划从 inactive 取项，执行器复用 `_load_platform_rows` 强制 active，因此一般停用计划重建为空。证据二：`_run_target_transaction` 约235起按表做 INSERT 存在跳过，没有先限制 action_type；stop使用 `params.code`，存在检查却取 diagnosis_code/operation_code。本次 fake探针已复现第二处。

修复：按动作明确分支；加载状态可由内部动作策略决定，不能改成所有动作都加载所有状态。单项 stop 核验精确业务键、原状态和行数，已停用回读一致记 no_op，缺失/多行/不同机构阻断，不执行新增查重跳过逻辑。JHEMR术式与标准术式的关联停用必须复核共享关系：共享标准码不能因某院内术式停用而误停其他术式；不能推断则阻断并说明。保留单目标事务和提交前回读。

### D05（P1）已存在同码不等于内容一致，计数会误导

证据：执行器存在查询主要为 SELECT 1；命中即 row_counts=0，`_actions_requiring_readback` 排除0行；最后 `succeeded_count=len(runnable)`。因此同码异名/属性不一致不能从“成功”计数识别。

修复：限定业务键读回待写字段，规范化NULL/空串等后比较；一致为 no_op，不一致为 conflict。不得把冲突自动改为 UPDATE。分列 inserted/stopped/updated/no_op/conflict/failed/unknown_commit，不再把零写入伪装成新增成功。对应源字段规范需要 sjzc 元数据核验，不能猜测。

### D06（P1）计划详情与实际运行状态脱节

证据：`get_plan_summary` 只为 sync_infectious 返回逐条 actions；普通计划只有数量。执行器成功更新 DictMedicalPushRun，当前函数未同步 action.status/plan聚合状态；摘要仍按 action.status 计数，前端审批后转“预览”，没有完整运行回读。

修复：详情按权限返回所有动作的业务预览；设计授权状态与执行状态两条轴，保留现有status兼容字段，新增明确的 execution_status，不让成功终态破坏worker的approved前提。按计划/目标/动作关联outbox和run，展示排队、等待配置、执行中、成功、部分成功、失败、需对账、过期；审计显示真实操作者/时间/原因。列表、搜索、详情刷新/轮询及按失败目标重试形成闭环；已成功目标不得再次写。

### D07（P1）重试、并发和跨库提交窗口需要验收，不能假设 exactly-once

现有outbox租约/重试和单目标事务是基础，不是跨HIS/JHEMR原子事务。必须模拟源端 commit 成功、平台结果落库失败，以及租约超时后第二worker接管。新执行前核验租约所有权/版本，源端凭业务键对账防重复；未知提交结果先reconcile，不盲目重放。HIS成功/JHEMR失败时聚合为部分成功，允许只处理失败目标。审批并发应锁定或条件更新 draft→approved，审批记录与outbox同事务、业务键唯一。此项是需要补证的风险，不声称本次已完成并发复现。

### D08（P2）操作界面缺少一眼可理解的范围、原因和真实结果

修复：按§4实现；`/execute`保持预览兼容接口，命名显示“执行预览（不写入）”；审批按钮明确“审批并入队”，禁止显示成“已下发成功”。后端错误使用稳定reason_code+中文说明+request_id，避免把全部400显示成笼统 invalid_push_plan_request。清理 `_dispatch_approved_plan` return 后不可达旧代码，避免后续AI误接旧路径。

## 4. 界面目标与角色矩阵

### 4.1 人员权限：先选人，再看“能做什么”

沿用 `frontend/src/views/identity/` 和现有路由，人员详情增加四个清楚区块：

1. **人员资料**：脱敏展示身份、科室、人员类别、来源与最后同步时间。
2. **平台登录**：是否有登录账号、启用/停用、最近登录；区别于HIS/JHEMR/CDMS账号。
3. **当前生效权限**：业务分组中文名称、来源角色、范围、起止时间；到期/未生效/已撤回放历史区，不混入生效区。
4. **外部系统账号与授权**：按目标系统展示最后已知状态、核验时间、待同步/失败原因；不以平台角色推断源端授权已经生效。199夜跑成果仅作链接，不自动调整外部账号。

角色页展示“角色中文名｜有效人数｜权限数量｜高风险操作｜最近变更”；点击权限能解释来源。保存前显示新增/撤回差异、影响人数；禁止空勾选因请求失败误保存为撤权。危险操作保留确认和审计；普通查询不反复确认。按有效角色查询用户反向清单，分页且不暴露无关个人资料。
