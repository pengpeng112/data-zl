## 4. 逐模块根因与整改结论

### 4.1 数据质量：规则库“空”的根因

后端 `GET /api/v1/quality/rules` 当前返回数组：

```json
{"data": [{"rule_code": "..."}]}
```

前端却读取 `data.items` 和 `data.total`，所以 185 条规则全部被显示成空。前端还发送分页和筛选参数，但后端接口签名不接收这些参数，筛选不会生效。

整改：

1. 将接口统一为分页契约 `data={items,total,page,page_size}`，补分类、范围、级别、启用状态、系统、数据连接筛选。
2. 过渡期前端兼容数组和分页两种返回，生产发布后删除兼容分支。
3. 失败时显示错误原因和关联编号，禁止空 `catch` 把接口错误伪装成“暂无规则”。
4. 增加 185 条基线契约测试，验证分页总数、过滤和字段完整性。

### 4.2 数据质量：总览和看板失真的根因

1. `/quality/summary/by-system` 返回 `findings_total/findings_open`，前端读取 `total_findings/open_count/resolved_count/critical_count`。
2. 后端把全局问题总数复制给每个系统，并不是真实系统归属。
3. `/quality/metrics` 返回的 `rule_categories` 是对象（`cat_counts` dict），前端按数组调用 `.length` 显示为空，且 `quality/index.vue` 的 `ruleCategoryChartOption` 对该对象直接调用 `.map` 会抛 `TypeError`，导致分类饼图整块渲染失败。
4. 前端硬编码 `system_code=DATA_CENTER`，而启用规则和大量历史问题的 `system_code` 为空，导致图表空。
5. “通过率”实际是已解决问题数/总问题数，不是规则通过率，名称误导。
6. 最近运行的 `total_findings` 只统计本批新增问题；历史问题被去重更新后显示 0，使用户误以为本次无问题。
7. 规则恢复正常时，旧问题没有按本次结果自动关闭，导致 10,439 条问题长期堆积为 open。

整改：建立统一统计语义：

- `rules_pass_rate`：本批无问题规则数/执行规则数；
- `current_open_findings`：当前仍存在的问题；
- `new_findings`、`reopened_findings`、`auto_resolved_findings`：本批变化；
- `resolution_rate`：已解决/已进入闭环的问题；
- `records_error_rate`：SQL 规则异常记录/扫描记录；
- 每个问题持久化真实 `system_code/source_code/schema/table/column`，无法归属时单独列“待归属”，不得复制到所有系统。

### 4.3 数据质量：自动生成 SQL 规则当前不能直接启用

当前执行器只可靠识别单行统计结果中的 `TOTAL_CNT` 和 `ERROR_CNT`。自动生成的主键唯一性 SQL 返回多行重复键，孤儿 SQL只返回 `ORPHAN_CNT`。执行器会把返回行数或单行结果误当总数和错误数，可能产生错误率和误报。

整改后的 SQL 规则契约固定为：

```sql
SELECT total_cnt AS TOTAL_CNT,
       error_cnt AS ERROR_CNT
FROM (...受限统计...)
```

- 主统计 SQL 必须只返回一行；
- 样本 SQL 与统计 SQL 分离，样本严格限行并脱敏；
- 每条规则明确方言、超时、最大扫描范围、时间窗口和大表保护；
- SQL 执行失败记录为 `rule_error`，不得按“0 问题通过”处理；
- `HIS.LAB_RESULT`、`INP_BILL_DETAIL` 等大表禁止无界全表聚合。

### 4.4 资产总览四张图为空

`frontend/src/views/asset/overview/index.vue` 一次并发请求关系图和表清单，其中表清单传 `page_size=1000`，但后端最大值是 200，必然返回 422。因为四张图共用一个 `Promise.all` 和统一异常处理，一处失败会把四张图全部清空。

即使修正 422，当前实现仍不可靠：

- 业务域只统计单页表，不是 7,766 张全量；
- 关系图最多 500 条，而平台有 537 条，未检查截断状态；
- 新图谱边的 `source/target` 是物理键，不能再用 `split('.')` 推断数据库分区；
- 核心表图会显示物理键而非中文表名；
- 四张图失败时没有单独错误态。

整改：由后端提供一次完整聚合接口，返回全量业务域、验证状态、数据库分区关系数和表关系度；前端不再下载大量明细后自行聚合。每张图独立加载、空态和错误态。

页面中文统一为：

- “数据库分区关系数 Top 10”；
- 说明提示“Oracle 对应 Owner，其他数据库对应数据库/架构或命名空间”；
- 技术详情可显示 `Owner/Schema`，主标题不再只写 `Schema`；
- “核心表 Top 10”增加说明“按已治理关系数量排序，不等同于业务重要性认定”。

### 4.5 关系图谱只有蓝色方块

生产当前使用 121 号 G8 发布包。只读检查生产验收截图和 G6 5.1.1 代码后确认：

- G6 基础节点的默认 `labelPlacement` 是 `bottom`；
- 当前节点文字颜色按深蓝底设置为白色；
- 未显式设置标签位置后，白色文字被画在节点下方的浅色画布上，几乎不可见；
- 默认资产概览只展示 10 个业务系统聚合节点，未明确提示用户还要继续下钻到数据连接、数据库分区和表。

整改：

1. G6 节点显式设置 `labelPlacement='center'`、垂直居中和稳定换行，文字必须在节点内部。
2. 系统聚合节点显示“系统中文名 + 表数量”；表节点显示“中文表名 + 技术表名”。
3. 节点可点击状态、下钻动作和面包屑必须清楚；无关系的聚合层优先用层级卡片/树式布局，不强行模拟关系散点图。
4. 增加“一键查看表资产”或对象层入口，用户不必猜测蓝色块用途。
5. 重新打开 121 的用户视觉验收。Canvas 存在、API 200、控制台无错误不能替代“名称可读”。
6. 1440×900 验收必须完成系统→数据连接→数据库分区→表下钻，并在截图中能直接读出至少 10 个表名。

### 4.6 关系复核中心按钮和数据模型接错

仓库已明确 `asset_relation_reviews` 是关系复核主表，但当前页面调用 `/api/v1/relations/list`，直接查询和修改 `asset_relations`。因此：

- 3 条真正的 draft 草稿不会出现在正确的待复核队列；
- “待复核/已确认/已拒绝”按正式关系 `validation_status` 拼装，不是复核状态；
- 批准/驳回直接改正式关系，绕过复核主表；
- 字段映射前端传 `rel_id`，后端接口不接受该参数（FastAPI 默认静默忽略未知查询参数，不返回 422），返回的是分页对象 `{total,page,page_size,items}`，前端却执行 `res.data || []` 把整个分页对象塞给表格。

整改：

1. 新增或改接真正的 relation-review API，列表、计数、详情和操作都以 `asset_relation_reviews.review_status` 为准。
2. 草稿批准时先做端点别名归一和稳定键查重：已有同语义 formal 关系（如 468/473）时链接该 formal，否则链接现有候选或创建正式关系，再写回 `source_relation_id`；禁止重复复制同一关系，禁止把不同命名口径的同语义关系重复提升为 formal。
3. 草稿拒绝保留证据和审计，只改变复核状态；不得物理删除。
4. `asset_relations` 继续作为图谱正式/候选关系资产，`asset_relation_reviews` 作为工作流事实源，两者通过稳定业务键和 `source_relation_id` 关联。
5. 顶部标签显示真实数量；切换、刷新、浏览器返回、分页和过滤均有契约测试。

### 4.7 关系配方库为空且难以使用

关系配方用于保存可复用的多表 JOIN、过滤、去重、适用范围、禁用口径和验证证据，供人员写 SQL 和 AI 获取上下文；它不是单条外键关系，也不是业务统计指标。

当前为空的直接原因和缺陷包括：

1. 已有 `view_relation_recipes.json` 种子，但导入脚本 `backend/scripts/import_relation_recipes.py` 使用 `parents[3]`，从 `backend/scripts/` 上溯三层会解析到仓库外的 `F:\python`，必然 `FileNotFoundError`；正确值为 `parents[2]`（仓库根 `F:\python\数据资产`）。
2. 导入只保存主表和 joins，丢失 `field_logic`、`hard_rules`、`validation_evidence`、禁止关联和 SQL 片段等关键内容。
3. 种子状态 `user_confirmed` 与代码状态机 `draft→submitted→approved→active` 不一致。
4. 种子 join 使用 `type/condition/from/to`，SQL 生成器读取 `join_type/on`，无法直接预览。
5. 前端只有原始 JSON 编辑，缺少表选择、关联选择、证据和状态流操作；API 有提交/批准/启用能力，页面没有对应按钮。

整改：先修导入、结构转换、哈希、幂等和 dry-run，再导入 53 号已经有用户确认依据的检查/影像报告配方。其他住院、检验、检查、手术配方先作为 candidate，不得仅凭同名字段自动 active。

### 4.8 AI 协作“无法使用”

当前页面本质上是 AI 接入管理和审计页，不是聊天机器人。但页面没有解释这一点，也没有提供创建会话、导出上下文、提交 SQL、风险扫描或只读试运行入口。

此外存在真实实现缺陷：

- 系统上下文 API 未返回前端使用的 `total_columns/total_relations`；
- 系统下拉只显示英文编码；
- `/ai/tool-execute` 只写一条审计并返回 `executed=true`，并没有调用目标工具，属于虚假成功；
- 工具策略写“所有工具只读元数据”，列表却包含审核后执行 SQL，文案矛盾；
- 会话、调用、草稿均为 0，页面没有首用引导。

### 4.9 治理管理用途不清楚

当前页面把 API Token、表负责人、业务术语和元数据快照放在一起，且负责人/术语均为 0。主要问题：

- 没有首页说明、覆盖率或初始化引导；
- 表负责人用自由文本 `SCHEMA.TABLE`，无法区分不同系统/连接中的同名表；

- “查看变更事件”和“元数据变更检测”两个按钮跳到同一路径；
- 快照管理和元数据变更模块重复。

整改定位：菜单改为“治理基础配置”，页面分为：

1. **责任归属**：负责人、责任科室、联系方式、覆盖率；绑定 `asset_table_id/physical_key`，保留旧 `full_table_name` 兼容。
