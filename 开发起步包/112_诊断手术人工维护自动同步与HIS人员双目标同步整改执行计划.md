诊断/手术的目标流程必须是“人工维护并审核后触发”，不能实现为夜间 cron：

```text
人工新增/单字段停用 → 校验 → 审核通过 → 生成不可篡改计划
→ HIS/JHEMR 分别只读预检 → 事件/队列自动触发
→ 两个目标分别事务执行 → 回读核对 → 成功/冲突/补偿/审计
```

## 2. 执行总原则

1. 先在隔离测试库和目标测试库复核，再改代码；生产环境、业务源库保持 DML/DDL 为 0。
2. 客户端只能提交业务字段和计划 ID，服务端根据平台数据生成 SQL/action；禁止客户端传 SQL、表名、连接串或 action。
3. HIS 与 JHEMR 不是跨库原子事务，必须分别提交、分别回读、分别记录状态；一方失败不得伪报整体成功。
4. 自动同步只允许审核通过事件触发；采用平台数据库持久化 outbox/任务表和独立 worker。外部 Oracle/Vastbase 写入不得放在 HTTP 请求中阻塞执行，也不得仅依赖 FastAPI `BackgroundTasks` 或裸线程，因为它们无法保证进程重启后的任务恢复。禁止用夜间任务代替即时触发。
5. 用户提供的 HIS/JHEMR 写账号不写代码、文档、日志或 Git，只能引用受控 secret 文件；生产写开关默认关闭。

## 3. A 线：诊断/手术审核后自动同步

### A0 业务口径与触发点

- 明确保存草稿不触发；只有审核通过的新增或停用变更触发。
- 单条维护立即生成事件；批量导入在整批审核通过后生成批次事件，事件包含操作者、审核者、版本和内容哈希。
- 审核事务内同时写入持久化 outbox，提交成功后由独立 worker 领取；使用 `SELECT ... FOR UPDATE SKIP LOCKED` 或平台 PostgreSQL 等价机制实现并发领取，记录租约、尝试次数、下次重试时间和死信状态。审核事务回滚时不得残留同步任务。
- 状态至少包含：`draft`、`approved`、`precheck`、`planned`、`executing_his`、`his_succeeded`/`his_failed`/`his_conflict`、`executing_jhemr`、`jhemr_succeeded`/`jhemr_failed`/`jhemr_conflict`、`reconcile_required`、`completed`。

### A1 计划与安全策略

- 计划由服务端生成并保存哈希；目标固定为 `HIS_SOURCE`、`JHEMR_VASTBASE`，不接受任意目标。
- 本期只允许“新增”和“单字段停用”；禁止覆盖名称、国临编码、医保编码等既有业务字段，冲突进入人工处理。
- 执行前做目标只读预检：编码、名称、国临/医保字段、停用状态、目标版本和权限；冲突分类为编码冲突、名称冲突、字段不一致、已停用、目标不可达。
- 诊断对应 JHEMR 多表时必须封装为一个目标内事务包；手术主表/字典表关联需按活库结构确认后再落 action。
- HIS 两张字典表实测无 PK/UK 且已有重复编码。预检必须返回同编码全部候选的聚合差异；多行、名称/国临/医保/停用状态不一致一律标记 conflict。上线前由业务/DBA 裁决重复编码是否合法，并选择数据库唯一约束、受控应用锁或其他可防人工维护并发的方案。
- JHEMR `serial_no` 实测无 default、无数据库关联 sequence，仅有唯一索引；用户确认不要求与表建立 default/关联。运行期仍不得使用 `MAX(serial_no)+1`，必须由 DBA 指定一个并发安全取号来源（可为独立 sequence 或已批准的等价 allocator），并证明能抵御平台 worker 与目标系统人工维护的跨进程并发。AI 不创建 sequence、不执行目标库 DDL。

### A2 执行、幂等与补偿

- 不重新实现底层写连接器：复用并加固现有 `medical_code_push.py::apply_one_action` 和 `_execute_write_sql` 的 `push_enabled`、write policy、confirmation token、credential 与 commit/rollback 门禁。核心改动是新增正式非 deprecated 执行入口，并把已审批计划/outbox worker 安全连接到既有 service；不得简单删除 `forced_mode="dry_run"` 后裸露原 API。
- 每个目标独立事务；同一计划重复执行按计划哈希和业务键幂等，禁止重复插入。
- 超时采用有限重试和指数退避；区分可重试网络错误与不可重试数据冲突。
- 部分成功必须进入 `reconcile_required`，提供重试、补偿或人工确认，不允许自动反向覆盖已成功目标。
- 执行后按业务键回读 HIS/JHEMR，核对关键字段和停用状态；回读失败不得标记成功。
- 记录审计：计划、版本、目标、结果、计数、冲突代码、correlation ID；密码/连接串/患者信息严格脱敏。

### A3 权限、开关与验收

- 维护、审核、执行、重试、冲突处理分离授权；维护者不得自审，执行接口需动作级权限。
- 写策略、专用账号、目标绑定、超时和熔断均配置化；当前平台 HIS/JHEMR 数据源的 `write_policy` 都是 readonly 且没有 `write_credential_ref`，必须先通过受控凭据流程登记为字典专用写通道。不得静默复用身份账号；如用户明确要求同账号复用，仍需在配置中分开 credential ref、权限用途和审计域。生产 `APP_DICT_MEDICAL_PUSH_ENABLED=false`。
- 测试库完成新增、重复执行、停用、字段冲突、目标不可达、JHEMR 多表回滚、HIS 成功/JHEMR 失败补偿等用例。
- 验收证据必须包含：两目标 DML 计数、提交/回滚结果、回读结果、审计脱敏样例、并发 `serial_no` 测试和全链路状态迁移。
