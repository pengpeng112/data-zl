## 4. 视图关系分析规则

### 4.1 必采信息

每个视图至少记录：物理来源、数据库、schema、视图名、对象 ID（如有）、创建/修改时间（如有）、定义可见状态、规范化定义 SHA-256、依赖对象、是否跨库、是否 `UNION`、是否聚合/窗口/去重、是否可更新、解析器版本、解析状态与错误。

同时解析：

- ANSI `JOIN ... ON`、逗号连接加 `WHERE`、相关子查询、CTE、派生表和各 `UNION` 分支；
- 单列键、组合键、常量过滤、日期窗口、状态/非空限定、类型转换、函数包裹、`CASE` 和去重逻辑；
- SQL Server 三/四段名和同义词、MySQL 库名限定、动态 SQL 或无法静态解析部分；
- 视图到表/视图的静态依赖，以及视图中显式 JOIN 所表达的候选关系。

### 4.2 三种对象不得混淆

| 层 | 含义 | 允许的落库状态 |
|---|---|---|
| 静态依赖 | 视图/模块引用了某表或视图，只表示“使用” | 确定性依赖/lineage edge；不得伪称业务主外键 |
| 业务关系候选 | JOIN 条件可能表达业务键关系 | `asset_relation_reviews` 的 `draft`、`existing`、`partial`、`candidate` 或 `rejected` |
| 关系配方 | 多表、过滤、转换、聚合、UNION 等复合逻辑 | `asset_relation_recipes` 的 inactive draft；不得在本轮激活 |

数据库显式声明且元数据完整的 PK/FK 可以按 `db_constraint` 证据幂等导入结构关系；视图 JOIN、同名字段和单纯依赖不能自动升正式。已有正式关系必须做同向/反向、列序和组合键查重；匹配时只追加脱敏证据，不覆盖人工说明、状态或验证指标。

### 4.3 每条候选的最小字段

`source_sql_sha256`、`source_file`、`system_code`、`dialect`、来源/目标数据库、schema、表和列、完整 `join_condition`、组合键顺序、限定条件、来源视图、已有关系 ID、`intake_status`、置信度、元数据证据、验证证据、风险说明、解析器版本、审核建议。

候选分类固定使用：`existing`、`candidate`、`partial`、`recipe_candidate`、`rejected`。跨系统候选在没有共同强键和限量验证前一律标 `cross_system_pending`，不得自动画成正式连线。

### 4.4 只读验证

默认只做元数据和静态解析，不执行视图本身。只有在查询计划可控、存在索引/明确键、不会扫大表且不返回患者行时，才允许执行限量聚合验证：

- 只允许 `SELECT`/只读 CTE；只返回计数、空值率、去重数、匹配数和命中率。
- 每项最多抽取/聚合 10,000 个去重键，设置连接、语句、锁等待超时；SQL Server 使用只读事务语义，MySQL 使用只读会话。
- 不输出姓名、身份证、电话、地址、病历号等值；报告只保存聚合指标和 SQL 指纹。
- 预估会全扫大表、缺少过滤键、锁等待、超时或权限不足时记 `VALIDATION_TIMEOUT`/`VALIDATION_SKIPPED_RISK`，继续后续对象。
