## 5. 生产发布步骤

1. 冻结 release tag，确认发布单、门禁和审批已签收。
2. 传输发布包至服务器临时目录，通过受管 SSH 经跳板机传递；两端执行 `sha256sum -c SHA256SUMS`。
3. 在 `/opt/data-asset/releases/<release-tag>/` 解压，禁止覆盖当前版本目录。
4. DBA 备份平台库，发布工程师记录当前 Alembic revision；执行新版本 `alembic upgrade head`。
5. 安装新版本依赖和前端静态文件；先以候选进程完成本机 readiness 检查。
6. 原子切换 `/opt/data-asset/current` 软链接至新版本；systemd 的 WorkingDirectory 和 Nginx 静态目录应引用该软链接或共享的版本化路径。
7. 重启服务并校验：`systemctl status data-asset`、`curl --fail` readiness、Nginx API、浏览器登录、管理员授权、只读探查抽检。
8. 观察一个业务窗口；保留上一版本、数据库备份和发布证据后再清理旧版本。

## 6. 回滚

1. 停止新版本服务，记录故障时间、错误日志和当前 Alembic revision。
2. 将 `current` 软链接切回上一已验证 release，重启 systemd 与 Nginx，并复测 readiness 和关键页面。
3. 数据库回滚优先恢复迁移前备份。仅当迁移已验证可逆、没有新平台数据写入且已获得 DBA 批准时，才执行 Alembic downgrade。
4. 不在故障现场直接覆盖发布目录，不删除日志或备份；根因修复后必须重新生成 release tag 和离线包。

## 7. 后续本地代码同步策略

**生产服务器不是开发协作节点，不允许直接 `git pull`、直接同步开发工作目录或在服务器修改源码。**

| 环节 | 做法 | 禁止项 |
|---|---|---|
| 开发协作 | 开发机分支开发、代码审查、通过测试后合并；仅 clean Git 提交可进入 release tag | 将 `.env`、密钥、`node_modules`、虚拟环境、缓存、日志提交或打包。 |
| 发布构建 | Linux 构建机检出指定 release SHA，构建不可变离线包并生成 SHA-256 清单 | 从带未提交改动的工作目录打包。 |
| 内网传输 | 受管 SSH/SCP 经跳板机传输单一发布包，双端校验哈希 | 生产服务器直接访问 GitHub，或把整个仓库 rsync 到生产目录。 |
| 服务器部署 | 解压到新 release 目录，迁移和验证后原子切换 `current` | 覆盖运行中的版本目录。 |
