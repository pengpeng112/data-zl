## 2. 计划根因是否成立（源码核实）

计划 §3.1 根因**基本成立**，当前代码仍可复现。

### 2.1 后端仍有「系统大类」与「其他业务系统」

文件：`backend/app/api/v1/systems.py`

- `_CATEGORY_CN` 仍含：
  - `ods_center` → 「ODS 数据中心系统」
  - `his_source` → 「HIS 源端系统」
  - **`external_business` → 「其他业务系统」**
  - `platform_asset` → 「平台元数据系统」
- `_classify_asset_source()`：
  - `physical_connection` 且非 `DATA_CENTER` / `HIS_SOURCE` / `HRP` 时，统一落入 **`external_business`**（Docare、JHEMR、LIS_SOURCE、PACS_SOURCE 等均会进「其他」）。
  - 遗留分支仍把 `MOBILE_NURSING`、旧 `LIS`/`PACS`/`SM` 等归到**数据中心 Owner** 语义，易与独立源端混淆。

与 90「十个一级平行系统、禁止其他业务系统」**直接冲突**。

### 2.2 前端表资产仍硬编码大类

| 文件 | 问题 |
|---|---|
| `frontend/src/views/asset/tables/hierarchy.ts` | `CATEGORY_ORDER` 含 `external_business`；中文标签硬编码 |
| `frontend/src/views/asset/tables/index.vue` | `categoryLabelOf` 把 `LIS/PACS/EMR/MOBILE_NURSING/SM` 打成「其他业务系统」；**未识别** `LIS_SOURCE` / `PACS_SOURCE` / `DOCARE` / `JHEMR_VASTBASE` 等 |

### 2.3 名称多源，未做到「只读 system_name_cn」

| 入口 | 现状 |
|---|---|
| 系统总览 | 相对较好，使用 `system_name_cn` |
| 资源树 / 表资产 | 大量使用 `system_category_cn`、`source_system_cn`、前端常量 |
| 后端分类 | 内置中文常量，**改总览名称不会全局联动** |

### 2.4 导入链路无「确认空表不入库」

`backend/scripts/import_explored_sources_to_platform.py` → `replace_assets()`：

- 对快照中表**全量写入**；
- `row_count` 仅写入 `row_count_stats`，**不据此过滤**；
- 字段、关系无「端点表是否保留」门禁；
- 实现为按 source **先 DELETE 再插入**，与「幂等 upsert」目标不一致，中断可能空窗。

HRP / HIS / 归一包导入同样缺少统一 `row_presence` 状态机。

### 2.5 空表判定风险

采集侧使用 Oracle `NUM_ROWS`、SQL Server/MySQL 统计行数。
90 要求「统计预筛 + 只读 LIMIT 1 + 禁止把超时当 0」——**代码侧尚未实现**。若简化为 `row_count==0` 即删，存在误伤风险。

## 4. 计划自身需改进（开发前裁决）

### A. 口径与历史计划冲突（高）

1. **与 74/76「按真实 IP 归并为 HIS/HRP/数据中心」冲突**
   - 76：ODS 内 LIS/PACS/… 为 Owner，连接去重到 `ods_8_216`
   - 90：独立 `LIS_SOURCE` / `PACS_SOURCE` / `DOCARE` / … **一级平行**
   → 须书面裁定：数据中心**镜像** Owner 与**独立源端**如何并存。

2. **system_code 双轨**
   - 库/旧逻辑：`LIS`、`PACS`、`SM`、`EMR`、`HIS`
   - 90/导入脚本：`LIS_SOURCE`、`PACS_SOURCE`、`DOCARE`、`HIS_SOURCE`、`JHEMR_VASTBASE`
   → 需要权威编码表 + 旧码 `merged` 策略。

3. **名称「HIS」vs 库内「HIS 源端」**
   → 明确导入是否覆盖人工改名、总览改名后全局生效规则。

### B. 数据与迁移前置（高）

4. 平台库版本落后 → **先 alembic upgrade 再导入**。
5. 脏数据：空 `system_code`、`pytest_*` 源 → 写入清理规则。
6. 表有 `DATA_CENTER`、连接缺失 → 先做引用完整性清单。
7. 锁定权威库（8.83 生产 vs `10.20.1.153`），禁止对着错误库 apply。

### C. 展示与 API（中高）

8. 树契约：现「大类 + source_system」→ 90「系统 → 连接 → Schema → 表」；兼容字段策略要写清。
9. 前后端分类改造必须同步，只改一端会更乱。
10. 图谱/关系复核的名称解析入口需点名纳入改造。
11. 「总览改名自动同步」需契约测试（只改 DB 名即可反映）。

### D. 空表治理（高，易做错）

12. 禁止仅凭统计 0 删除；补：超时默认、并发、大表名单（含 `HIS.LAB_RESULT`）、`unknown/blocked` UI。
13. 历史已入库 zeroish（本库 397）是否清理、是否审批。
14. 视图默认 `unknown` 或白名单，避免 LIMIT 1 打重视图。
15. 关系一端 empty 时删/候选，对齐 40 号 A/B/C/D。
16. HRP 是 keep 67 还是扩大范围，与「全量探库导入」表述对齐。

### E. 导入与幂等（中高）

17. `replace_assets` 删除再插 → 改为 upsert 或明确整源替换风险。
18. 稳定键 `(system, source, db, schema, object)` 与历史 schema+table 唯一性冲突。
19. `backfill_catalog_display_names.py` 硬编码名称 + token 猜名，与「禁止第二套硬编码」冲突。
20. 多脚本统一空表门禁与编排顺序（explored / 归一 / JHEMR / HRP）。

### F. 安全与运维（中）

21. 无凭据源不得把 0 当空；dry-run 强制列出不可核验源。
22. 探测窗口、超时、并发需量化。
23. 平台备份 / head / 禁止生产 downgrade 与 85 封板挂钩。

### G. 测试与协作（中）

24. 90 所列专项测试尚未落地。
25. 全量 pytest 仍受测试库缺失阻塞（见 85）。
26. 与 85 F1–F11 的优先级在 55 中写清，避免多 AI 并行改同一文件。
27. 82 文件名通配；89 与 90 的「报告 vs 执行计划」分工写清。
