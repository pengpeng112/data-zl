### 2.2 中文名不是缺数据，而是 API 富化失败

但默认图谱响应中 127 个节点的 `table_name_cn` 全为空。已定位到以下契约错位：

1. `asset_relations.from_namespace_name/to_namespace_name` 的既有关系多为 `NULL`；
2. 对应 `asset_tables.namespace_name` 多保存为与 `schema_name` 相同的值，例如 `HIS`；
3. `backend/app/api/v1/graph.py::_table_map_by_physical_key()` 查询时允许 `NULL/空/schema` 的宽松 namespace，却在建立返回字典时重新使用表资产的真实 namespace；
4. 边端点键仍使用关系行的空 namespace，导致 `table_map.get(edge.source)` 永远匹配不到；
5. 因此中文名、业务域、表角色、纳入状态、字段数等已有资产信息都没有富化到节点。

这是本轮 P0 根因，必须先修后改视觉。禁止用前端硬编码中文名或仅放大字体掩盖。

## 3. 目标产品模型

### 3.1 只保留三个用户任务模式

用三个互斥模式替代当前七个并列标签和独立 `group_by` 组合：

| 模式 | 用户问题 | 默认节点层级 | 允许的核心操作 | 不应出现的操作 |
|---|---|---|---|---|
| 资产概览 | 系统之间、库之间大致有什么关系？ | 系统 → 数据源 → Schema/Owner 的聚合节点 | 下钻、返回上级、按业务域着色 | 上游/下游、1跳/2跳、技术 limit |
| 关系探索 | 某一张表与哪些表有关？ | 选定中心表后的表级节点 | 双向/引用它/它引用、1跳/2跳、关系详情 | 全局 127 表默认展开 |
| 证据审核 | 哪些关系已验证、待验证或需拆分？ | 表级或关系列表 | 等级、验证状态、候选/依赖、证据抽屉 | 与普通浏览混在同一默认视图 |

旧 `system/domain/schema/table/lineage/deferred/review` code 如已有外部链接依赖，可在 API 保留兼容映射，但新 UI 不再把它们作为七个平级入口。

### 3.2 明确物理层级与业务维度

物理层级固定为：

```text
一级业务系统
  └─ 数据源/数据库连接
       └─ Schema / Owner / 数据库命名空间
            └─ 表或视图
                 └─ 字段（仅详情抽屉，不默认铺在主图）
```

“业务域”是横向分类，不是物理层级。界面不得继续把系统、数据源、表空间、业务域做成四个互不相关的同级查询框。统一用以下术语：

- 系统：中文 `system_name_cn` 为主，`system_code` 为辅；
- 数据源：中文连接名称/数据库名为主，`source_code` 为辅；
- 命名空间：统一显示“Schema / Owner”，不要只写“表空间”；
- 表：中文表名为主，技术名为辅；
- 业务域：作为筛选、着色或泳道维度。

### 3.3 知识图谱式探索流程

默认进入“资产概览”，首屏只显示 10 个左右一级系统节点及系统间关系数量，不显示 127 张表。

用户典型路径：

1. 点击“数据中心”；
2. 展开其 6 个数据源；
3. 点击 `ods_8_216`；
4. 展开 HIS、CDA、ODS、MTL、JHEMR、YDHL、SM 等 Schema/Owner；
5. 进入某 Schema 后搜索或选择中心表；
6. 切到“关系探索”，默认显示中心表一跳双向关系；
7. 点击节点查看中文名、技术名、系统、数据源、Schema、业务域、主键、字段数；
8. 点击边查看字段映射、基数、置信度、验证等级、验证状态和证据；
9. 需要时再展开二跳，且只扩展当前选中节点，不一次性替换成全局二跳毛线团。

### 3.4 节点视觉规范

| 节点类型 | 形状建议 | 主标签 | 副标签 | 补充信息 |
|---|---|---|---|---|
| 系统 | 大圆角卡片或圆形 | 中文系统名 | system_code | 数据源数/表数 |
| 数据源 | 胶囊或圆角卡片 | 中文连接/数据库名 | source_code | Schema 数 |
| Schema/Owner | 圆角矩形 | Schema/Owner | 所属数据源 | 表数 |
| 业务域 | 椭圆 | 中文业务域 | 所属系统 | 表数/关系数 |
| 表/视图 | 双行圆角卡片，禁止统一小方块 | 中文表名 | `SCHEMA.TABLE` | 角色/状态角标 |
| 中心表 | 加粗描边和中心标记 | 中文表名 | 技术名 | 固定在画布中心 |

硬性要求：

- 主标签永远是字符串；优先中文名，其次技术表名；
- 表节点至少支持两行，不能简单截成 16 个字符后无提示；
- 完整名称必须可通过 tooltip、详情抽屉和键盘焦点查看；
- 画布节点超过可读阈值时应聚合或提示继续筛选，不得继续缩小到文字不可辨认；
- 1440×900 首屏默认缩放下，所有一级节点名称必须肉眼可读；
- 颜色表示节点类型或业务域，边颜色表示关系证据；两套颜色语义不得混用。

### 3.5 边与方向规范

边默认只画线和箭头；字段映射仅在 hover、选中或证据抽屉显示，避免全量文字叠加。

方向文案按关系语义区分：

- 普通表关联：`全部方向 / 引用它 / 它引用`；
- 已确认数据血缘或视图依赖：`上下游 / 上游 / 下游`；
- 无方向证据的候选关系：只允许“关联”，不得伪装为血缘；
- tooltip 必须解释箭头：`from_table.from_columns → to_table.to_columns`；
- 1 跳/2 跳只在已选中心物理表后启用；默认 1 跳；
- 2 跳显示按 hop 分层或同心环，必须提供“收起二跳”；
- 点击某个邻居时允许“设为中心”，而不是要求重新输入表名。

### 3.6 筛选与搜索规范

主筛选采用级联状态：

```text
system_code 变化
  → 清空 source_code/schema/physical_key
  → 重新加载该系统的数据源和 Schema

source_code 变化
  → 清空 schema/physical_key
  → 重新加载该数据源的 Schema 和表

schema 变化
  → 清空 physical_key
  → 限定中心表搜索范围
```

业务域可以跨物理层级筛选，但选项必须受当前系统/数据源范围约束，并显示命中数量。表搜索结果必须返回并展示：

- 中文表名；
- `SCHEMA.TABLE`；
- 系统中文名；
- source_code/数据源名；
- `physical_key`；
- 业务域；
- 是否存在正式关系及关系数。

如果同名表有多个物理来源，必须弹出选择列表，禁止静默选第一条。

## 4. 目标 API 契约

### 4.1 保留兼容端点

以下路径保持不变，避免破坏现有前端链接：

- `GET /api/v1/graph`
- `GET /api/v1/graph/neighbors`
- `GET /api/v1/graph/options`
- `GET /api/v1/graph/edges/{edge_id}`
- `GET /api/v1/graph/diagnostics`

可以增加字段或新增端点，但不得删除既有字段。旧请求在迁移期继续返回兼容结果。

### 4.2 P0 修复节点富化

在 `graph.py` 中引入单一 canonical endpoint 规则：

1. 物理身份仍以 `system|source|namespace|schema|table` 为权威；
2. 仅用于查找表资产元数据时，把 `namespace=NULL/空/与 schema 相同` 视为同一兼容组；
3. 查找必须同时限定 system、source、schema、table；
4. 同一兼容组出现多条资产时返回诊断错误，不允许 `LIMIT 1` 猜测；
5. 不直接批量改写既有正式关系，除非另有迁移、备份、对账和用户授权；
6. 节点返回 `table_name_cn/domain/table_role/include_status/column_count` 的完整率必须进入 diagnostics。

建议新增独立函数：

```python
canonical_namespace(namespace_name, schema_name)
table_metadata_key(system_code, source_code, schema_name, table_name)
resolve_table_metadata_for_endpoint(...)
```

关系物理键和表元数据查找键不得再混用同一个字典键。

### 4.3 新增服务端概览聚合

建议新增：

```text
GET /api/v1/graph/overview
  level=system|source|schema|domain
  parent_system_code=
  parent_source_code=
  parent_schema=
  domain=
  confidence=A
  validation_status=
```

返回聚合节点和聚合边：

```json
{
  "nodes": [{
    "id": "system:DATA_CENTER",
    "type": "system",
    "label": "数据中心",
    "technical_label": "DATA_CENTER",
    "table_count": 865,
    "relation_count": 192,
    "child_count": 6
  }],
  "edges": [{
    "source": "system:DATA_CENTER",
    "target": "system:HIS_SOURCE",
    "relation_count": 12,
    "verified_count": 10,
    "candidate_count": 2
  }],
  "meta": {
    "aggregation_level": "system",
    "matched_relations": 537,
    "returned_nodes": 10,
    "is_complete": true
  }
}
```

聚合必须在数据库完整匹配集上完成，然后才限制聚合节点数量；禁止复用“先取前 120 条边再在浏览器聚合”的算法。

### 4.4 新增级联选项与中心表搜索

优先扩展现有 `/options`，或新增：

```text
GET /api/v1/graph/filter-options?system_code=&source_code=&schema=&domain=
GET /api/v1/graph/tables/search?q=&system_code=&source_code=&schema=&domain=&limit=20
```

选项由纯字符串改为至少包含：

```json
{"value": "ods_8_216", "label": "数据中心主库（ods_8_216）", "count": 865}
```

中心表搜索必须返回完整 `physical_key`。新前端调用 `/neighbors` 时优先只传 `physical_key`，不再用自由文本 `table` 作为正常路径。

### 4.5 邻居图响应补充

邻居响应增加：

- `center_physical_key`；
- 节点 `hop=0|1|2`；
- 边 `direction_relative_to_center=in|out|cross`；
- `edge_semantic=relation|lineage|dependency|candidate`；
- `meta.direction_semantics`；
- `meta.truncated_by_hop`；
