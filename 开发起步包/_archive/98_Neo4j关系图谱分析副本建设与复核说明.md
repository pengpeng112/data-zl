# 98 Neo4j 关系图谱分析副本建设与复核说明

## 1. 供复核 AI 快速判断的结论

建议把 Neo4j 定位为**可选的只读分析副本**，而不是当前关系治理库的替代品。

当前不应直接部署上线，先完成 97 号计划中的关系图谱 P0 治理，再进行资源评估和最小验证。原因如下：

1. 生产平台当前约有 537 条关系，数据量本身没有逼迫系统迁移到图数据库；
2. 当前空图、错乱和图片无法显示的主要原因是筛选契约、节点唯一键、重复边和前端渲染问题，不是 PostgreSQL 查询容量问题；
3. Neo4j 的主要收益是多跳路径、最短路径、影响范围、环路和跨系统关系探索；
4. 未治理的错误关系同步到 Neo4j 后仍然是错误关系，不能因图形展示更直观就视为可信；
5. 新增 Neo4j 会带来同步一致性、备份恢复、权限、监控和故障处置成本。

因此建议决策为：

```text
先治理关系资产
    ↓
完成 Neo4j 最小验证（PoC）
    ↓
收益和资源达到门槛
    ↓
批准部署只读分析副本
```

## 2. 当前事实基线

- 生产服务器 `10.10.8.83` 没有 Neo4j 容器、systemd 服务或 Neo4j 实际进程；
- Neo4j 常用端口 `7473`、`7474`、`7687` 未监听；
- `01_平台执行方案.md` 将 Neo4j 定位为第二阶段可选增强，第一版使用 PostgreSQL 关系边表；
- 正式关系、候选关系、审核状态和治理过程目前保存在 PostgreSQL；
- 97 号计划已修复部分图谱筛选和渲染问题，但生产发布、物理端点唯一化及关系分层仍需完成。

## 3. 目标与非目标

### 3.1 目标

Neo4j 首期只承载以下分析能力：

1. 表级上下游 1～10 跳查询；
2. 两张表或两个系统之间的最短关联路径；
3. 删除、修改或停用表后的影响范围分析；
4. 循环依赖、孤立节点、高中心度节点检测；
5. HIS、ODS、JHEMR、LIS、PACS 等系统间关系探索；
6. 为前端“分析视图”提供图查询结果。

### 3.2 非目标

首期明确不做：

- 不取代 PostgreSQL 的关系审核、版本、备注和证据管理；
- 不允许用户、AI 或同步程序直接在 Neo4j 审核正式关系；
- 不从 Neo4j 反向覆盖 PostgreSQL；
- 不把候选关系伪装为正式关系；
- 不在第一期同步患者级业务数据或敏感数据；
- 不为了使用 Neo4j 而重写全部现有图谱页面。

## 4. 推荐架构

```text
元数据采集 / SQL 关系摄取 / 人工审核
                  ↓
PostgreSQL（唯一事实源）
表、字段、正式关系、候选关系、证据、审核、版本
                  ↓
      受控同步任务（单向、可重放）
                  ↓
Neo4j（只读分析副本）
多跳、最短路径、影响分析、环路、中心度
                  ↓
后端图分析 API
                  ↓
前端分析视图
```

治理视图继续查询 PostgreSQL；分析视图才查询 Neo4j。Neo4j 不可用时，治理、审核和基础一跳图谱仍应正常工作。

## 5. 建议的数据模型

### 5.1 节点

首期节点类型：

- `System`
- `DataSource`
- `Schema`
- `Table`

字段级血缘在表级模型稳定后再增加 `Column`，避免第一期节点规模和同步逻辑过度膨胀。

表节点唯一键必须使用物理身份：

```text
system_code + source_id/source_code + schema_name + table_name
```

不能只使用 `schema.table`，否则同名镜像表、源库表和历史别名会错误合并。

**实施前提**：当前 `asset_relations` 只有 `from_table/to_table` 文本，没有端点
`system_code/source_code/schema_name`。上述唯一键必须以 97 G2 的手写 Alembic
迁移结果为准，迁移完成前本模型不可实施。G2 应新增独立的起止系统、数据源和
Schema 字段；`from_table/to_table` 中的 `SCHEMA.TABLE` 只能作为迁移回填输入，
不能继续作为物理身份真值。无法唯一映射的数据进入待审核队列，不得猜测归属。

### 5.2 关系

推荐关系类型：

- `BELONGS_TO_SOURCE`
- `BELONGS_TO_SCHEMA`
- `RELATES_TO`
- 后续可增加 `DEPENDS_ON`、`MAPS_TO`、`SYNCED_TO`

`RELATES_TO` 至少携带：

- `relation_id`：来自 PostgreSQL 的关系标识；
- `relation_scope`；
- `from_columns`、`to_columns`；
- `join_condition`；
- `cardinality`；
- `confidence`；
- `validation_status`；
- `review_status`；
- `evidence_type`；
- `source_updated_at`；
- `sync_batch_id`。

同一对表允许存在多条不同字段或不同业务含义的关系，不能仅按起止节点去重。

同步幂等键优先使用经过治理后稳定的 `relation_id`。当前导入流程可能重建行或令
数据库主键漂移，因此不能把自增 `id` 单独视为跨重建永久标识；发生标识漂移时由
全量重建兜底。S0 还需验证 `relation_id` 的唯一性与稳定性，必要时增加基于物理端点、
字段和关系语义计算的不可变业务键。

## 6. 同步策略

### 6.1 数据范围

PoC 建议分别测试两个图层：

1. **正式层**：仅同步人工确认或验证通过的关系；
2. **探索层**：同步候选/依赖关系，前端默认关闭。

不得把两层合并展示后统一标记为“已验证”。

首期裁决：使用统一关系类型配合强制的 `layer/scope/review_status` 属性隔离，
不为每个审核层复制一套关系类型。固定查询模板必须显式限定允许的层；跨层分析
只有具备相应权限且由用户主动选择时才开放。

### 6.2 同步方式

当前 `asset_relations` 没有 `created_at/updated_at`，不能按更新时间增量；
`asset_relation_reviews.updated_at` 也只有 `server_default=func.now()`，没有
应用层 `onupdate` 或数据库触发更新。故首期同步方案裁决为：

```text
可靠更新时间补齐后增量 upsert
        +
每日全量差集检测删除/停用/降级
        +
随时可从空库全量重建
```

具体约束：

- 全量任务可以从空库根据 PostgreSQL 重建全部图数据；
- S0 必须为正式关系补齐可靠 `created_at/updated_at`，使用手写 Alembic 迁移，
  并通过应用层 `onupdate` 或数据库机制保证每次更新刷新时间；
- 增量任务只承担 upsert，不声称可以发现物理删除；
- 每日全量差集负责发现删除、停用、降级和主键/业务键漂移，并移除陈旧图数据；
- 每批次记录数量、校验值、失败原因和批次号；
- 同一批次重复执行必须幂等；
- 同步失败不得影响 PostgreSQL 主业务。

首期不引入复杂 CDC 或 outbox；若未来同步时效要求提高，再单独评估。S0 必须在
测试库修改、删除、降级各一条关系，证明增量 upsert 与全量差集能覆盖三类变化，
且重复执行结果不变。

### 6.3 一致性校验

至少校验：

- PostgreSQL 与 Neo4j 的节点数、边数；
- 每个正式关系 ID 在 Neo4j 中恰好出现一次；
- 随机抽样的起点、终点、字段和状态一致；
- 停用或删除关系不会残留；
- 同步重跑前后数量和结果稳定；
- Neo4j 清空后可在规定时间内完整重建。

## 8. 建议的启用门槛

满足以下任一业务条件，才进入正式上线评估：

- 关系达到数万条以上；
- 高频使用 3～10 跳上下游或最短路径查询；
- 字段级血缘规模显著增长；
- 需要跨多个系统做持续影响分析；
- PostgreSQL 递归查询在约定数据规模和并发下不能达到 PoC 前确定的 P95 阈值。

PoC 启动前必须记录至少两周的查询频率基线，并由用户确认 P95 目标。建议初始
比较基线为：常用 1～5 跳、结果不超过 1000 节点的查询 P95 不高于 2 秒；该数字
只是待确认门槛，不得在没有真实并发和数据规模压测时当作既成 SLA。

即使未达到数量门槛，如果多跳分析是明确的高频核心功能，也可根据 PoC 的
正确性、P95、资源消耗和运维成本对照提前采用。

## 9. 验收标准

### 9.1 正确性

- 正式层节点、关系与 PostgreSQL 对账一致；
- 任一关系均能追溯到 PostgreSQL 关系 ID 和证据；
- 同名物理表不发生错误合并；
- 正式与候选关系视觉和 API 字段明确区分；
- 页面和 API 返回最近成功同步时间、同步批次和数据滞后/降级状态；
- 随机抽取至少 30 条路径，人工核对起止节点及关系方向。

### 9.2 性能

- 预设 1、3、5、10 跳场景分别压测；
- API 必须限制最大跳数、最大返回节点数和超时；
- 验收报告同时记录 PostgreSQL 与 Neo4j 对照数据，不预设 Neo4j 必然更快；
- 记录 P50/P95、查询频率、超时率、CPU 和内存，不只比较单次最快耗时；
- 前端大图交互不能因一次性返回无限节点而冻结。

### 9.3 可运维性

- 全量重建、增量同步、备份和恢复均完成演练；
- Neo4j 停止时 PostgreSQL 治理功能不受影响；
- 同步失败可告警、可重试、可定位批次；
- Community Edition PoC 接受单一数据库账号，但其所有用户具有隐含管理员权限，
  因而只能部署在隔离网络，由后端持有账号，前端和 AI 均不可获得直连能力；
- 若生产要求数据库内读写角色隔离、在线备份或高可用，则必须评估 Enterprise
  许可或替代图数据库，Community 不得冒充满足该要求；
- Community 的备份验收按“停库离线 dump/load + PostgreSQL 全量重建”执行；
  在线备份不作为 Community 能力；
- 配置通过受控密钥引用提供，不进入 Git、文档或日志。

版本能力依据（核查日期 2026-07-29）：

- Neo4j 官方文档说明 Community 中没有角色，用户具有隐含管理员权限：
  <https://neo4j.com/docs/operations-manual/current/authentication-authorization/manage-users/>
- RBAC 面向 Enterprise：
  <https://neo4j.com/docs/operations-manual/current/authentication-authorization/manage-privileges/>
- 在线备份面向运行中的 Enterprise，Community 可采用离线 dump/load：
  <https://neo4j.com/docs/operations-manual/current/backup-restore/online-backup/>
  与 <https://neo4j.com/docs/operations-manual/current/backup-restore/restore-dump/>

### 9.4 安全性

- 不同步患者、姓名、证件、电话、地址等敏感数据；
- 前端不直接访问 Bolt/HTTP 管理端口；
- AI 只能调用受限分析 API，不能获得 Neo4j 写权限；
- 后端只执行固定参数化模板，不开放自由 Cypher；
- 所有查询具备超时、结果上限和审计记录。
