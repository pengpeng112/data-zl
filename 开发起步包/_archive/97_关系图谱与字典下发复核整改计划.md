# 97 关系图谱与字典下发复核整改计划

## 1. 本轮结论

### 1.1 关系图谱

生产平台只读实测：

- `asset_relations` 共 537 条；
- `confidence='A'` 共 192 条；
- `confidence='A' AND validation_status='A_rechecked'` 为 0 条；
- 主要状态为 `candidate=293`、`verified=150`、`partial=39`、`user_confirmed_sync=25`。

旧页面的表级、系统、Schema、业务域和上下游模式默认同时发送：

```text
confidence=A
validation_status=A_rechecked
```

因此默认图谱必然为空，“图形/图片关系无法显示”不是无数据，而是前端默认条件与生产状态枚举不一致。

已完成本地修复：

1. A 类视图只默认限定 `confidence=A`，不再绑定不存在的 `A_rechecked`；
2. 验证状态下拉只返回数据库真实状态，不再注入幽灵状态；
3. 路由参数中的无效验证状态不再覆盖当前筛选；
4. 复合字段关系支持 `|` 分隔，修复 `PATIENT_ID|VISIT_ID` 映射错乱；
5. 跳过空端点，节点按名称稳定排序；
6. 正式边 ID 改用数据库主键，避免同端点或空 `rel_id` 造成 SVG/G6 键冲突；
7. 查询增加稳定排序，降低刷新后布局随机跳动。

### 1.2 字典下发

已确认实现包含：

- HIS：`COMM.DIAGNOSIS_DICT`、`COMM.OPERATION_DICT`；
- JHEMR：`diagnosis_dict`、`jhdict_icd_vs_clinic`、诊断对照表、`operation_dict`、`operation_dict_code`、手术对照表；
- 只允许单行 `INSERT` 和单条停用 `UPDATE`；
- 禁止 `DELETE/MERGE/DDL/批量 VALUES/IN 多值`；
- 灰码按既定规则处理；
- 总写开关和确认令牌默认关闭；
- dry-run 和 apply 审计已存在。

发现并已修复的 P0 安全缺口：

1. 写连接原来允许 `write_credential_ref` 缺失时回退到只读凭据；
2. 实际执行函数未独立复核 `write_policy`；
3. apply 未校验所选数据源是否属于目标系统。

修复后强制：

- `write_policy` 必须为 `medical_dict_push`；
- 必须配置独立 `write_credential_ref`；
- 禁止回退到只读凭据；
- HIS 只接受 HIS/HIS_SOURCE 来源，JHEMR 只接受 JHEMR/JHEMR_VASTBASE 来源。

生产只读核查现状：

| 来源 | 连接 | 当前策略 | 只读凭据 | 专用写凭据 |
|---|---|---|---|---|
| HIS_SOURCE | Oracle `10.10.10.15/his` | `readonly` | 已配置 | 未配置 |
| JHEMR_VASTBASE | Vastbase `10.10.8.177/jhemr` | `readonly` | 已配置 | 未配置 |

当前没有开启业务源写能力，符合安全预期。

## 2. 尚需整改的问题

### P0：上线前必须完成

#### G1 图谱筛选契约统一

- 后端为每种模式返回明确的默认筛选说明；
- 前端不再同时隐式组合互斥条件；
- 增加“当前条件实际命中关系数”；
- 空图必须展示具体原因：无数据、筛选为零、端点缺失或接口失败；
- 对所有生产真实状态建立中文映射。

验收：默认打开表级图谱能展示 A 类关系；切换 `verified/partial/candidate` 均有确定结果。

#### G2 物理来源端点唯一化

当前关系端点主要仍以 `SCHEMA.TABLE` 标识；不同物理系统存在同名 Owner/表时，节点可能被错误合并。应升级为：

```text
system_code + source_code + schema_name + table_name
```

- `asset_relations` 增加或补齐 from/to system/source；
- API 节点 ID 使用稳定物理键；
- 展示名称与物理 ID 分离；
- 数据中心镜像与独立源库不得因为同名表合并；
- 老关系通过资产目录和导入来源幂等回填。

验收：HIS 源端、数据中心 HIS 镜像、JHEMR 独立库的同名对象分别显示，跨系统边有明确标识。

#### G3 图谱数据分层

- `formal`：已发布正式关系；
- `candidate`：候选审核层；
- `dependency`：视图静态依赖；
- `deferred`：D 类跨系统待验证；
- `sync_mapping`：已确认同步/镜像关系。

目前部分 `validation_status=candidate` 数据位于正式关系表中，API 却统一标记 `relation_type=formal`，需按状态和来源重新分类。

验收：候选关系不再以正式实线出现；图例、统计和证据抽屉一致。

#### D1 写凭据与权限

- 通过平台“数据库连接 → 写凭据”或服务器受控密钥流程录入；
- 凭据文件权限目录 700、文件 600；
- 平台库仅保存 `file://...` 引用和脱敏用户名；
- 两个目标来源设置 `write_policy=medical_dict_push`；
- 全局 `APP_DICT_MEDICAL_PUSH_ENABLED` 保持 false，直到全部测试通过；
- 不得把通用字典写账号授权给人员科室同步或任意运维 SQL。

诊断/手术下发账号只能访问白名单字典表。人员科室和运维工具需要另建不同账号、不同凭据引用和不同审批模板，禁止共享权限边界。

#### D2 apply 前幂等与并发

- apply 前必须再次做目标库存在性检查，不能只依赖用户先点“检查”；
- 对已存在启用记录返回 `skip_exists`；
- 对停用记录只能生成明确的恢复审批，不能当新增重复插入；
- `MAX(serial_no)+1` 存在并发冲突，应改为目标库序列、受控锁或平台分配加唯一冲突重试；
- 对照表存在性检查加入 `classify + code` 完整业务键；
- 每次 apply 固定单条事务，失败自动回滚。

#### D3 字段长度和必填门禁

- 将 HIS 34/22 列和 JHEMR 各目标表长度生成机器可读约束；
- 计划阶段逐参数检查长度、必填、数值类型和枚举；
- 禁止静默截断关键编码；名称可按明确规则截断并在计划中提示；
- 手术本地码 HIS 长度 16、JHEMR 长度 18 的差异必须显式阻断；
- 对 `hospital_no` 建立平台配置，不允许普通用户随意输入生产机构编号。

### P1：功能可用性

#### G4 图谱交互重整

- 默认只保留“表级、上下游、待复核”三个主模式；
- 系统/Schema/业务域聚合放入二级分析视图；
- 系统选择后联动过滤数据源和 Schema；
- 节点点击固定高亮直接上下游，双击进入表详情；
- 边点击展示字段映射、验证指标、来源证据和限制条件；
- 支持一键适配画布、重置视角、SVG/PNG 导出；
- 大图超过阈值自动聚合，禁止静默切换引擎。

#### G5 SVG 与 G6 统一

- 两个引擎共用同一规范化数据和布局输入；
- 节点/边点击事件、标签、聚合、筛选完全一致；
- 建立截图或 DOM 回归测试；
- G6 初始化失败时展示错误并回退 SVG，不允许空白画布。
- G6 当前构建产物约 1.4 MB，应保持按需加载；默认 SVG，只有用户主动切换时才加载高级引擎。

#### D4 下发操作界面

- 计划、只读存在性检查、dry-run、apply 四阶段明确分栏；
- apply 必须展示目标系统、表、单条编码、变化类型和确认摘要；
- 前端不显示完整 SQL 参数中的敏感值；
- 显示写策略、专用写凭据状态和全局开关；
- 无专用写凭据时 apply 按钮必须禁用。

### P2：人员科室与运维工具

- 人员科室同步继续使用独立模块和专用最小权限账号；
- 默认 dry-run，批量 apply 继续走审批批次；
- 运维工具只执行已发布模板，不接受自由 DML；
- 每个模板绑定目标 source、表、动作类型、最大影响行数和专用凭据；
- 执行前 `SELECT COUNT` 预估，执行后记录影响行数；
- 字典下发、人员科室、通用运维三类审计和凭据彻底分离；
- 禁止把 `medical_dict_push` 策略扩展成通用业务源写权限。
