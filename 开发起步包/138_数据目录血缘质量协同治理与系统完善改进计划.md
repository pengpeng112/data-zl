# 数据目录、数据血缘、数据质量协同治理与系统完善改进计划

## 0. 结论先行

结合两篇治理文章和当前仓库证据，系统**需要继续完善**，但不需要推倒重建。现阶段应把已有的“资产目录、业务关系图谱、质量模块、查询/指标/产品”连成一个可追溯的治理闭环，重点不是再画一张更复杂的图，而是完成以下六项能力：

1. **把业务关联关系与数据流血缘彻底分层**：`PATIENT_ID + VISIT_ID` 等 JOIN/主外键关系说明对象如何关联，不天然表示数据从左表流向右表；影响分析不得把二者混为一谈。
2. **建立统一、稳定的对象标识**：系统、数据连接、Schema、表、字段、视图、查询版本、指标版本、数据产品和消费端使用同一套可解析的对象键，禁止只靠中文名、表名或 `ILIKE` 模糊匹配。
3. **把静态依赖升级为可解释血缘**：保存上游、处理活动、转换表达式/摘要、实际版本、下游、证据来源和可信状态；先覆盖核心链路，再扩字段级和运行级。
4. **把目录、血缘、质量串成事件闭环**：字段变更可触发影响分析和质量规则复核；质量异常可反查上游、圈定下游、分派责任、整改、复验并恢复资产状态。
5. **补齐真实消费端和 AI 来源证据**：查询、指标、产品、API、报表、AI 调用不应停在“已发布”，还要知道谁在用、使用哪个版本、回答依据和数据截至时间。
6. **首期不强求业务闭环和完整字段流动**：先把视图 DDL、查询版本、指标/产品引用等可证明的静态依赖准确落地；复杂转换、运行任务、真实消费和质量闭环待基础稳定后再做。

本文是 55 下的**专项模块计划**，不是新的平行总计划。130 仍负责应用、测试、Git 和 8.83 统一发布；138 负责补充 130 尚未详细展开的血缘基础。用户已于 2026-08-21 批准将 138 纳入 130 的统一开发和服务器发布窗口，但明确将闭环管理后置；该批准不授权业务源库写入，也不要求首期推断难以证明的数据流。

## 1. 两篇文章带来的可执行原则

### 1.1 第一篇：血缘从核心链路和自动采集开始

来源：[《数据血缘，没你想的那么复杂》](https://mp.weixin.qq.com/s/qI-EEGLlwLku3kI7Ns2y5w)

可落地原则：

- 血缘要回答“从哪里来、经过什么处理、被谁使用”。
- 粒度按问题选择，系统级、表级、字段级不必一次全部完成。
- 优先从数据库视图、SQL、ETL、报表等现成技术证据自动采集。
- 核心价值是端到端追溯和变更影响分析，不是图上连线数量。
- AI/Data Agent 使用数据时，必须能够返回来源、口径和链路证据。

### 1.2 第二篇：目录、血缘、质量围绕同一对象协同

来源：[《数据治理“三驾马车”：数据目录、数据血缘与数据质量如何协同落地》](https://mp.weixin.qq.com/s/KlnV-zoyTT0yQiiibNZXOg)

可落地原则：

- 目录回答“有什么、在哪里、谁负责”；血缘回答“从哪来、怎样处理、影响哪里”；质量回答“当前能否使用、怎样整改和复验”。
- 三者连接需要统一对象标识、统一责任、统一版本/状态和统一治理事件。
- 血缘不仅有上游和下游，还应记录处理活动、运行实例和责任主体。
- 静态解析、运行采集和人工确认必须并用，并标记来源和可信状态。
- 质量规则要绑定具体对象、场景、阈值、频率、责任人和失败动作。
- 验收应使用一次真实异常，验证发现、追溯、影响圈定、整改、复验和通知能否闭环。

### 1.3 对本系统的裁决

| 文章原则 | 当前基础 | 主要缺口 | 裁决 |
|---|---|---|---|
| 可发现目录 | 已有系统、连接、Schema、表、字段五层资产目录 | 责任人、术语、状态、热度和真实消费信息未完全贯通 | 复用现有目录，补对象身份和运营字段 |

## 3. 目标模型：两张图、一个目录、一条治理事件链

### 3.1 两张图必须分开

1. **业务关系图**：继续使用正式关系、候选关系和关系配方，回答“表之间怎样 JOIN、主从和业务关联是什么”。边可保存组合键、限定条件、覆盖率、孤儿率和验证级别，但不得被默认解释为数据流。
2. **数据血缘图**：只保存有明确方向证据的派生/读取/生产/发布/消费关系，回答“数据从哪来、经过什么、流向哪里”。
3. 页面可以共用图形组件，但必须有“业务关系 / 数据血缘”模式切换、不同图例和不同方向说明；任何 API 也不得把两种边合并成一个无类型列表。

### 3.2 端到端目标链路

```text
业务源表
  --syncs_to--> 数据中心镜像表
  --derives_to--> ODS/CDR/V_EMR 视图或加工表
  --reads_from / produces--> 查询版本
  --calculates--> 指标版本
  --publishes--> 数据产品 / API / 报表
  --consumed_by--> AI 应用 / 业务应用 / 责任部门
```

处理活动作为一等对象插入上下游之间：视图定义、同步任务、ETL/SQL、查询运行、人工修正规则或接口转换均有稳定 `process_key`、版本和运行实例。

### 3.3 统一对象身份

对象键必须区分逻辑身份和物理实例：

- 表/视图物理键：`system_code|source_code|schema_name|object_name|object_type`。
- 字段物理键：`table_physical_key|column_name`。
- 查询版本：`query|query_code|version`。
- 指标版本：`metric|metric_code|version`。
- 数据产品：`product|product_code`，若锁定版本则同时记录 `pin_version`。
- 处理活动：`process|process_type|source_code|process_code|version`。
- 消费端：`consumer|consumer_type|consumer_code`。

中文名、别名、旧表名仅作为可搜索属性；不能作为关联主键。对象迁移/改名通过 alias 与 supersedes 事件延续，不改历史运行证据。

## 4. 数据模型改进

所有新表继续放在 `asset` schema，使用 `asset_` 前缀；Alembic 必须手写 upgrade/downgrade，不删除旧表。

### 4.1 P0：统一血缘边 `asset_lineage_edges`

建议字段组：

| 字段组 | 内容 |
|---|---|
| 身份 | `edge_key` 唯一、`from_object_key`、`to_object_key`、两端 object_type |
| 语义 | `edge_type`：syncs_to/reads_from/derives_to/produces/calculates/publishes/consumed_by；`granularity`：system/table/column |
| 转换 | `process_key`、`transform_type`、`field_mapping` JSONB、`expression_hash`；原 SQL 只引用受控查询/视图版本，不复制敏感正文 |
| 证据 | `evidence_type`、`evidence_ref`、`evidence_hash`、`parser_version`、`confidence`、`review_status` |
| 版本 | `logic_version`、`valid_from`、`valid_to`、`observed_at`、`batch_id` |
| 状态 | active/stale/unresolved/rejected；失效只关版本，不物理删除历史证据 |

唯一性至少覆盖 `from_object_key + to_object_key + edge_type + process_key + logic_version`。导入使用 dry-run、业务键查重、批次摘要和二次零写验收。

### 4.2 P2（后期）：处理活动与运行 `asset_lineage_processes` / `asset_lineage_runs`

- `processes` 保存 view/sql/etl/sync/api/manual_rule 等定义、所属系统、负责人、代码/配置版本和内容摘要。
- `runs` 保存实际运行时间、状态、输入输出版本、行数摘要、调度/查询 run 引用和错误分类。
- 以后启动运行血缘时允许部分运行信息为 `unknown`，但禁止用静态 DDL 伪装为实际运行成功。
- 能复用 `asset_query_runs` 的查询运行不得重复存明细，只保存 typed reference。

### 4.3 P0：对象引用桥接

- 为表负责人、业务术语、质量规则/问题补充 `object_key` 或规范化关联表；保留旧 `full_table_name` 兼容字段。
- 查询、指标、产品继续保留当前业务表，血缘层只保存类型化引用，不复制版本实体。
- 增加对象解析服务：精确物理键命中、别名命中、未解析三态；未解析不得回退到模糊表名后静默连边。

### 4.4 P2（后期）：治理事件与影响快照

- 复用/扩展 `asset_govern_events`，支持 publish/change/deprecate/quality_failed/remediated/reverified/restored。
- 新增影响快照，记录事件发生时的上游路径、下游对象、责任人、规则、版本和证据摘要，避免后来图变化后无法复盘。
- 该阶段首版只生成平台待办和审计记录；邮件/企业微信等外部发送需另行明确授权和连接配置。

## 5. 数据摄取与解析顺序

### L0：建立基线和语义隔离

1. 备份测试平台库，读取生产只读计数和 Alembic head。
2. 给现有图边标注 `graph_kind=business_relation`，修正界面和 API 方向文案。
3. 建立对象键解析器和 collision 报告，先处理 ODS 镜像与 HIS 源端同名表。
4. 生成可重复的 `lineage baseline JSON`：对象数、边数、粒度、状态、未解析和冲突数。

验收：业务关系仍可用；任何业务 JOIN 边不进入血缘影响路径；同名表不会跨 source 串线。

### L1：导入现有视图依赖，先形成表级血缘

1. 将 ODS 119 视图/772 条依赖按物理键导入血缘草稿。
2. 将 HIS 335 个 `VALID` 视图的 1,191 条依赖导入；91 个 invalid 视图只登记目录状态，不进入 active 血缘。
3. 导入已探周边库的视图依赖时使用各自 source_code，禁止仅凭 Schema 合并。
4. 每条边保存 DDL/快照来源、哈希、采集时间、解析器版本和 `static_declared` 证据类型。
5. unresolved 单独输出，不因无法确认就中止其余批次。

验收：二次导入零写；有效视图的可解析表级依赖覆盖率 100%；未解析对象均有原因，不产生伪物理键。

### L2：贯通查询—指标—产品—消费

1. 把 active 查询版本的表依赖转为 reads_from/produces 边，并校验版本引用。
2. 把指标 query_code/version、分子/分母查询引用转为 calculates 边。
3. 把产品 query/metric 引用转为 publishes 边；锁定版本和跟随 active 必须明确区分。
4. 新增消费登记：API Token/调用审计、内部报表、AI 工具或业务应用以 consumer_code 关联产品；仅登记真实证据。
5. 对引用不存在、版本漂移、disabled 产品仍被消费等情况生成治理问题，不自动修复。

验收：所有 active 查询、active 指标和 enabled 产品的上游引用要么完整命中，要么明确 blocked；禁止 silent orphan。

### L3（后期）：核心场景字段级血缘

本阶段按用户裁决后置，不作为首期发布门禁。以后若启动，建议仍从下列已有证据较充分的链路小范围试点，而不是全库解析。

后期建议试点范围：`PAT_MASTER_INDEX/PAT_VISIT → ORDERS → LAB_TEST_MASTER/LAB_RESULT、EXAM_MASTER/EXAM_REPORT → 核心查询/指标/产品`。

解析至少支持：

- 直接列引用、别名、算术/字符串/日期函数；
- CASE/DECODE/NVL、聚合、窗口函数；
- JOIN/WHERE 中的限定条件；
- UNION/UNION ALL 分支；
- 子查询/CTE、字段重命名、常量字段；
- 无法可靠解析的 PL/SQL、动态 SQL、外部文件和人工规则进入 unresolved/manual_review。

字段映射必须区分：direct、derived、aggregated、filtered、constant、unknown。关系配方中的 JOIN 键是处理逻辑证据，但不能自动冒充 SELECT 输出字段血缘。

验收：核心场景 active 输出字段解析覆盖率目标不低于 90%；其余均显示 unknown/unresolved，错误连线抽样为 0；复杂表达式可展开查看证据但不展示敏感数据样本。

### L4（后期）：目录—血缘—质量事件闭环

本阶段按用户裁决后置，不进入首期开发和发布范围。

1. 质量规则绑定 object_key、适用场景、阈值、频率、责任人和失败动作。
2. 质量失败时保存失败版本和影响快照，沿血缘向上找候选根因、向下列受影响查询/指标/产品/消费者。
3. 问题单记录 assigned→acknowledged→remediated→reverified→closed/restored；没有复验不得关闭。
4. 资产详情同步展示当前质量状态、最近成功检查、开放问题和使用限制。
5. 字段/视图/查询版本变更时自动生成影响预览，人工批准后再改变 active 版本；不自动执行源库 DDL/DML。

验收：用一条合成异常和一条真实、脱敏、只读发现的问题分别跑通发现、追溯、影响、整改记录、复验和恢复；历史证据完整可审计。

### L5（后期）：AI 可解释使用

本阶段中依赖运行血缘、真实消费端和质量闭环的内容后置；首期 AI 仅可读取已审核静态血缘证据，不新增自动闭环能力。

1. AI 上下文返回 object_key、来源路径、口径/查询版本、质量状态、证据等级和 `data_as_of`。
2. AI 只能引用 active 或被明确允许的 draft；存在 unresolved/quality_failed 时必须告警，不得编造完整血缘。
3. 每次 AI 工具调用记录实际使用的产品/查询/指标版本和 lineage snapshot id。
4. Dify 继续只接收白名单脱敏摘要，不获得数据库凭据或患者样本，不自动修改质量事实。

验收：随机抽取 AI 回答可回放到精确查询版本和上游对象；无法证明来源时回答明确标记“不确定”。

## 6. 后端 API 与服务改进

| API/服务 | 目标 |
|---|---|
| `GET /lineage/object/{object_key}` | 返回对象、上下游摘要、质量状态、责任和当前版本 |
| `GET /lineage/paths` | 按 upstream/downstream、深度、边类型、状态查询有向血缘路径 |
| `GET /lineage/impact` | 精确对象键影响分析，覆盖字段→查询→指标→产品→消费者 |
| `GET /lineage/evidence/{edge_key}` | 返回证据类型、来源、哈希、解析状态、人工审核和运行信息 |
| `GET /lineage/coverage` | 按系统/来源/对象类型统计表级、字段级、运行级覆盖和 unresolved |
| `POST /lineage/import/dry-run` | 管理员受控预览新增/更新/失效/冲突；不写库 |
| `POST /lineage/import/apply` | 仅平台元数据白名单写入，需批次、审计、幂等和回滚点 |
| `POST /governance/events/{id}/impact` | 固化变更或质量事件的影响快照 |

所有响应必须有分页/上限；路径查询限制最大深度和节点数；大图使用服务端裁剪。源库连接器仍只允许 SELECT，AI 路由不得接触平台写执行器。
