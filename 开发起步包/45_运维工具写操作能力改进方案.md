## 1. 背景与目标

### 1.1 现状一句话

当前运维工具模块（`backend/app/api/v1/ops_tools.py` + `models/ops_tool.py`）已从脚手架推进到第一阶段可用状态：

- ✅ **审批流框架完整且真好使**：`OpsToolRun` 状态机 draft→submitted→approved/rejected→executing→succeeded/failed（兼容 pending/executed 历史状态），含审批人≠申请人校验、二次确认（`require_second_confirm`）、全链路写 `GovernAuditLog`。
- ✅ `readonly_sql` 已接入平台库真实只读 `SELECT`，并写 `GovernAuditLog(action="execute_readonly_sql")`。
- ✅ `whitelist_dml` 已回填 `OpsToolRun.affected_count` / `risk_scan`，支持 dry-run 和正式执行结果记录。
- ✅ `OpsToolTemplate.execution_mode` 已支持 `whitelist_dml`；`stored_procedure` / `http_api` 第一阶段明确拒绝执行。

### 1.2 目标

把这条已预留的写通道接上，让运维人员能通过**预定义模板 + 参数 + 审批**对平台库 `asset.*` 做受控的 `INSERT` / `UPDATE ... WHERE`。业务源库仍只读，任何 HIS/ODS/HRP/LIS/PACS/EMR 等源库写入都不在第一阶段范围内。

### 1.3 明确不做的事

- ❌ DELETE / DROP / ALTER / TRUNCATE 等 DDL 永远禁止（写通道也禁）。
- ❌ 不放开"运维人员自由输入裸 UPDATE/INSERT SQL"——必须走模板。
- ❌ AI 工具不接入写执行器（AGENTS.md 第5条）。
- ❌ 一期不做跨库事务、不做 governance change-requests 与 ops_tools 的合并（列为阶段4可选）。

## 2. 核心矛盾与红线协调

### 2.1 矛盾

AGENTS.md 安全红线明确："**源库一律只读，仅 `SELECT`，禁止任何 DML/DDL**；高风险操作需人工确认。" 而本需求要做 UPDATE/INSERT。

### 2.2 协调结论：不是"突破"红线，而是"接上已预留的受控通道"

证据——系统**早已为写操作预留了字段和设计**，只是没实现：

| 已预留的设计 | 现状 | 本方案做什么 |
|---|---|---|
| `AssetDataSource.write_credential_ref`（`asset_system.py:40`） | 字段存在，能录入，但第一阶段**不用于业务源库写入** | 保持预留；业务源库写入需另行确认后再接入 |
| `AssetActionExecutor.execution_mode` 含 `whitelist_dml`（`governance.py:316` 注释） | 设计有，无实现 | 在 ops_tools 实现 `whitelist_dml` 执行分支 |
| `OpsToolRun.affected_count`/`risk_scan`/`require_second_confirm` | 字段存在，从不填充 | 执行器真实回填 |
| `OpsToolTemplate.require_approval`/`require_second_confirm` | 框架完整可用 | 直接复用 |

**读写物理隔离原则**：
- 读路径（质控、元数据采集、连通性检测）→ 用 `credential_ref`（只读账号）+ 保持现有 `validate_sql_safety` 黑名单**不变**。
- 写路径（运维写）→ 第一阶段仅走平台库连接 + `validate_writable_sql` 白名单校验；业务源库 `write_credential_ref` 保持预留但不启用。
- 两条路径的连接、账号、校验函数**完全独立**，互不影响。

## 4. 总体架构：受控运维写通道

```text
[运维人员] → 前端运维工具设计器（§11）
   │  ① 选数据源(system_code/source_code) → ② 选操作类型 → ③ 写/生成SQL模板(带:param)
   │  ④ 定义参数表单(input_schema) → ⑤ 配置 risk_level/审批/二次确认/审计开关
   │  ⑥ dry-run预览 → ⑦ 保存为草稿 → 提交治理审批 → enabled=true
   ▼
OpsToolTemplate(asset_ops_tool_templates)  ← 模板注册表（白名单）
   │
[运维人员] → 前端工具执行页 → 创建 OpsToolRun(draft)
   │
[申请人/运维人员] → submit（提交审批）
   │
[审批人] → approve（审批人≠申请人校验 + 二次确认）
   ▼
OpsToolRun(approved) → dry-run 预览 → execute_start → 执行器 execute_whitelist_dml
   │
   ├─ 1. 从 tool.sql_or_endpoint_ref 取SQL模板 + run.input_params 绑定参数
   ├─ 2. validate_writable_sql(sql, allowed_tables, allowed_ops)  ← AST白名单校验
   │     失败 → run.status=failed, risk_scan回填, 终止
   ├─ 3. 第一阶段仅校验 `source_code in (asset, ASSET_PLATFORM)`，不解析业务源库写账号
   ├─ 4. 建写连接（独立于读连接），开事务：
   │     ├─ 读 before 快照（SELECT 受影响行）
   │     ├─ execute_write(sql, params) → affected_rows
   │     └─ 读 after 快照
   ├─ 5. COMMIT（成功）/ ROLLBACK（异常）
   ├─ 6. 回填 run.affected_count / execution_summary / risk_scan
   └─ 7. 所有正式写执行 → 写 GovernAuditLog(module='ops', action='execute_write',
            before_data/after_data 脱敏, sql_hash)
   ▼
[运维人员/管理员] → 执行历史页查看 before/after/affected_count/审计链
```

**设计原则**：
1. **模板优先**：SQL 存固定模板带 `:param` 占位符，运行时只接受参数，不拼裸 SQL。
2. **读写物理隔离**：独立账号、独立连接、独立校验函数。
3. **白名单校验**：AST 解析，只允许 UPDATE/INSERT，目标表必须在白名单，UPDATE 必须有 WHERE。
4. **dry-run 先行**：执行前可预览影响范围（只读版本）。

## 5. 多数据库连接与写账号体系

### 5.1 多源支持（已具备，复用）

现有架构已支持多数据源，**不是新问题**：
- `AssetDataSource`（`asset_system.py:23`）支持注册任意数量的源库（Oracle/PG/Vastbase/MySQL/SQLServer），每个有独立 `source_code`。
- `OpsToolTemplate.source_code`（`ops_tool.py:16`）已存在——每个运维工具**绑定单个数据源**。
- `DB_CONNECTOR_MAP`（`db_connectors.py:361`）按 `db_type` 分发到对应连接器。
- 执行时按 `tool.source_code` → `AssetDataSource` → 对应连接器。

**跨库写（D4）**：一期不做。每个工具单库单表；跨库需求用"工具链"——工具A的输出（如查出的一批主键）作为工具B的入参，串行执行。这在受控运维场景已足够（修正脏数据、补发消息都是单库操作）。

### 5.2 业务源库写账号（二期候选，第一阶段不启用）

第一阶段不申请、不解析、不使用 HIS/ODS/HRP/LIS/PACS 等业务源库写账号。`AssetDataSource.write_credential_ref` 仅保留为数据模型预留字段，不接入当前执行器。

如二期确需启用业务源库写入，必须重新确认：允许写入的系统和表、写凭据与只读凭据物理隔离、审批级别、双人复核、回滚方式、审计字段和 DBA 最小授权。未经重新确认，不得把以下内容实现到生产执行路径。

---

## 6. 连接器写能力（二期候选）

第一阶段 `whitelist_dml` 不接业务源库连接器写能力，只使用平台库 SQLAlchemy 会话执行 `asset.*` 白名单参数化写入。Oracle、Vastbase、MySQL、SQLServer 等业务源库连接器的 `execute_write`、`resolve_write` 和写账号最小授权，全部列为二期候选能力。

当前仍建议独立加固只读路径：源库 `execute_readonly` 应尽量设置只读事务和 statement timeout；这属于安全增强，不代表放开源库 DML。

## 7. SQL 白名单校验设计

### 7.1 新增 `validate_writable_sql`（与读校验完全独立）

位置：`backend/app/services/quality_rule_engine.py` 新增函数，或独立 `sql_safety.py` 文件。

```python
def validate_writable_sql(
    sql: str,
    allowed_tables: list[str],     # 白名单目标表（如 ["HIS.MED_OPERATION_MASTER"]）
    allowed_ops: list[str],        # 允许的操作（如 ["UPDATE", "INSERT"]）
    db_type: str = "oracle",
) -> dict:
    """白名单校验写 SQL，返回 {valid, errors, warnings, parsed_summary}"""
```

### 7.2 校验规则（严格白名单）

1. **AST 解析**：引入 `sqlglot`（呼应 44 号文档），解析失败直接拒（不降级到正则）。
2. **操作白名单**：只允许 `allowed_ops`（UPDATE/INSERT），禁 DELETE/MERGE/DROP/ALTER/TRUNCATE/CREATE/GRANT/REVOKE。
3. **目标表白名单**：解析出的所有目标表必须在 `allowed_tables` 内（防越表写）。
4. **UPDATE 强制 WHERE**：UPDATE 无 WHERE 子句直接拒（防全表更新）。
5. **禁多语句**：`;` 出现在末尾分号前 → 拒。
6. **禁注释绕过**：解析前剥离注释再校验，或 AST 解析天然免疫。
7. **返回 `parsed_summary`**：操作类型 + 目标表 + WHERE 摘要，回填 `OpsToolRun.risk_scan`。

### 7.3 读校验保持不变

`validate_sql_safety`（`quality_rule_engine.py:15`）继续服务所有读路径，**一字不改**。两个函数独立，互不影响。

## 8. 运维工具模板制作：可视化 vs AI 配置（D1）

**推荐方案：可视化低代码设计器为主 + AI 辅助起草 SQL 模板**。理由：

- 可视化设计器保证"模板结构可控、参数表单规范、安全配置不遗漏"，适合反复使用的标准化运维工具。
- AI 辅助降低"写 SQL 模板"的门槛，但 AI **只生成草稿**，用户必须审阅修改，提交治理审批后才入库生效——符合 AGENTS.md "AI 不执行写"红线（AI 起草 ≠ AI 执行）。

### 8.1 可视化设计器流程（前端分步表单，详见 §11）

```text
步骤1 选数据源：下拉选 system_code → source_code（从 AssetDataSource 已注册列表）
步骤2 选操作类型：只读查询 / UPDATE / INSERT / 存储过程（决定 execution_mode）
步骤3 写SQL模板：代码编辑器（Monaco/CodeMirror），支持 :param 占位符高亮
        ┌─ AI辅助按钮：自然语言"把MED_OPERATION_MASTER里STATUS为null的改成0"
        │  → AI 读 asset_columns 元数据 → 生成 SQL 模板草稿 → 用户审阅修改
        └─ SQL语法实时校验（调 validate_writable_sql 的 dry-run 版本）
步骤4 定义参数表单：参数名/类型/必填/校验规则 → 自动生成 input_schema (JSONB)
步骤5 配置安全项：
        - risk_level: low/medium/high/critical
        - require_approval: 是否需审批（critical 强制 true）
        - require_second_confirm: 是否二次确认
        - require_audit: 保留为模板配置字段；第一阶段正式写执行始终审计，critical 不可关闭
        - allowed_tables: 自动从SQL解析+人工确认（白名单）
        - allowed_operations: 自动从SQL解析
步骤6 dry-run预览：填测试参数 → 用只读账号跑"SELECT 版本"看影响范围（不真正写）
步骤7 保存草稿 → 提交治理审批 → 审批通过 enabled=true
```

### 8.2 AI 辅助的边界（严格遵守红线）

- ✅ AI 可以做：读 `asset_tables`/`asset_columns` 元数据，根据自然语言描述生成 SQL 模板**草稿**。
- ✅ AI 可以做：dry-run 预览（只读，调 SELECT 版本）。
- ❌ AI 不能做：直接触发写执行（写执行只走 ops_tools 审批流，经人工 approve + second_confirm）。
- ❌ AI 不能做：绕过 `validate_writable_sql` 白名单。
- ❌ AI 端点（`/api/v1/ai/*`）**不挂载** `whitelist_dml` 执行器。

### 8.3 备选方案（若不选推荐）

- **纯可视化**：去掉 AI 辅助按钮，SQL 模板完全人工写。简单但门槛高。
- **纯 AI 对话**：用户对话描述需求，AI 生成完整模板（含参数表单+安全配置）。灵活但难保证安全配置完整性，不建议。

## 10. API 与执行器接入

### 10.1 EXECUTOR_DISPATCH 新增 whitelist_dml 分支

```python
# ops_tools.py
EXECUTOR_DISPATCH = {
    "readonly_sql": lambda tool, run, db: _exec_readonly(tool, run, db),
    "stored_procedure": lambda tool, run, db: _exec_stored_procedure(tool, run, db),
    "http_api": lambda tool, run, db: _exec_http_api(tool, run, db),
    "whitelist_dml": lambda tool, run, db: _exec_whitelist_dml(tool, run, db),  # 新增
}
```

### 10.2 `whitelist_dml` 执行器逻辑（当前实现）

当前实现位于 `backend/app/services/ops_executor.py`，只支持平台库 `asset.*`：

1. 从 `tool.sql_or_endpoint_ref` 读取固定 SQL 模板，从 `run.input_params_masked` 读取参数。
2. 调 `ops_sql_safety.validate_writable_sql` 校验：单语句、参数化、目标表必须在 `asset` schema 和 `allowed_tables` 白名单内，只允许 `INSERT` / `UPDATE ... WHERE`。
3. `dry_run=true` 时只执行 `dry_run_sql` 预览影响数量，不修改本地库。
4. 正式执行前由 `ops_tools.execute_run` 校验审批状态、二次确认和三项 `APP_OPS_WRITE_*` 门禁。
5. 正式执行使用平台库会话执行参数化 SQL，回填 `affected_count` / `risk_scan`。
6. 所有正式写执行固定写 `GovernAuditLog(module="ops", action="execute_write")`，参数写入前脱敏。

`stored_procedure` / `http_api` 第一阶段直接拒绝执行；不解析业务源库写凭据，不连接 HIS/ODS/HRP/LIS/PACS 等业务库执行 DML。

### 10.3 凭据边界

第一阶段不新增业务源库写凭据解析，不接 `write_credential_ref` 到业务源库。正式写执行仅限平台库 `asset.*`，并受 `APP_OPS_WRITE_ENABLED`、`APP_OPS_WRITE_D1_D5_CONFIRMED`、`APP_OPS_WRITE_CONFIRMATION_TOKEN` 三项门禁控制。

后续如要启用业务源库写账号，必须重新确认范围、凭据隔离、审批级别和审计策略。未经重新确认，不得写 HIS/ODS/HRP/LIS/PACS/EMR 等业务源库。

### 10.4 ops_tools 主执行入口回填 affected_count

`ops_tools.py:execute_run` 已回填 `affected_count` / `execution_summary` / `started_at` / `finished_at`。`whitelist_dml` 正式执行前还会校验审批状态、二次确认和三项运行时门禁。

## 13. 安全约束升级清单

1. **写范围限制**：第一阶段仅平台库 `asset.*`；业务源库写账号和连接器写能力不启用。
2. **读路径加固**：源库 `execute_readonly` 后续应补只读事务 + statement timeout（独立于写能力，纯加固）。
3. **白名单校验**：§7，`validate_writable_sql` AST 白名单。
4. **读写隔离**：独立账号（`credential_ref` vs `write_credential_ref`）、独立连接、独立校验函数。
5. **AI 隔离**：写执行器不挂 `/api/v1/ai/*`；AI 只辅助起草模板和 dry-run（§8.2）。
6. **dry-run 先行**：执行前预览影响范围。
7. **critical 强制审批 + 强制审计 + 二次确认**（D2 已确认）。
8. **源库 SELECT 探查审计（额外缺口）**：调研发现质控执行对源库 SELECT 完全没审计，建议顺带补上（独立小任务，不阻塞本方案）。

## 16. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 写账号权限过大（被授了 DELETE/DDL） | DBA 最小授权 + 定期审计权限视图 + 连接层 `validate_writable_sql` 二次拦截 |
| SQL 模板被篡改（绕过白名单） | 模板注册本身走治理审批（change-request）；模板修改需重新审批；运行时再次校验 |
| sqlglot 解析 Oracle/Vastbase 方言失败 | 降级为**拒绝执行**（非降级到正则）+ 提示人工；记录到 risk_scan |
| 大表 UPDATE 锁表 | statement timeout + UPDATE 强制 WHERE + dry-run 预览影响行数 |
| AI 起草的 SQL 模板有隐藏危险 | AI 只生成草稿，必须人工审阅 + `validate_writable_sql` 校验 + 审批才生效 |
| 关闭审计后出问题难追溯 | critical 强制审计（D2）；建议 low/medium 也默认开 |
| 读路径被误改 | 读校验函数独立，写校验独立，互不影响；加回归测试锁死 |
