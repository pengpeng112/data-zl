# SQL 关系摄取与治理

## 目标

把历史 SQL 当作“关系证据”，而不是直接当作“关系真相”。完成 SQL 解析、活元数据核对、正式关系查重、风险分级和候选交付，使后续 AI 始终从仓库或平台获取最新关系。

## 首次使用时读取

1. 读取仓库根目录 `AGENTS.md`。
2. 读取 `开发起步包/README.md` 和 `开发起步包/55_系统未完成事项统一执行计划.md`。
3. 读取本技能 `references/relation-intake-guide.md`。
4. **按 SQL 目标库选择资产包与系统技能（勿默认 ODS 包）**：ODS/数据中心 → `数据资产_资产包/` + `ods-readonly-sql`；JHEMR/EMR(Vastbase) → `数据资产_JHEMR_Vastbase资产包/`；HIS 源端 → `数据资产_HIS源端资产包/` + `hisuser-readonly-sql`；无纸化 CDMS → 平台元数据 + 79 号证据。跨系统边按 40 号 D 级延后口径（154 号试点先例）。
5. 只读取与本次表和业务主题有关的元数据、关系文件和证据报告；不要把 `_archive/` 当作当前依据。

## 字段值域硬规则（149 值域知识库，强制）

- 涉及编码/状态/类型/阈值/字典类字段（如 SQL 中出现的离院方式、急诊标志、诊断类别、OPER_STATUS 等编码/状态/阈值字段）写 SQL/给口径前**必须先取值域，禁止凭字典表名、字段注释或惯例猜测**。
- 获取顺序：① 平台 `GET /api/v1/ai/system-context?system_code=对应系统编码` 或 `POST /api/v1/ai/context/resolve`（响应 `value_domains` 段=该系统全部 confirmed 值域+陷阱，逐条带 version_no）；② 平台不可达 → 离线 `开发起步包/数据资产_资产包/value_domains.json`（超过 max_age_days=7 天须提示用户重新导出）；③ 仍无 → `开发起步包/148_病案首页关键值域与离院方式口径字典.md`（平台导出视图，勿手改）。
- 三处都查不到：SQL 写注释 `【值域待确认：OWNER.TABLE.COLUMN】` 并在交付说明中明示，**不得假设含义**；发现新证据按 149 提交平台 pending（AI 仅可提交，确认/裁决须人工）。
- 陷阱（domain_kind=trap）同样强制：离院方式 **4=非医嘱离院、5=死亡**，勿用 `COMM.DISCHARGE_DISPOSITION_DICT`（那是治疗结果字典）；`PAT_VISIT.DEATH_DATE_TIME` 源端基本不填，不能识别死亡。

## 标准流程

### 1. 登记来源

记录 SQL 的业务用途、来源系统、数据库方言、来源文件和可追溯说明。对 SQL 计算 SHA-256；不得把口令、Token、身份证、姓名、电话、地址或患者条件值写入证据文件。包含敏感内容时先生成脱敏副本。

### 2. 静态解析

先运行：

```powershell
python .agents/skills/sql-relation-intake/scripts/extract_sql_relations.py `
  --sql-file D:\temp\query.sql `
  --system-code HIS_SOURCE `
  --output D:\temp\relation_candidates.json
```

脚本输出表、别名、等值 JOIN、附加条件、SQL 指纹及与正式关系的初步查重结果。它是确定性预解析器，不替代人工语义判断；动态 SQL、旧式逗号连接、相关子查询、`UNION` 分支、函数包裹键和隐式关联必须人工补充。

### 3. 获取当前资产

按以下优先级获取，不依赖聊天记忆：

1. 平台 AI 上下文和关系配方接口可用时，读取当前平台资产；
2. 平台不可用时，读取仓库机器可读资产；
3. 元数据快照只作为表字段存在性证据；
4. 报告只作为关系验证和业务限制证据。

具体路径、平台端点和系统路由见 `references/relation-intake-guide.md`。

### 4. 核对和查重

对每个关系确认：

- Owner、表、字段真实存在；
- 别名解析正确；
- 组合键完整；
- JOIN 中的状态、非空、日期、类型转换和子集条件没有丢失；
- 是否已有同向或反向正式关系；
- 是否只是已有关系的新证据；
- 是否属于多表配方而非单条关系边；
- 是否跨物理实例且缺少已验证 DBLINK/同步对象。

同名字段不构成关系证据。历史 SQL 与活元数据冲突时保留冲突记录，不得自动修正后冒充原 SQL。

### 5. 分级

- `existing`：与正式关系等价，只补充来源证据。
- `candidate`：表字段存在且 JOIN 可解释，但未做活库验证。
- `partial`：仅在状态、非零键、时间窗口或特定业务子集成立。
- `recipe_candidate`：多个 JOIN、去重、聚合或过滤共同构成可复用查询逻辑。
- `rejected`：字段不存在、组合键明显缺失、跨库不可达或已被证据否定。

历史 SQL 本身最高只能给 C/B 级候选证据，不得仅凭“曾经跑过”标记 A/A+ 或 `verified`。

### 6. 验证

只有用户明确要求验证时，才按所属系统的只读 SQL 技能生成和执行限量验证 SQL。验证父键覆盖率、孤儿率、重复键和 JOIN 放大量；巨表必须先用业务键、时间范围或受限父键集合缩小。

不得执行 DML、DDL、锁表、存储过程或无界扫描。不得把未脱敏患者明细带入 AI、日志或报告。

### 7. 交付与回写边界

默认只交付候选 JSON/表格和建议，不修改正式资产。

用户明确要求“纳入”时：

1. 将新关系写入平台 `asset_relation_reviews` 草稿/待审区，或生成可审查导入文件；
2. 将复杂逻辑写成 `asset_relation_recipes` 草稿；
3. 展示与正式关系的 diff；
4. 经审核和验证后，才更新正式 `relationships.csv`、catalog 或发布配方；
5. 若新增编号文档，严格同步 `开发起步包/README.md` 的目录和更新记录。

技能自身不得绕过审核直接发布。

```markdown
## 来源
- 系统/方言：
- SQL SHA-256：
- 业务用途：
- 是否已脱敏：

## 解析结果
| from | to | JOIN 键 | 附加条件 | 查重 | 分级 |

## 元数据与关系证据
| 候选 | 表字段存在 | 既有关系 | 证据来源 | 风险 |

## 建议动作
- 补证据 / 进入候选审核 / 生成验证 SQL / 关系配方草稿 / 驳回

- 默认：未修改正式资产。
```

明确区分“解析到”“元数据确认”“活库验证”“审核发布”，不要混用这些状态。
