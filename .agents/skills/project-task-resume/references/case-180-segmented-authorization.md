# 案例回放 180：分段授权与观察点纪律

> 类别：技能参考（只读回放，不是执行计划）
> 源文件：`开发起步包/180_G13分域提交与G1G3生产发布一次性执行计划.md` + 同号 `_执行报告.md`
> 证据目录：`开发起步包/output_r180/`

## 场景

用户点名「按照这个执行」授权 180 号计划。计划本身分段：A（分域提交）、B（DB
备份+镜像构建）、C（生产发布切换）、D（夜跑验证）、E（前端切换）、G2（runner
子任务激活）各段授权边界不同。执行 AI 在拿到整计划授权后如何把握"执行到哪条线"。

## 输入事实

- 计划明确：A+B+C+E 属本批执行；D1 夜跑验证**排程到次日 02:25**；
  G2/D2 **未授权不做**。
- 报告 §0：九组提交入库（他人域 13 文件零触碰）、生产镜像 r178-20260905
  发布（G1/G3 ✓）、前端原子切换；夜跑 runner 保持 r175 旧版系是**刻意决策**
  （避免未授权激活 G2）。

## 判定过程

1. **授权范围内全做**：A/B/C/E 四段一次性闭环，含 DB 备份、回滚链、回读六项
   ——发布类动作因用户点名授权而合法。
2. **未授权段刻意不做并留名**：G2 runner 激活、D2 未授权，报告显式写"刻意
   决策"，防止后续 AI 把"没做"误读成"漏做"而补执行。
3. **观察点未出数不宣称完成**：D1 排程后报告只写"已排程、结果待出前不宣称
   F-2 已验证"——事后证明该纪律正确：首夜 02:00 夜跑实际 failed（水位死锁，
  见 185 N1 三行对账），若按"最新一行 success"或排程即宣称，结论就是错的。
4. **域纪律贯穿**：13 个他人域文件全程零触碰，每组提交 show 零越界。

## 输出形态

报告 + `_结果.json` + output_r180/（workspace_snapshot/progress/exceptions/
release_evidence/nightly_d）。

## 回放要点

分段授权计划的接手三查：①用户原话授权到哪段（点名授权 ≠ 整计划无限授权）；
②哪些段被计划本身排除（刻意不做要留名）；③观察点是否已出数（未出数只能写
"待出"，不能用间接证据宣称验证完成）。
