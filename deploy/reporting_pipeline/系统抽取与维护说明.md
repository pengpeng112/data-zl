## 2. 抽取怎么走

```mermaid
flowchart LR
    A[源视图与逐表路由] --> B[Python或DataX受控读取]
    B --> C[持久暂存与完整清单]
    C --> D[字段质量与父子关系核对]
    D --> E[批准和同表写租约]
    E --> F[前置机业务数据和提交回执同事务]
    F --> G[按键和内容回读]
    G --> H[院内抽取完成]
    H --> I[省端抽取及回执 另行确认]
```

日期按 `Asia/Shanghai`。T+1取昨天00:00到今天00:00，条件为 `>=开始 AND <结束`，业务日一经冻结不能在重试时变成“新的昨天”。`DATETIME`是源端窗口依据，目标不需要为了抽取再增加同名列；`SYSTEM_TIME`是前置机本次真实写入时间，不能拿源视图动态 `SYSDATE`当业务变更时间。

Python负责读取、校验、恢复和统一装载。DataX用于已经验证适合它的源，只写批准的暂存区，再由同一个受控目标执行器装载。不能让DataX另开一条直接写正式表的路线。DataX读取数、写入数和脏数据数必须齐全，读写数相等且脏数据为0才算完整。

每次尝试独立保存文件和哈希，完整清单最后写。日期、金额、小数和二进制保留原类型。装载前重新检查文件行数和哈希，不能只看有无 `complete.json`。新建POSIX暂存目录为0700、文件为0600；Windows部署另配ACL。已有目录不擅自改权限，接入时单独验收。

真实INSERT/UPDATE、目标时钟和提交回执要在同一个目标事务内。已有同键同内容不重写、不刷新时间；有真实修正才更新。历史数据整体重打时间属于另一项明确范围的操作，不能每天把全表时间都刷一遍。

## 3. 出错后怎么处理

| 情况 | 处理方式 |
|---|---|
| 单表读取失败、慢视图或数据校验不通过 | 保留失败窗口/隔离账和告警，继续独立表；不得标成跳过成功 |
| 父表失败 | 依赖它的子组等待；其他链路继续 |
| 网络断在COMMIT应答上 | 标为 `COMMIT_UNKNOWN`，冻结该表重叠写入，先查同事务回执；其他独立表继续 |
| 预览后目标内容变了、DML行数不符、写租约失效 | 整批回滚并重新核对，不写成功回执 |
| 控制库不可用、范围无法判断或全局安全门失效 | 停止受影响的正式写入，保留已完成证据，不能无记录继续 |
| 告警接口不可达或401 | 本地队列保留；401暂停盲重试；抽取不因HTTP等待被拖住，但不能宣称告警已送达 |

普通失败继续补，提交不明先查清再补。`retry`目前给恢复动作，调度装配还必须实际按动作调用下一步；不能把“给出了建议”当成“已经补完”。

## 4. 日常查看入口

程序入口在 `backend/scripts/reporting_ctl.py`。当前没有专门的T+1管理页面，以CLI和日报为准。以下前3条只读本地配置，不连生产：

```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/reporting_ctl.py doctor
.\backend\.venv\Scripts\python.exe backend/scripts/reporting_ctl.py validate --offline
.\backend\.venv\Scripts\python.exe backend/scripts/reporting_ctl.py list
```

`doctor`当前应退出2并说明生产未接通，这是如实检查，不是任务失败后要强行绕过的错误。`validate`只证明种子结构合法；`list`显示逐层就绪，不代表77表获准上线。默认读执行包的候选种子，不能自动把旁边某个v1.3候选文件当成生效配置。正式装配必须记录加载文件的完整路径、版本和哈希。

完成生产接入后，由受控启动器注入 `APP_REPORTING_CONTROL_DB_URL`，再运行：

```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/reporting_ctl.py daily-report --business-day 2026-10-21
.\backend\.venv\Scripts\python.exe backend/scripts/reporting_ctl.py resume
```

日期是示例，实际用待核业务日。不要把带密码的控制库URL粘到 `--state-db` 或截屏中。服务器上应使用发布后的容器内路径和受控配置，不能把Windows命令照抄到Linux。

每天至少看这几项：启用表是否全部形成回读结果；各表最早未补窗口；隔离/缺父数量；提交不明；最后连续完成日；月重扫逾期；告警实际送达状态；暂存盘可用空间和worker心跳。日报的“逐表每日”现在只算指定业务日，历史欠账另列。未启用表不进入正式上线分母，但77项总数和待处理项仍保留。

前置机回读一致只表示院内已落库。省端是否接收、是否认可字段或关联，还需要逐表回执；目前 `delivery`明确保持 `PENDING_RECEIPT`，不能据此报省端已完成。

## 5. 新增表、改视图和补历史

新增一张表按以下顺序处理，不复制整个旧脚本：

1. 在原77项配置或获准扩展配置中登记源实例、Owner、真实视图名、引擎和路由，先保持停用。
2. 核对目标唯一键、完整写入投影及类型、业务时间和变更依据。字段在配置里填写后，装载器必须保留；本轮已修复投影、装载策略等字段被丢弃的问题。
3. 核对父子关联、取消/删除语义、迟到范围；DataX-only表和LIS双源要单独接路由，不允许默认退成Python单源。
4. 配置本表超时、行数/字节预算、重试和慢查询阈值。出院等慢表按实测画像配置，不能统一3分钟超时。
5. 用合成测试和获准隔离库验证空窗、分页、重跑、修改、重复键、超长精度、缺父、断连和提交不明。
6. 小日窗试点前拍旧写者进程/作业快照，确认逐表交接；一表一个正式写者。核数量、键和内容、回执及目标时间，随后才启用日轮。

改视图后先比较字段和定义指纹，再决定定向字段UPDATE、缺行INSERT还是重抽窗口。只有已有记录字段错时优先按ID差异UPDATE；不要为几个字段无条件删整月。主键或费用分类ID变了，需先隔离并明确替换范围，不能按旧ID硬覆盖。

迟到数据不能只靠昨天日窗。`EMR_DOC_ORDER_CHECK`、`EMR_IN_FEE_INFO_CHILD`至少应按原策略登记历史月覆盖并做周期重扫；当月回看与历史月份轮巡分开记。月度替换必须完整暂存、核对范围后，在批准的原子发布事务中执行；当前SQL执行器仅实现MERGE，没有实现REPLACE_MONTH删除，代码会明确拒绝。不能因为有月扫计划JSON就认为已经自动重扫。

## 6. 上线前还缺什么

1. **代码接线**：CLI尚未装配源工厂、目标连接工厂及平台生产ApplyPort；JSON批准字符串不能替代真实批准。DataX暂存回收、双源路由、父子质量校验和恢复动作还要在同一日轮端到端接通；回读后缺口关闭、连续水位推进和恢复告警也要验收。
2. **版本与容量**：正式配置要明确修改覆盖/撤销规则和版本证据；不能拿采集时刻伪装源版本。大日窗需要把拆分后的叶子窗口贯穿暂存、事务和恢复，不能整月放进内存或一个目标事务。
3. **生产环境**：批准后发布镜像、全链控制库迁移、目标回执表、持久暂存挂载及单入口调度；02:00和06/12/18只属候选时刻，尚未启用。
4. **外部验收**：告警注册、密钥引用、测试订阅及逐目标送达；Oracle方言隔离验证；首组四表试点和至少7业务日观测；省端逐表回执另行推进。
