# 复核对象：149_字段值域知识库与AI自动注入执行计划（多 AI 互查方案包）

## 一、被复核方案全文摘要（源：开发起步包/149_字段值域知识库与AI自动注入执行计划.md）

背景：2026-08-24 取数事故——AI 依据错误字典表（COMM.DISCHARGE_DISPOSITION_DICT，实为治疗结果）猜值域，把病案首页离院方式 4/5 含义写反（正确 4=非医嘱离院、5=死亡），经 JHEMR report.r_pat_visit 交叉验证纠正。同类值域（手术急诊标志 2、诊断类别 1/2/3/7/8、OPER_STATUS>=35、免疫组化项目名等）已沉淀 148 号文档。

方案四阶段：
- P1 最小闭环：新表 asset_column_value_domains + 版本表 asset_column_value_domain_versions（asset schema，Alembic 手写）；API：GET /api/v1/metadata/value-domains（按 system/table/column 过滤，confirmed 默认）、POST（AI 提交 pending 候选，evidence 必填）、PATCH confirm/deprecate（人工）、GET versions；扩展 /api/v1/ai/system-context 与 propose-sql：解析 SQL 涉及字段自动附 confirmed 值域数组；审计复用 asset_govern_audit_logs。
- P2 首批导入：import_value_domains_seed.py 幂等导入 148 号 8 组值域为 confirmed，证据字段引用实测数字与 JHEMR 交叉。
- P3 技能路由+兜底：hisuser/ods/docare/mobile-nursing/query-governance-intake 五技能 SKILL.md 加硬规则（先查平台 API→兜底 value_domains.json/148→仍无输出【值域待确认】禁止假设）；tools/export_value_domains_json.py 单向导出 JSON 与库同步。
- P4 摄取联动（二期）：126 查询 ingest 时 SQL 字面量 vs confirmed 值域冲突 warning；值域修订触发引用影响分析。

主表关键字段：system_code、source_owner、table_name、column_name、code、meaning、note、status(pending/confirmed/deprecated)、evidence_method、evidence_sample_count、confirmed_by、confirmed_at、current_version_id。
版本表：domain_id、version_no、快照、change_reason、evidence、actor、created_at。

风险表：Q1 确认人机制待定；Q2 SQL 解析准确率（宁缺勿错）；Q3 平台库不可达时兜底 JSON 滞后；Q4 148 文档与库双写一致性（库为权威，文档为导出视图）。

## 二、方案owner追加的核心关注点（本次审查重点）

1. 值域必须便于其他 AI 随时调用、分析、日常问题处理（获取通道要快、准、不易漏）；
2. 必须能记录各个来源（多来源证据：如 HIS 字典表、JHEMR 交叉、人工确认、不同 AI 实测）；
3. 冲突可检测：不同来源/不同时间对同一字段值域说法冲突时系统能发现并暴露；
4. 便于扩展和维护分析（新增字段值域、修订、追溯、统计）。

## 三、审查要求

逐条输出【同意/反对/疑问+理由+风险】，每条必须引用方案节号或原文片段；重点评估：数据模型是否支撑关注点 2/3（当前 evidence 为单字段，多来源冲突记录能力是否不足）；API/注入设计是否满足关注点 1；P4 二期是否应提前；有无遗漏的关键风险。
