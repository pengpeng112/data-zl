# ZCode(GLM) 独立初审（步骤1-3阶段，与其他方互不通气）

## 逐条意见

1. 【反对】§一·主表字段：evidence_method/evidence_sample_count 为单值字段，同一字段值域常有多来源证据（HIS 字典、JHEMR 交叉、人工确认、多次实测），单值无法记录来源列表，直接削弱关注点 2；建议证据独立成 asset_column_value_domain_evidences 子表（来源类型/来源系统/方法/样本数/时间/actor，一对多），主表只留汇总引用。
2. 【反对】§一·冲突检测缺失：方案仅 P4 有"SQL 字面量 vs confirmed 冲突告警"，没有"新提交证据/新版本与既有 confirmed 值域语义冲突"的检测（如不同 AI 提交 4=死亡 vs 4=非医嘱），关注点 3 无落点；应在 POST 候选/确认/新版本写入时即做同字段同 code 语义冲突检测并阻断或标记 conflict。
3. 【疑问】§一·API：POST 允许 AI 提交 pending，但无防重复/幂等键（system+table+column+code），多 AI 重复提交会产生大量重复候选；建议唯一约束+upsert 或先查后插。
4. 【疑问】§一·注入：SQL 解析在别名/子查询场景下解析 owner.table.column 命中率有限（Q2 已自认），"宁缺勿错"正确，但应补一个兜底：AI 上下文全量摘要按 system_code 分组返回 top 值域（热点字段白名单），避免解析失败时完全无注入。
5. 【疑问】§一·P3：五个 SKILL.md 属仓库文件，更新依赖 AI 自觉遵守；建议在 P1 就把 GET value-domains 接到 query-governance-intake 的强制步骤（已有技能路由机制），而非全部推迟 P3。
6. 【同意】§一·架构分层（平台库权威+三层获取+pending/confirmed 状态机+版本表）方向正确；Q4 库为权威、文档为导出视图的取向正确。
7. 【疑问】§一·P4 二期：ingest 字面量告警依赖 SQL 解析器，与注入共用，若 P1 已建解析能力，P4 告警增量小，可考虑提前至 P1 末尾做最小版（只比对等值字面量）。

## 结论

架构方向正确；数据模型对"多来源记录（关注点2）"和"冲突检测（关注点3）"支撑不足，建议证据子表化+写入时冲突检测，其余为收敛性问题。
