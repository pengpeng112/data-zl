• # 独立审查结论：review/round-8/方案.md

  ## 总体判断

  方案的四条发现线（S/C/A/V）设计扎实、确实瞄准"增量发现问题"而非空转，对"不确定项单列"的响应也到位。但存在**三个必须修正的硬伤**和若干可行性风险，其中"编号冲突 + 现状底座已过期"属于会直接导致执行混乱的阻断级问题。

  ---

  ## ① 对用户需求的覆盖度与忠实度

  | 需求要点 | 覆盖情况 | 评价 |
  |---|---|---|
  | 一次性免费 AI、单会话执行 | §3 T0→T6 顺序批次 + checkpoint + PARTIAL 续批 | 覆盖，但见风险 R4 |
  | 全部前端+后端模拟测试 | §2 四线覆盖后端全路由+前端全 api 文件+全源码 | 覆盖合理，且 §4 铁律 6 如实声明不含真实浏览器层，属于诚实缩界而非漏项 |
  | 能核查出问题（非重跑绿测试） | §2 明确"既有 1300+245 绿测试重复无意义"，只做增量发现 | **忠实度最高的一点**，策略正确 |
  | 问题记录 MD | §3 T6 + §5 模板（P0–P3 分级、每条带证据） | 覆盖完整 |
  | 不确定项完成后单独告诉 | §2 三③ + §5 模板"三、不确定项"独立节 + DoD | 覆盖完整，且"两种可能解释+建议核查方式"的字段设计超出需求 |
  | token 不设限、要有测试效果 | §3"token 不设限"+ DoD"探针总数≥1000、四线各有执行证据" | 覆盖 |

  **缺口（唯一一处忠实度问题）**：用户原话结尾是"请生成计划**给出提示词**"——交付物应包含可直接喂给那个一次性 AI 的**执行提示词**。方案 §0 拆解第⑧条自己承认了这一点，但 §3 T6 的产出清单和 §6 DoD 里**都没有"提示词"这一项**。若按此方案定稿，产出物将缺了用户点名要的一半。建议：在 T6 增加"执行提示词（含四线脚本骨架、铁律、分批指令、不确定项呈报格式）作为正式交付物，并在 DoD 加验收项。

  ## ② 自发发现的问题

  **P0-1：编号冲突与越号（违反仓库强制规则，§1/§3 T6/§5/§6）**
  方案自称"170 号草案"，产出 `开发起步包/170_全栈模拟测试_问题清单.md`。但我实测 `开发起步包/` 目录下**已有 171_（3 个文件）和 172_**，即当前最大编号是 172。按 AGENTS.md 强制规则"续用当前最大编号 +1"，新文档应为 **173_**。此外"170"这个号实际上已被占用：`开起步包/output_r170/` 下的 import170/export170 重灌工装（171 报告 W1 明确引用）已把 170 用作隔离库重灌工装编号，方案再用 170 会与既有资产混淆。

  **P0-2：现状底座已过期（§1）**
  方案标注"2026-08-31 校准，禁止重探"，但我读取 `开发起步包/171_..._执行报告.md` 显示 171 已于 **2026-09-01 完成闭环**：后端实测 1341 passed（方案写 1327，差 14+）、前端 vitest 253/253（方案写 245）、新增 system-map 页面、生产已切 r171-20260901、167 后端已在产。方案的"现状底座"和"禁止重探"指令会让执行 AI 拿着过期基线跑，T0 的"只记录不修"基线对照会全部对不上，直接误判成"基线退化"。修正：以 171 执行报告为最新底座，重新校准数字。

  **P1-1：工作区状态描述失真（§1/§4 铁律 3）**
  §1 称"工作区存在多会话未提交改动（执行 AI 禁 checkout/stash）"。但 171 报告 §0 显示 R1 已完成四域提交（169/167/170/171-卫生），剩余"他人域"19 文件。该禁令方向仍正确，但描述的范围已变。执行 AI 若按旧描述决策会误判哪些是"禁动域"。

  **P1-2：C 线"14 个 api ts"含 types.ts（§2 C 线/§3 T3）**
  我实测 `frontend/src/api/` 共 14 个文件，但 `types.ts` 只是通用类型定义（ApiResponse/PageData 收敛文件，实测确认无请求），真实请求模块是 13 个。比对脚本若按"14 个"统计会出现一个永远 0 命中的文件，无伤大雅但会让"漂移率"统计虚增分母；同时 13 个模块中 admin/auth-admin 等命名也可能误判。建议明确"排除 types.ts，实测 13 个请求模块"。

  **P1-3：T2"逐条读路由源码定性"对一次性免费 AI 是最易卡死的环节（§3 T2）**
  S 线预计产生数百条偏差候选，逐条读路由源码定性是真发现问题的前提，但也是最烧上下文的一步。免费 AI 单次会话的上下文/token 上限是硬约束——若免费额度只够跑完扫荡而没余力做逐条源码定性，清单就会变成"偏差原始堆叠"，违背"一定要能查出真问题"的目标。建议：T2 增加"预算保护"规则——偏差按路由聚合去重、按鉴权类/校验类/声明漂移类分桶，先吃最容易出真 bug 的桶（声明 200 实际 500），其余可批量定性。

  **P1-4：90 分钟超时记 PARTIAL 与"一次性"目标冲突（§3）**
  单批 90 分钟超时是必要的保险丝，但也意味着"一次性执行完成"实际上是"一次会话分批执行"。建议在方案里明确告知用户这个现实：一次会话≈4-6 小时级，需说明 PARTIAL 状态下哪些产物已可用，避免用户对"一次性"的预期落空。

  **P1-5：探针矩阵的环境前提偏乐观（§3 T0/T1）**
  后端全量 pytest 实测 27m43s（171 报告），Vitest 约几秒，加上写探针脚本、跑 1000+ 探针、再读 333 条路由源码，对"只能用一次的免费 AI"而言大概率会触发会话上限。PARTIAL 意味着任务可能中断。建议：把"最低可交付结果"前置——先跑最容易出真问题的 C 线和 A 线（脚本型、低依赖），把 S 线的逐条源码定性放最后，这样即使会话中断也已拿到最硬的问题清单。

  **P2-1：探针总数≥1000 的证据标准偏松（§6 DoD）**
  1000 个探针本身不代表发现了问题，只代表跑了 1000 次请求。真正的有效性指标应是"偏差候选→定性为真 bug 的比例"和"不确定项→闭环的转化数"。DoD 建议补一条"P0/P1 级问题≥N 条或说明为何为 0"。

  **P2-2：T1 的探针可能误伤写路由（§2 S 线）**
  "写类路由只测鉴权+校验探针（不真实执行）"是个好约束，但实操中"类型错"探针如果服务端校验不严，可能穿透到 handler 执行真实写操作（尽管是测试库）。建议补一条：写类探针固定使用"缺失必填字段"这一种最安全 payload，类型错探针只用 GET 做；POST 只用"空 body/缺鉴权头"两种。

  **P2-3：序号引用混乱（§3 T3 的 tools/check_api_contract.py）**
  `tools/` 按 AGENTS.md 应放"开发起步包"类资产，脚本进 `tools/` 没问题，但 `check_api_contract.py` 这种通用名会与既有 `tools/export_value_domains_json.py` 等并列，建议加 `_r170` 前缀避免与既有工具混淆。

  **P3-1：前端 Vitest 基线数字未引用 output_r171 的实际值（§1）**
  前端 253/253、后端 1341/1/0 是 09-01 的实测；方案引用的仍是 08-30 的 245/1327。这种 14/8 条的偏差在"只做增量、不重造"的铁律下会被放大成"假偏差"。

  ## 结论

  方案**方法学正确、风险意识强**（白名单、只测不修、只测不写、不确定项独立成节都是优点），但**不能直接交付**。需修正：编号改 173、底座对齐 171 完成态、C 线排除 types.ts、补"执行提示词"交付物、T0 基线对齐 09-01 实测、T2 增加分批定性策略。
