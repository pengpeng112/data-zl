这份方案**方向基本符合需求，但还不能直接交给另一 AI 执行**。保留现有编号体系、复用查询治理工具、不另建平行状态库，这些取舍合理；主要问题在于：现状统计存在错误，迁移步骤与仓库实际约束冲突，对查询生命周期、多 AI 协作和快速检索的设计仍不完整。

本次全程只读，未修改文件、未连接数据库。核查了方案、仓库入口、184 号历史复盘、查询模板、相关工具及 GitHub/官方资料。目录检查实际结果为 **error 1 / warn 1 / info 18**，错误和警告分别是 181 正文与输出目录未登记；没有把已识别的同号配套误报为冲突。以下历史判断基于仓库复盘与记录，未重新分析全部原始聊天。

**优先修正的执行问题**

1. **计划要求移动已明确保护的他人域文件，内部冲突。**  
   §3.6 要移动六个 `capture_*.py`，§4 又要求“他人域文件零触碰”。实际 `tools/dev_env.sh` 的 `OTHER_DOMAIN_FILES` 明确包含其中五个采集脚本，不只是所谓“前端 9 文件”。按现方案执行，会破坏它自己要求保留的域基线。应在 P0 根据当前协作状态逐文件确认归属，再确定可迁移清单。  
   出处：方案 §3.6、§4；[dev_env.sh](/F:/python/数据资产/tools/dev_env.sh:13)。

2. **“全程 git mv”无法处理主要迁移对象。**  
   `.gitignore` 明确忽略根目录 `_tmp_*`、`取数/exports/`、离线构建目录等；本次 `git ls-files` 也未列出 exports 和 `_tmp_*`。这些未跟踪文件无法直接按方案统一 `git mv`，更不可能统一验收为“git status 可见纯 rename”。不能为满足该验收而强制纳入 Git。  
   应区分已跟踪、未跟踪、已忽略三类：分别采用合适的移动方式，并对非 Git 资产做清单和哈希验证。  
   出处：方案 §4 P1、执行边界、§6；[.gitignore](/F:/python/数据资产/.gitignore)。

3. **根目录验收目标排除了必须保留的文件。**  
   “仅 3 入口文件”遗漏 `.gitignore`、`.gitattributes`、`start_backend.bat`、`start_frontend.bat`、`三仓库互通地图.md` 等实际文件；地图还是 AGENTS 指定的跨仓库权威入口。目标树自身列了 11 个原有核心目录，验收却写 10 个。  
   应改成“允许保留清单＋待迁移清单”，不能用固定数量驱动清理。  
   出处：方案 §3.1、§5；根目录实际清单；[AGENTS.md](/F:/python/数据资产/AGENTS.md)“三仓库互通”。

4. **取数目录计数错误，使验收无法成立。**  
   实际 exports 有 **14 个目录，其中 3 个无编号**。编号缺位不是第四个无编号目录，当前还存在 8 号缺位。给三个目录改名后仍是 14 个目录，不会成为 §4、§5 的 17 个。14、15、16 的拟编号目前可以成立，但执行时仍须重新核对最大号。  
   出处：方案 §1、§2、§3.2、§4 P2、§5；`取数/exports/` 实际目录。

5. **只针对“顶层散 SQL”的整理规则没有覆盖实际查询分布。**  
   当前 `取数/` 顶层没有散 SQL，SQL 分布在 exports、`48项目核心制度/`、`_query_working/`、`_query_outbox/`、`工作量日报/` 等子目录。本次统计分别发现 115、39、16、13、3 个 SQL，另有模板 1 个。  
   若按“顶层”执行，会漏掉真实对象；若按“exports 外全部”执行，又可能误搬工作流包和明确要求保留的试点目录。必须先给各子目录指定处理规则。  
   出处：方案 §3.2 第 2 条；[START_HERE.md](/F:/python/数据资产/取数/START_HERE.md)“推荐目录”；实际 SQL 路径统计。

6. **采集脚本迁移属于代码变更，不能只做文档验收。**  
   六个采集脚本使用 `Path(__file__).resolve().parents[1]` 定位仓库根。移动到 `tools/capture/` 后，该表达式会指向 `tools/`。例如 `capture_competition_screens.py` 由此构造 `backend/scripts` 的导入路径，迁移后会失效。  
   方案虽写“更新其内引用”，但没有列明这种动态依赖，也没有对应测试。至少应验证根路径、导入路径和输出路径；不应为验证整理结果直接运行会访问生产的采集流程。  
   出处：方案 §3.6、§4 P5；[capture_competition_screens.py](/F:/python/数据资产/tools/capture_competition_screens.py:19)。

7. **只搜旧路径不足以证明“全仓无断链”。**  
   相对链接可能在文件移动后失效，但正文并不包含旧完整路径；动态拼接路径也一样。默认搜索还可能漏掉 ignored 文件，而本方案大量对象恰好被忽略。  
   应明确搜索范围、忽略目录例外、Markdown 相对链接解析，以及脚本路径检查。否则“grep 验证”只能作为部分证据。  
   出处：方案 §4、§5；上述采集脚本的动态路径实现；`.gitignore`。

8. **回滚设计不能覆盖未跟踪数据和中途失败。**  
   “反向 mv”“目录名还原”“revert”没有解决目标已存在、部分移动成功、后续新文件写入、README 和链接已经修改等情况。Git 回滚也恢复不了未跟踪导出数据。  
   每批应有旧路径→新路径映射、跟踪状态、文件数量/大小/哈希、碰撞处理、恢复顺序和停止条件；避免回滚覆盖后来其他 AI 的改动。  
   出处：方案 §4 回滚列、§6。

**查询与 Markdown 治理仍缺关键设计**

9. **任务 README 与既有查询包元数据的关系未定义。**  
   现有 `query.yaml` 已包含 `query_code`、`source_code`、方言、粒度、参数、敏感级别、关系配方引用及 AI 来源。再在任务 README 手填一遍数据源和口径，很容易产生两个不一致的描述。  
   应明确：平台维护查询权威信息，查询包承载本地缓存，任务 README 记录交付关系；重复字段引用或生成，不另立权威。  
   出处：方案 §3.2、§3.4；[query.yaml](/F:/python/数据资产/取数/_query_templates/query.yaml)；START_HERE“平台是唯一事实源”。

10. **仅记录 query_code，无法还原某次导出的真实口径。**  
    同一查询可以有多个版本，同一版本可以按不同月份、科室多次运行。只有 query_code 清单，无法判断某个 Excel 使用的是哪个版本、哪些参数、何时执行。  
    应定义最小交付追溯字段：查询版本或 SQL 哈希、参数、执行时间、run 标识（存在时）、输出文件映射及必要校验摘要；离线查询允许字段缺失并明确原因。  
    出处：方案 §3.2 第 3 条；START_HERE 硬规则第 5 条“参数只产生 run，SQL/口径变化必须新 version”。

11. **“有 query_code 就移对应任务目录”缺少一对多处理规则。**  
    一条可复用查询可能支持多个任务，一个任务也可能组合多个查询。将查询实体按任务搬走，会削弱复用，并可能破坏 `queryctl` 对 `query.yaml + query.sql` 成包的要求。  
    应区分“可复用查询包”和“某次交付快照”，规定引用方式，不能只凭 query_code 决定物理归属。  
    出处：方案 §3.2 第 2 条；[queryctl.py](/F:/python/数据资产/tools/queryctl.py:119)。

12. **导出数据只讨论摆放，未定义长期管理。**  
    缺少 SQL、汇总结果、患者明细、缓存、正式交付之间的保存规则，以及接手 AI 能读哪些内容、哪些只允许读取脱敏元数据。全部 gitignore 不能解决跨机器交接，也不等于访问控制。  
    应补充受控存储位置、可检索摘要、保留/清理条件及恢复来源，并沿用现有“结果默认不保存”的规则。  
    出处：方案 §3.1、§3.2、§6；START_HERE 硬规则第 2、6 条；`.gitignore` 的取数目录规则。

13. **MD 治理重点偏向搬证据目录，没有解决入口文档本身的可读性。**  
    184 已明确记录 README 超长导致上下文超限；当前 README 的“状态定义”表还混入多条带日期的更新事件，“当前完成度总览”标注 2026-08-24，而当前入口已有 9 月进展。这些会直接影响新 AI 判断现状。  
    方案应安排入口结构核对、最新状态与历史记录的区分、按任务切片读取方式，而不只是给文件加索引。  
    出处：方案 §3.3、§3.4；[README.md](/F:/python/数据资产/开发起步包/README.md)“状态定义”“当前完成度总览”；[184 号报告](/F:/python/数据资产/开发起步包/184_AI协作复盘_高频流程沉淀与中断分析报告.md) §5“上下文”。

14. **文档编号不能直接作为唯一标识。**  
    目录检查确认，149、174 等编号下存在不同主题文件；还有大量计划、执行报告、结果文件共用编号的正常形态。manifest 若以编号为唯一键，会覆盖条目或误关联。  
    应以完整相对路径或独立稳定标识区分文件，编号只作为关联字段，并区分“同任务配套”与“不同主题同号”。  
    出处：方案 §3.4；`check_doc_index.py` 本次输出；README 对同号文档的登记。

15. **机器索引缺少防漂移契约。**  
    没有规定状态从 README、55 还是正文读取；没有 schema 版本、生成来源、过期判断、失效回退和禁止手改规则。“gitignored 可选；建议入库”也把关键决策留给执行者。  
    特别是当前方案允许用 manifest 替代 glob，但过期 manifest 恰好会漏掉新文件。应明确它只是生成视图，不能取代当前事实核验和权威入口。  
    出处：方案 §3.4；AGENTS 启动目录自检要求；README 和 55 的权威定义。

16. **一个全量 JSON 未必让不同 AI 更快找到内容，当前没有验证方法。**  
    方案只要求“生成且被引用”，没有定义按业务词、系统、查询码或任务状态怎么检索，也未说明大文件如何分片读取。  
    应至少用实际任务验证：找现行查询、找最新执行报告、找待办、找脚本用途、找离线资产。记录命中是否正确、读取文件数量和是否误入旧计划。  
    出处：方案 §3.4、§5；用户需求“不同 agent AI 快速获取”；184 §5 上下文超限证据。

17. **索引将本地忽略资产的信息带入 Git，缺少字段边界。**  
    §3.4 同时索引 exports、临时脚本和 artifacts，并建议入库。文件名、用途说明、docstring 也可能带内部信息，不能认为“不读文件正文”就天然可公开或跨 AI 传递。  
    应区分可入库公共索引和受控本地索引，对允许字段、排除路径、敏感信息检查作明确约定。  
    出处：方案 §3.4；`.gitignore` 对临时脚本“可能含凭据”的说明；START_HERE 第 6 条。

18. **output_r 生命周期规则既矛盾，也不适合按编号直接执行。**  
    “最近 3 轮”列出 r180、r181、r185、r186 四轮；较旧目录又可能含仍在使用的工具。例如 `dev_env.sh` 当前仍提示使用 `output_r170/import170.py`。  
    “被引用者保留”能保护部分对象，但应先区分活动工具、证据、缓存和回滚材料，再决定归档；同时说明未完成计划引用、外部引用如何处理。  
    出处：方案 §3.3；[dev_env.sh](/F:/python/数据资产/tools/dev_env.sh:89)。

19. **现有目录检查器不会检查新归档的 output 子目录。**  
    `scan_package()` 扫 `_archive/` 时只处理顶层文件，跳过子目录。将 `output_r*` 移进去后，当前检查器无法证明里面的证据得到完整登记。P4 只写扩展取数/artifacts 联检，没有明确补这个盲区。  
    出处：方案 §3.3、§4 P3/P4；[check_doc_index.py](/F:/python/数据资产/tools/check_doc_index.py:87)。

**多 AI、调研依据及计划完整性问题**

20. **目录守护表和“尽早提交”不足以解决历史互踩。**  
    域哈希只能发现变化，不能预防两位 AI 同时修改 README、55、manifest、编号或同一查询任务。提交也不是文件锁；测试库互清和发布竞态更不是目录归属能解决的。  
    应补充当前任务认领、共享文件单一整合者、编号分配串行化、冲突后的接手协议，以及共享测试资源占用规则。是否采用独立 worktree 可以评估，但必须说明 ignored 查询数据如何供不同工作区使用。  
    出处：方案 §3.5；184 §5、§7；dev_env.sh 的哈希基线实现。

21. **历史聊天依据存在，但覆盖深度未达到方案声称的程度。**  
    方案基本只引用 184 的二次复盘，没有给出与查询散落、目录命名、跨 agent 找文件直接相关的会话样例或最近 9 月会话核对范围。并且把 184 的 **11,531 条消息**写成 11,311 条。  
    不必重新读全部聊天，但应说明“使用既有复盘＋哪些新增样例”，为关键建议附会话编号、日期或可定位证据；不能把二次摘要写成此次已完成的全面历史分析。  
    出处：方案 §1、§7；184 报告首部、§3；[export_zcode_conversations.py](/F:/python/数据资产/tools/export_zcode_conversations.py)。

22. **GitHub 调研证据不足以支撑当前采纳结论。**  
    §8 主要是官网和博客，没有列出具体 GitHub 仓库的目录实例、文件路径、适用限制及本仓取舍。不能据此断言没有搜索过，但交付材料无法复核“从 GitHub 借鉴了什么”。  
    本次能核实的官方仓库包括 [agentsmd/agents.md](https://github.com/agentsmd/agents.md) 和 [dbt-labs/jaffle-shop](https://github.com/dbt-labs/jaffle-shop)。修订稿应将调研落到具体文件或机制，并说明哪些仅借鉴理念、哪些实际引入。  
    出处：方案 §2、§8。

23. **dbt、Diátaxis、ADR 的类比过强。**  
    dbt 官方把 analyses 用于可版本管理、可用 Jinja、但不物化为模型的查询，不等于混放 SQL 与 Excel 的交付目录；Diátaxis 按教程、操作指南、参考、解释分类，也不等于按状态和证据类型分组；编号报告本身不自动成为架构决策记录。  
    可以借鉴，但应明确差异，不能以“≈ 已成立”“同构方案”跳过适配分析。  
    出处：方案 §2；[dbt 官方说明](https://docs.getdbt.com/best-practices/how-we-structure/5-the-rest-of-the-project)、[Diátaxis](https://diataxis.fr/)、[ADR 官方入口](https://adr.github.io/)。

24. **执行计划遗漏正文承诺，部分验收依赖倒置。**  
    §3.6 的 capture 分组没有进入任何明确批次；§1 识别 backend/scripts 混放，但后续只索引用途，没有分类处置或明确延期。P2 要求“check 工具通过”，相关扩展却在 P4 才开发；P5 才同步规则，前面已开始迁移。  
    应补一张“问题→措施→批次→产物→验收”的对应表，先完成规则、迁移清单和检查能力，再分批移动。  
    出处：方案 §1、§3.6、§4。

25. **验收会把未解决问题算作完成。**  
    “散 SQL 归属率 100%（含待决清单）”把已发现和已治理混为一谈。可以要求盘点覆盖 100%，但应分别报告已归属、保留原位、待判定数量。  
    同时，“error=0”和“既有 181 他人域除外”应改为精确基线差异检查；本次实际还有 1 个 error，不能口头豁免后宣称工具全绿。  
    出处：方案 §4、§5；本次目录检查结果。

26. **只移动旧产物，没有阻止新产物继续散落。**  
    frontend 的日志、根目录临时脚本、P0“review 外工作记录”都没有统一的新建路径、任务命名和生成入口规则。整理后，下一位 AI 仍可能按原习惯写回原处。  
    应补充“新文件从哪里产生”的约定，必要时调整生成脚本的默认输出，并给 artifacts/_scratch 按任务建立最小归属信息和生命周期。  
    出处：方案 §3.1、§4 P0/P1；现有 frontend 日志与根目录临时文件清单。

我建议保留这份方案的整体方向，但先修成**可复核的治理规范＋逐项迁移清单＋防回退机制＋行为验收用例**。其中第 1–8 条应在交给执行 AI 前解决；否则执行者仍需自行作出大量影响范围、数据保留和路径兼容性的决定。
