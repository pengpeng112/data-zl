1. **【需求覆盖自评】** 用户四要素（定期只读巡查/合并优化现有界面/固定数据中心演示/换模型证明在应用）+AI 写 SQL+好看直观——§3/§4/§5 逐条映射；H1–H6 假设显式列出待校验，无"私自加戏"（定时调度/live 采样均推等待域）。
2. **【缺口·巡查数据新鲜度】** A 的指标摘要全取平台库（H3），但平台元数据/QualityFinding 可能陈旧——演示场景可接受（剧本固化），巡查历史若长期使用会"分析的是旧数据"。方案未声明数据时点标注。建议：结果卡标注"指标数据截至 <质量规则最近 run 时间>"。
3. **【缺口·jobs 模型复用细节】** 复用 ai_quality jobs 落库 type=patrol——jobs 表是否有 type/scene 字段可区分？若需要加列则违"零迁移"。执行 AI 须先读 jobs 模型确认；若无区分字段，降级方案=独立结果文件+审计（不入 jobs 表）或复用 note/标签字段。此为 S1 第一验证点。
4. **【缺口·演示集选取脚本】** H2 说"S1 在隔离库跑质量规则选 top 问题表"——隔离库的 QualityFinding 是测试数据，选出的"问题表"在生产可能不成立。演示集应以**生产平台库只读查询**（质量规则最近结果）选取，或直接用已知真实问题（164 §2 同源结论的 ODS 镜像表）。需在 S1 写明选取数据源与只读授权边界。
5. **【疑问·generate 的 LLM 输出稳定性】** hospital_llm（deepseek-r1）生成 SQL 可能带思考过程/markdown 围栏，需解析与失败重试策略；max_tokens 1800 对复杂 SQL 可能不够——方案未提。建议 B2 补：输出清洗（围栏剥离）+截断检测+一次重试。
6. **【疑问·累计调用次数来源】** "审计聚合"每次 status 查询聚合全表可能慢；建议首次实时聚合+缓存（或 count 审计行本身有索引）。小点，S1 处理。
7. **【同意】** A/B 全复用既有端点与安全通道（propose-sql/try-run/risk-scan/context resolve）；零迁移边界；S1–S5 划分与验收颗粒度；演示离线回放兜底设计。
8. **【风险提示】** ai-quality 页重构触碰 446 行现状页——需保留既有功能回归（分析任务/治理简报 Tab 不降级），S2 验收应加"现状功能回归测试"。
